# G7: `check`

Status: done, 12 October 2026.

## The contract

From BETA.md: `check`: the in-memory copy's consistency, a damaged batch
named, sizes reported. Done when planted damage in memory and in files is
reported.

## What was built

- **`beta/internal/store`**, in new files only:
  - `check.go`: `Store.Check`, the store's own check, which returns a
    `Checked` with the four counts, `Bytes` and `Problems`. It reads the
    whole copy once, as a read, and leaves the write path as it was. It
    checks each table's shape, each table's keys in byte order with their
    records, the hash table, each record's fields, every link at both ends
    with its mirror and every list in order, and every vector in its
    table's array: laid out for the table's size, finite and not all zeros,
    with the norm its values give, and the slots in use one for each
    record with a vector, every free slot on the free list once.
  - `memory.go`: the copy's size, added up from its parts at the sizes Go
    lays them out, each block rounded up as Go's allocator rounds it.
  - `checkplant_on.go` and `checkplant_off.go`: three planted bugs in the
    check, in a pair of files of their own, since `plant_on.go` can't
    change this round.
  - `check_test.go`: the store's half of the closing test, and three more.
- **`beta/internal/logfile/applied.go`**, new: `Log.Applied`, how far this
  process has applied the log, the file by device and inode and the end of
  its log there. It reads the position the log already publishes for
  `Follow`, and takes no lock.
- **`beta/hypercrux`**, the public package:
  - `check.go`: `Check` in place of the count it had, `Report` with two
    fields beside 0.x's, `FileBytes` and `MemoryBytes`, and Check's own
    read of the file. `refuse` gives Export's and Import's refusal.
  - `export.go`: Export runs the copy's check in its read and refuses a
    database it finds problems in, and Import runs it before it reads any
    table.
  - `glue.go`: `DB.files`, the file calls the log goes through, kept for
    Check's read of the file, and `readStore`, a read that hands Export the
    copy itself. `read` and `readStore` share their start, `enter`.
    `hypercrux.go` has the field.
  - Five planted bugs in `plant_on.go`; `doc.go` says what Check does now.
  - Tests: `check_test.go`, new, and `checkhooks_test.go`, new, with
    `PlantProblems`, which has the copy's check find problems besides its
    own, for the package's tests of what it does with them.
- **`beta/conformance`**: `check.go`, new, with `CheckCounts`, on one
  engine, and `SameCounts`, on two. `betax` runs `TestCheckCounts`,
  `TestCheckCountsAs0xDoes` and `TestCheckCountsAfterAReopen`, and `zerox`
  runs `TestCheckCounts`. The three `doc.go` files say so.
- **Existing tests changed:** `api_test.go` takes `addedFields` (below);
  `file_test.go`'s `look` gives Check's counts and problems without the
  sizes, which a compaction or a reload changes; and
  `TestABatchThatBreaksTheRulesIsDamage` and `TestAReloadThatFailsPartway`
  expect the damage among Check's problems, where Check returned it as its
  error before. `calls_test.go` loses a comment that said G7 was still to
  come.
- `beta/plants.txt`: eight new lines.

## The result

- **Planted damage in memory is reported.**
  `TestTheCheckFindsDamageInTheCopy` damages a healthy store in 26 ways,
  one at a time, through the store's own fields: a link's half gone from
  either end, a link to or from a record that isn't in the store, a link
  type that breaks the rules, a list of links out of order or with an
  empty block, a table's keys out of order or miscounted, a record missing
  from the hash table or from its table's keys, a record in a table that
  isn't there or under another key, a key in another table's keys, fields
  out of order or holding a null, a vector of zeros, a value that isn't a
  number, a wrong norm, free slots off the free list or on it twice, a
  slot held for a record that's gone, a record whose slot is free, vectors
  in a table without a vector size, a table's vector field or index out of
  step with its fields. Each gives the exact problems wanted, in words like
  0.x's where 0.x has the same problem, such as "links listed only at the
  record they're from: docs:1 -cites-> docs:2" and "the vector of docs:1
  is all zeros". Where damage has a second true consequence, the case
  names it too: a list of links out of order can't be searched, so both
  its links read as listed at one end.
- **Planted damage in files is reported.**
  - `TestCheckNamesDamageInTheFile` damages the file of an open database
    in place, after its copy has read all four commits, in each of the
    ways the damaged fixtures damage batch 2, and the header, and cuts the
    file short. No read sees damage in a part of the file it has read, so
    reads go on. Check's own read of the file names each one: "the file is
    damaged: batch 2 at offset 159: the checksum is 0x..., where CRC32C
    gives 0x...", at the batch's start for its head and its checksum, and
    at its marker's offset for its marker. The copy's counts come with it,
    and a fresh Open then fails on the file with `ErrDamaged`. The cut is
    damage the read before Check meets, named once.
  - `TestCheckNamesTheDamagedFixtures` moves each of the 29 fixtures in
    `damage.txt` into place under an open database. Its next read reloads
    the file and fails, and Check names the batch and the offset that
    `damage.txt` gives, with the file's size and no counts. No fixture
    changes by a byte.
  - `TestCheckNamesABatchRefusedAtAFollow`: a batch that breaks the rules
    for the state, written beside an open database, is named at its
    offset with "change 2", beside the copy's counts before it.
- **After a failed reload,** a read error gives Check that error, and once
  the file reads, Check counts again. While an Update holds the write lock
  after a reload that failed on damage, Check's read doesn't reload, and
  Check names the damage from `DB.unread`, with nothing of the copy.
- **A check while a writer commits.** `TestCheckWhileAWriterCommits` runs
  Check through two handles on one file while one of them commits a chain
  of 200 records with vectors and links, 60 with `-short`: through the
  other handle, as another process, and through the writer's own beside
  its Updates. One run made 228 checks. Each found no problems, a whole
  chain, and at least what the check before it found. It passes with
  `-race`.
- **The conformance suite.** `CheckCounts` passes on 0.x, on the Beta and
  on the Beta reopened before every read, with the same counts known in
  advance through deletes, a cleared vector, an unlink of every type, a
  failed Update, a drop and a reopen. `SameCounts` gives the same counts on
  0.x and the Beta after fill's calls, before and after a reopen.
- **Sizes.** `TestTheCopysSizeIsWhatItTakes` holds the copy's size to what
  the heap grows by as a store fills: 4,000 records with 384-value vectors
  came to 7,175,175 bytes against 7,165,352, 1,794 bytes a record, which
  BETA.md puts at about 1.7 KB. Records with fields and five links each
  came out at 0.988 of the heap's growth, and records with longer text at
  1.004. In `TestCheckReportsSizes` the file's size is its size on disk,
  and 1,000 records with vectors give 1,792 bytes a record, the same after
  a reopen.
- **Export and Import.** With a problem planted through `PlantProblems`,
  Check reports it, Export refuses with 0.x's words and writes nothing,
  and Import into a new database refuses with 0.x's words and keeps
  nothing. Once it's gone, both go ahead and give the same export.
- **The planted bugs are caught,** each by the test written for it:
  `store/check-skips-mirror`, `store/check-zeros-let-through` and
  `store/check-free-slots-counted` by `TestTheCheckFindsDamageInTheCopy`;
  `hypercrux/check-file-skipped` and `hypercrux/check-marker-at-the-batch`
  by `TestCheckNamesDamageInTheFile`;
  `hypercrux/check-follow-damage-dropped` by
  `TestCheckNamesABatchRefusedAtAFollow`; `hypercrux/check-reload-copy-read`
  by `TestCheckNamesTheDamagedFixtures`; and `hypercrux/export-unchecked`
  by `TestExportAndImportRefuseWhatCheckFinds`. The tests pass with the tag
  and no bug switched on. Run as `scripts/planted.sh` runs them, the
  store's are caught in 2 to 8 seconds and the package's in 12 to 14, most
  of it the build and the tests that run before these.
- **Speed,** timed by hand on the shared machine, twice: at 20,000 records
  with 384-value vectors and five links each, a file of 35 MB and a copy of
  41 MB, Check took about 80 ms. The copy's check was about 65 ms of it and
  the read of the file about 8.5 ms. Opening the same file took about 0.3
  seconds.
- `go vet ./...`, `go test -short ./...`, `go test -race -short` on
  `beta/internal/store`, `beta/hypercrux`, `betax` and `zerox`, and
  `sh scripts/check-beta.sh` pass. The new tests take about half a second
  in each package with `-short`.

## Decisions settled

**The store's check is a read of the store.** `Store.Check` runs inside
`Read`, or on a store a goroutine has to itself, and reads only what
changes under the copy's lock, so it races with nothing. Inside `Read` no
transaction's changes are in the store, so every free slot is on its free
list. It doesn't panic on a broken layout: a block that's empty is
reported, and nothing is looked up in it. Its counts are its own: records
in their tables' keys, links once at the record they're from, and records
with a vector, which are the slots in use when the copy is sound. When the
tables' keys account for every record in the hash table, each in order
under its own key, the hash table isn't read a second time.

**Problems in 0.x's words and form.** A kind of problem that names keys
gives the first five in byte order and how many more there are, and each
bad vector is a problem of its own, up to 20 a table, as in 0.x. Where 0.x
has the problem the words are 0.x's: "keys in docs that don't start with
docs:", "links from keys that don't exist", "links with a bad type", "the
vector of docs:1 has a value that isn't a finite number", "is all zeros",
"is there, but the table has no vector size recorded", and "and 3 more bad
vectors in docs". Where the Beta's copy has a part 0.x hasn't, the words
follow 0.x's: "keys in docs missing from the hash table" for 0.x's "rows in
docs missing from hc_keys", and "keys in the hash table with no place in
docs's keys" for "keys in hc_keys with no row in docs". The rest are the
Beta's own, such as "links listed only at the record they're to".

**Damage is a problem.** Check returns an error only when it can't check.
Wherever damage comes from, it's the report's first problem, "the file is
damaged: batch 2 at offset 159: ...", which is what `Damage`'s Error says
without the package's name and the path:

- **damage in a file Check reads:** Check's own read names it, and the
  counts are the copy's, which read the file before the damage;
- **a batch the log refused at a follow:** the read before Check meets it,
  and Check names it beside the copy's counts as the batch before left
  them, since a follow applies a batch whole or not at all;
- **after a failed reload:** the copy holds part of the file at the path,
  a batch in part among it, and no read sees it. A reload that failed on
  damage gives the report that problem and the file's size alone, and one
  that failed for another reason gives Check its error. Check reads
  `DB.unread` under the gate, so it names the damage also when an Update
  holding the write lock keeps its read from reloading.

0.x reports SQLite's integrity check the same way, as problems. A caller
that wants the numbers has them in the problem's text, or in the error of
any read, which carries the `*Damage`.

**Check reads the file again from its start,** as 0.x's Check reads every
page through SQLite's integrity check. Without it, a bit gone wrong in a
batch this process read hours before goes unseen until the next Open
fails, when the copy that could have been exported has gone. The read:

- goes from the start of the file to the end of the log this process has
  applied (`Log.Applied`). Bytes before the end of a marker never change,
  so it needs no lock and nothing it finds there can be a writer at work.
  What lies past that point is the follow's, which confirms what it finds
  under the lock;
- reads the file only when it's the one the copy came from, by device and
  inode, through `DB.files`, the fault layer's disk in tests;
- checks the header, then each batch's head, checksum and marker, and
  decodes no changes: this process took each batch's changes, or wrote
  them, and the checksum shows the bytes are as they were. It streams a
  batch through CRC32C a megabyte at a time, so a batch of any size costs
  that much memory;
- names a bad head or checksum at the batch's start and a bad marker at
  the marker's offset, and a file shorter than what this process read as
  the follower does, once.

At 100,000 records with 384-value vectors and five links each, five times
the size timed, Check would take about 0.4 seconds: about 45 ms to read the
175 MB file, and the rest the copy's check, mostly the links' mirrors, the
vectors' dot products and the walk that adds up the copy's size. Opening
that file takes several times as long.

**Sizes beside 0.x's fields.** `Report` keeps 0.x's five fields in 0.x's
order and adds two after them: `FileBytes`, the size of the file at the
path as Check found it, and `MemoryBytes`, the copy's size, which BETA.md's
row on memory asks for, so `GOMEMLIMIT` can be set a little above it. The
copy's size is an estimate. Go can't give one structure's memory, so
`memory.go` adds up each block of memory the copy holds, rounded as Go's
allocator rounds it, with Go 1.24's maps of groups of eight slots. It
leaves out each link type's text, which the unique package keeps once, and
the buffers the writes reuse. After a failed reload it's 0.

**`TestTheAPIMatches0x` allows the new fields** through `addedFields`,
"Report.FileBytes" and "Report.MemoryBytes". The Beta's struct is compared
with 0.x's with those fields left out, they have to come after 0.x's
fields, in that order, each with a comment, and 0.x's structs mustn't have
them. A field added anywhere else, or without a comment, fails the test.

**Export refuses a database Check finds problems in,** as 0.x's does, with
0.x's words: "hypercrux check finds problems in the file, so it isn't
exported; the first is: ...". It runs the copy's check in its own read,
before it writes anything. It doesn't read the file again. In 0.x the
file is the database, but in the Beta the copy is what an export writes,
and when a part of the file read long ago is damaged, the copy holds what
it held and an export is the way to save it. Damage the read meets as it
follows the file fails Export, as it fails every read.

**Import checks the database first,** as 0.x's does, with 0.x's words,
"so nothing was imported". It runs the copy's check inside its Update,
before the first change, once it has refused a database with tables. A
copy without tables holds nothing to check unless it's broken, so the check
costs next to nothing, and keeps 0.x's refusal. The Update's Lock has just
checked the end of the log, and the file isn't read again.

**The planted bugs:** `store/check-skips-mirror`, a check that takes each
half of a link for the whole link; `store/check-zeros-let-through`, a
vector of zeros taken; `store/check-free-slots-counted`, free slots counted
as vectors; `hypercrux/check-file-skipped`, Check reading the copy alone;
`hypercrux/check-marker-at-the-batch`, damage in a marker named at its
batch's offset; `hypercrux/check-follow-damage-dropped`, damage the follow
meets ignored; `hypercrux/check-reload-copy-read`, the copy after a failed
reload checked and counted; and `hypercrux/export-unchecked`, Export
writing a copy with problems.

## Notes for later tasks

- **G5, the command's `check` verb:**
  - Open fails on a damaged file with an error that carries a `*Damage`,
    so Check never sees that file. The verb can print it as a problem in
    Check's words, "problems in FILE:" and then "  - the file is damaged:
    batch 2 at offset 159: ...", exit 1, as 0.x prints problems. Those
    are the words of `damaged` in `check.go`: the error's text without
    "hypercrux: " and the path.
  - Otherwise it prints Check's report as 0.x's verb does, "ok: 2 tables,
    3 records, 0 links, 2 vectors", which the command suite looks for.
    The sizes can go on a line of their own after it, so 0.x's line stays
    as it is.
  - `hypercrux import FILE` follows the import with Check, as 0.x's does.
    Import has checked the copy already, so Check finds problems after an
    import only in the file.
- **R1, long runs:** `TestTheCheckFindsNothingTheWritesLeave` takes 3,000
  random steps, 600 with `-short`, checking the store after each, and can
  run longer from more seeds. The eight planted bugs join the run.
- **R2, the review:**
  - `MemoryBytes` is an estimate that rests on Go's runtime: its size
    classes and its maps. A Go release that changes them moves the
    estimate, and `TestTheCopysSizeIsWhatItTakes` fails once it's off by
    more than an eighth. CI runs Go 1.27, so the test there is the check.
  - Check's read of the file takes the ID and the generation from the
    header it reads. A file that another database's file of the same
    length was copied over in place reads as sound to it. The next
    writer's check of its last marker finds it.
  - Check's read of the file decodes no changes, so it finds no damage
    that keeps every checksum. Only applying a batch finds a change that
    breaks the rules for the state, as the follow and a reload do.
  - Export no longer exports a copy Check finds problems in, so a bug in
    the store that left a problem would stop exports until it's fixed,
    as in 0.x. Scan and Get still read such a copy.
  - `checkCopy` is a package variable that `PlantProblems` swaps in the
    tests, which run one at a time.
