# G6: Import and export in the Beta

Status: done, 9 October 2026.

## The contract

From BETA.md: import and export in the Beta: the same JSON lines as A2.
Done when going from 0.x to the Beta and back gives a byte-identical
export.

## What was built

- **`beta/hypercrux`**, the public package:
  - `export.go`: `DB.Export` and `DB.Import` in place of the stubs, through
    `internal/export`, the package 0.x's export and import use, so the two
    engines write the same bytes and read the same exports.
  - `doc.go` says what works now.
  - Six planted bugs, in `plant_on.go` and `beta/plants.txt`:
    `hypercrux/export-fields-sorted`, `hypercrux/export-unlocked`,
    `hypercrux/import-size-dropped`, `hypercrux/import-kept-in-part`,
    `hypercrux/import-twice-merged` and `hypercrux/import-over-tables`.
- **`beta/conformance`**:
  - `api.go`: `Export` and `Import` on the `DB` interface.
  - `export.go`, new: `RoundTrip`, an export and import round trip on one
    engine, and `Across`, a move from one engine to another and back, from
    0.x's TestExportImportRoundTrip, TestExportKeepsWhatTablesRemember and
    TestImportRefuses. They aren't in `Tests()` (see "Decisions settled").
  - `zerox` and `betax`: both adapters pass the two calls on, and betax's

    `TestExportAndImport` in each, and `TestMovingAcross` and

- **Tests,** in `beta/hypercrux`:

## The result

- **Going from 0.x to the Beta and back gives a byte-identical export.**
  `TestZeroxToTheBetaAndBack` takes A2's 40 random files, or 8 with
  `-short`: A2's generator, run through 0.x's API from A2's seeds, with
  subnormals, -0, the extremes, text with zero bytes and every length of
  UTF-8, empty and random bytes, and vectors of odd floats. The 40 hold 98
  tables, 970 records, 397 vectors and 190 links.
  - Each file's export goes into a new Beta database, whose export is the
    same bytes, and again after a reopen, which reads the import back from
    the file.
  - That export goes into a new 0.x file, whose export is the same bytes
    again. A2's dump of the two 0.x files, every value with its SQLite type
    and its bits, is the same.
  - Every key reads the same from 0.x and the Beta, with its links both
    ways, and so do each table's scan and Check's counts.
- **The Beta to 0.x and back.** `TestTheBetaToZeroxAndBack` runs A2's
  generator through the Beta's API from 20 seeds of its own, or 4 with
  `-short`. The same calls on 0.x give the same export, byte for byte. The
  Beta's export goes into 0.x, whose export is the same, and back into a
  new Beta database, whose export is the same before and after a reopen.
- **What tables remember.** `TestTheExportKeepsWhatTablesRemember` gives
  A2's exact lines from both engines: fields in the order they first came,
  a vector size with no vectors left, and a table with no records. 0.x's
  tables of plain SQL, adopted, with declared types and generated columns,
  come into the Beta as their export has them and go back unchanged. After
  the import the Beta still refuses a vector of the wrong size in the
  table whose vectors had gone.
- **0.x's refusals.** `TestImportRefusesWhat0xRefuses` gives 57 exports to
  both engines: broken JSON, exports cut short or run together, and ones
  that break the rules of table names, field names, keys, values, vectors
  and links, with records and links there twice. The Beta gives each the
  kind of error 0.x gives and 0.x's message, word for word. One database
  on each engine takes every case in turn, and after each the Beta's
  exports as an empty one, Check counts nothing, and its file keeps its
  size. Both refuse a second import, and an import over a table whose
  records have gone, with "already holds record tables", and both refuse
  garbage into a database with records as garbage. Once the table is
  dropped, both take the import.
- **Where the rules differ,** pinned by the same test and by
  `TestTheWidestTablesMoveBothWays`:
  - a vector size without a vector field, which 0.x keeps and the Beta
    refuses;
  - a link type that starts with a zero byte, which both refuse as
    invalid, 0.x in its link trigger's words and the Beta in its Link's;
  - a table of 2,000 fields, which 0.x's SQLite refuses with a plain error
    and the Beta with ErrInvalid and Put's limit. A table of 1,999 goes
    into both and exports the same from both. 0.x takes about 4 seconds
    over each, adding the columns one at a time, so with `-short` only the
    Beta's side runs.
- **A failed import changes nothing.** `TestAFailedImportChangesNothing`
  makes imports of 3,303 lines fail at the end: a record there twice, a
  vector of the wrong size, a link to a record the export lacks, an export
  without its end line, and input that fails to read, whose error comes
  back as it was. The database's file holds history, a table made, filled
  and dropped. Each time the database exports as an empty one, Check
  counts nothing, the file keeps its bytes, and a reopen reads it empty.
  Then the whole export goes in through the same handle, and a reopen
  reads it back.
- **A failed commit.** `TestAnImportWhoseCommitFails` fails the import's
  batch write, its sync and its marker write on the fault layer's disk,
  three seeds each. The import gives the disk's error, the database is as
  it was, and a reopen reads it empty, since the log cuts the batch back.
  A later import through the same handle goes in.
- **A cut in the power.** `TestAnImportCutAtEveryCall` cuts the power at
  each of the 8 calls an import of 50 records and 50 links makes on the
  file, four seeds each. 12 reopens found the whole import and 20 found
  none of it. None found part of it.
- **Cut short anywhere.** `TestImportCutShortAnywhere` cuts an export of
  294 bytes at every byte. Each cut is refused as "not a valid HyperCrux
  export" and nothing is kept, apart from the one that takes off the last
  line break alone, which goes in, as in 0.x.
- **One point in the log.** `TestExportReadsOnePoint` exports five times
  while another handle on the file commits a record and a link to the one
  before it, over and over. Each export imports, which needs its links to
  point at records in it and its counts to add up, holds a whole chain,
  and holds more than the one before.
- **An export that fails** at its writer, at 0 bytes, 100, half way, and
  just before the end line, gives the writer's error. What reached the
  writer is the start of the export without its end line, and Import
  refuses it and keeps nothing.
- **Calls and readers.** Inside an Update, Export goes ahead until the
  first change, giving what was committed, and then fails with
  `ErrInsideUpdate`. Import fails with it at once. From another goroutine,
  Export waits from the Update's first change until the commit. On a
  closed database, or one that was never opened, both give `ErrClosed`,
  and Export writes nothing and Import reads nothing.
  `TestReadsWaitForAnImport` feeds an import from a pipe: until its first
  table a read through its handle goes ahead, then reads through that
  handle wait until it commits and see all of it, and a read through
  another handle goes ahead throughout and sees nothing until the commit.
- **The conformance suite.** `RoundTrip` passes on 0.x, on the Beta, and on
  the Beta reopened before every read. `Across` passes from 0.x to the Beta
  and back, and from the Beta to 0.x and back.
- **The planted bugs are caught,** each by the test written for it:
  `export-fields-sorted` and `import-size-dropped` by
  `TestTheExportKeepsWhatTablesRemember`, `export-unlocked` by
  `TestCallsThroughTheDatabaseInsideUpdate`, and `import-kept-in-part`,
  `import-twice-merged` and `import-over-tables` by
  `TestImportRefusesWhat0xRefuses`. Run as `scripts/planted.sh` runs them,
  each is caught in 15 to 19 seconds, most of it spent in the tests that
  run before these.
- **Speed,** timed once by hand on the shared machine: an export of 10,000
  records with 384-value vectors, 42.5 MB, took about 0.5 seconds, of which
  one pass over the snapshot is about 15 ms. Importing it took about 1.4
  seconds and made a file of 15.9 MB.
- `go vet ./...`, `go test -short ./...`, `go test -race -short` on
  `beta/hypercrux`, `betax` and `zerox`, and `sh scripts/check-beta.sh`
  pass. The new tests in `beta/hypercrux` take 2.7 seconds with `-short`
  and 15 without, 7.8 of them 0.x making tables of 2,000 columns.

## Decisions settled

**Export: one read, two passes over the snapshot.** Export reads through
`read` in `glue.go`, so it follows the file first and then reads one point
in the log inside the copy's `Read`. In that read it ranges over the
store's snapshot twice. The snapshot comes in the export's order, the
tables by name, each table's records by key and the links by from, type
and to, apart from two things:

- It gives each table's records straight after the table, where an export
  lists every table first. So the first pass writes the tables and the
  second the records and the links. The first pass builds every put only
  to pass it by, which costs about 3 per cent of an export, so no call to
  list tables was added to the store.
- A put in the snapshot gives its fields in byte order of name, and an
  export gives them in the table's order. So each record's fields are put
  back in the table's order, by their places in the table's field list.

The vector goes to the writer as a `[]float32` from one buffer, which the
writer encodes at once. The writer checks the order of what it's given,
so if the store ever gave something out of order, the export would stop
there with an error. Every value in the copy is one Put took, or one a
batch brought that the store checked by the same rules, so the writer
takes all of them.

While the export runs, other processes carry on writing. In its own
process an Update waits from its first change until the export ends, as
it waits for any read, so writing to a slow `w` holds up that process's
writers. 0.x's writers carry on through an export.

**Import: one transaction.** The log's API commits a transaction as one
batch, and nothing else, so an import goes in as one Update:

- The export's first line is read before the Update, as 0.x reads it
  before its transaction. `ErrClosed` and `ErrInsideUpdate` come before
  anything is read, as for every other call.
- In the Update, a database with a table, even an empty one, is refused.
  Its snapshot starts with a table if it has one.
- Each table is made whole, in one CreateTable through `Tx.Apply`, with
  its fields in order and its vector size, as FORMAT.md says an import
  writes it.
- Each record's values go through `value.FromGo`, the conversion Put
  makes, in the table's order, and then through the store's Put, which
  checks them again. A record that's there already is refused, where Put
  would merge the two.
- Each link goes in as a Link change through `Tx.Apply`, which refuses a
  link that's there already, where the API's Link takes it as made.
- The checks come in 0.x's order, with 0.x's errors, so an export that
  breaks several rules at once is refused for the same one by both.

**What a failure leaves.** A refusal, input that fails to read, or an
export cut short ends the Update with an error, so its transaction rolls
back and nothing reaches the file, as for any Update whose function fails.
A commit that fails is cut back out of the file by the log, as for any
Update, or leaves the handle stuck with `ErrStuck` when the cut fails too.
A crash leaves the batch whole or gone, and the next writer's check marks
it or cuts it.

**A new file switched in** would suit a large import better, and needs
more than the log has, so the import doesn't use one. As one transaction,
an import's data is held twice more in memory, in the change list and in
the batch, beside the copy, and every other process reads and checks the
whole batch before it applies any. The log measures a file's live data by
what its last compaction wrote, so a new database that takes an import of
a megabyte or more is due for compaction at once, and the compaction after
a commit, once G5 adds it, writes the data again. Written as the
compacted part of a new file and switched in, the data would be written
once, in batches of any size, and other processes would reload it. It
would need:

- in the log, a call for the holder of the write lock that writes changes
  the log hasn't read into a new file beside the database, syncs it once,
  checks the path still names the locked file, renames it over and syncs
  the folder, and moves to the new file, as `Compact` does after writing
  a snapshot. The import would hand it its transaction's change list in
  place of `Append`, and the copy would keep the transaction's state.
- in FORMAT.md, a header that names no batch it continues from. A
  compacted part holds the state after the batch its header names, and
  the state before an import is empty. Continues-from fields of 0 in a
  later generation could mean a file that starts afresh, as after a
  restore. Without that, the import's batches would have to follow an
  empty compacted part as ordinary commits, which the log counts as data
  that may be dead, so the file would be due for compaction again at
  once.

**Errors.** The texts the command's tests look for are 0.x's exactly:
"hypercrux: invalid: not a valid HyperCrux export: ..." for input that
isn't a valid export, from `internal/export`'s `ErrFormat`, and
"hypercrux: invalid: the file already holds record tables; import into a
new file". A broken rule names its line, "hypercrux: invalid: line 4 of
the export: ...", wrapping `ErrInvalid` alone, as 0.x's does. An error
reading the input keeps its own kind. The rules package has 0.x's texts,
and the importer adds 0.x's own, such as "the record docs:1 is there
twice" and "a link to a key that does not exist", which 0.x's triggers
give.

**Two refusals of the Beta's own.**

- A table with a vector size and no field vec: a CreateTable can't carry
  one (FORMAT.md), and the store refuses it. P2.md's note offered
  refusing it or dropping the size. Dropping it would lose the size, and
  the round trip with it, so Import refuses: "table docs has a vector size
  of 3 and no field vec, which a table can't have in the Beta; make its
  dims null". 0.x comes to hold one only through plain SQL that goes
  around its API, or an import of an export written by hand.
- A table of more than 1,999 fields, Put's limit (`rules.MaxFields`), is
  invalid: "table docs has 2000 fields, and a table holds at most 1999". A
  CreateTable could carry 65,535, and then the table couldn't go back to
  0.x, whose SQLite refuses it with a plain error, "too many columns".

**The conformance suite.** `Export` and `Import` are on the `DB`
interface, and the types in `difftest` and `query`'s tests that wrap a
`DB` take them by embedding. `RoundTrip` and `Across` are functions each
adapter's tests call, outside `Run`. A test in `Tests()` needs a row in
beta/SQL.md's named tests, which `TestEveryNamedTestExists` checks, and
that file is the coordinator's.

**The planted bugs:** `hypercrux/export-fields-sorted`, each table's fields
and each record's written in byte order of name; `hypercrux/export-unlocked`,
Export reading the copy without its `Read`; `hypercrux/import-size-dropped`,
tables made without their vector size; `hypercrux/import-kept-in-part`, an
import that fails on a line committing what came before it;
`hypercrux/import-twice-merged`, a record there twice merged and a link
there twice taken as made; and `hypercrux/import-over-tables`, an import
into a database that holds tables.

## Notes for later tasks

  - `hypercrux export FILE` can be `Export` to standard output, and
    `hypercrux import FILE` `Import` from standard input followed by
    Check's counts, as 0.x's command prints them. 0.x's command creates a

    command suite's ExportAndImport checks that, with exit code 1 and the

    export", which Import gives.
  - An import commits one batch, so with the compaction after a commit, a
    new database that takes an import of a megabyte or more compacts at
    the end of the import's own commit, writing the data a second time.

  watch its memory. Its change list and its batch each hold about the
