# F2: Log and write lock

Status: done, 8 October 2026.

## The contract

From BETA.md: the log and the write lock: create, append, sync, marker,
reading on open; the mutex then `flock` with the 10-second wait; the device
and inode check. Done when batches survive a reopen, the lock times out
across processes, and a replaced file restarts the commit.

## What was built

- **The real file calls,** `fsys.OS`, in `beta/internal/fsys/os.go`, over
  `syscall`. P3's `File` and `FS` are unchanged.
  - Every open has O_CLOEXEC. `Create` uses O_EXCL, then `fchmod` for
    exactly the permissions asked for. `Sync` is fdatasync, `SyncDir` is
    fsync on the folder, and `TryLock` and `Unlock` are flock.
  - A call that fails with EINTR is made again, apart from close, which
    Linux finishes whatever it returns.
  - `ReadAt` and `WriteAt` loop over pread and pwrite until they're done.
    `ReadAt` returns io.EOF when the file ends first, as io.ReaderAt
    promises.
  - `RenameNoReplace` is renameat2 through `syscall.Syscall6`, with
    AT_FDCWD (-100) and RENAME_NOREPLACE (1) defined. Its number is in
    `renameat2_amd64.go` (316) and `renameat2_arm64.go`
    (`syscall.SYS_RENAMEAT2`, 276). On any other architecture,
    `renameat2_other.go` sets it to 0, and the call fails with an error
    matching `errors.ErrUnsupported`. The EINVAL renameat2 gives for a flag
    the file system lacks becomes an error matching both
    `errors.ErrUnsupported` and EINVAL.
  - Errors are `*fs.PathError`s, or `*os.LinkError`s for the renames, so
    `errors.Is` finds `fs.ErrExist`, `fs.ErrNotExist` and the errno.
  - `fsys.Umask()` reads the umask from `/proc/self/status`, since
    `syscall.Umask` would change it for a moment under every goroutine.
- **The log,** in the new package `beta/internal/logfile`:
  - `log.go`: `Open`, `Lock`, `Append`, `Unlock` and `Close`, with
    `Target`, `Options` and `DefaultWait`. A comment at its top says where
    each later task fits in, and each place has a comment of its own.
  - `create.go`: creating a database, making a database of an empty file,
    and removing leftover `.new-` files.
  - `read.go`: reading the header and the log, the check that what was
    read is still in the file, and a reader that reads through a window of
    up to 1 MiB.
  - `plant_off.go` and `plant_on.go`, with five planted bugs, which
    `beta/plants.txt` lists.
- **Tests:**
  - `fsys/os_test.go`: 11 tests of the real calls in a temporary folder,
    among them FD_CLOEXEC on every file, exact permissions under umask
    0o077, io.ReaderAt's promise, flock between two opens of one file,
    `RenameNoReplace` refusing to replace, and renameat2's EINVAL for an
    unknown flag matching `errors.ErrUnsupported`.
  - `logfile`: 31 tests in `log_test.go`, `lock_test.go`,
    `create_test.go` and `replace_test.go`, with `helpers_test.go`.
    `TestMain` sends a copy of the test binary to a helper's role, for the
    tests across processes: holding the lock, or racing to create a
    database.

## The result

- **Batches survive a reopen.** `TestBatchesSurviveAReopen` commits 36
  random change lists over 8 opens of one database, one or two batches
  under each lock. Every reopen hands back every batch in order, numbered
  from 1, and the file holds the header and each batch with its marker,
  byte for byte as the codec makes them. `TestALongLogReadsThroughItsWindow`
  reads 7,000 batches, 18 of them longer than the window, 30 MB in all, on
  opening and when `Lock` reads on.
- **The lock times out across processes.** A helper process takes the
  lock and commits a batch. With a 300 ms wait, `Lock` fails with
  `errs.ErrLockTimeout` once the whole wait is over. Once the helper lets
  go, `Lock` gets the lock and reads the helper's batch. With the default
  wait, `TestTheLockWaitsTenSeconds` gave up after 10.0 seconds. When the
  helper holds the lock for 400 ms, `Lock` waits and then gets it. Inside
  one process, the mutex keeps goroutines apart, and the wait covers the
  mutex and flock together.
- **A replaced file restarts the commit.** Another database is moved into
  place between two commits. The second commit resets the Target, reads
  the new file's two batches, and goes in as its third, and the old file
  keeps its one batch. It goes the same way when the replacement comes
  while the writer waits for the lock, as at the end of a compaction, and
  when an empty file replaces the database. With nothing at the path,
  `Lock` fails with an error matching `fs.ErrNotExist`, and starts again
  once a database is back. Another database copied over the file in place,
  an older copy of the same one, and a cut to the header are damage, and
  `Lock` writes nothing.
- **Creation:** a new database is exactly a header of generation 1, with
  mode 0o640 under umask 0o027. In 30 rounds of 6 goroutines, and 5 rounds
  of 4 processes, racing to create one database, every creator opened the
  same one, and nothing was left beside it. A creator that loses the rename
  removes its file and opens the winner's. Without RENAME_NOREPLACE,
  creating fails with `errors.ErrUnsupported` and leaves nothing behind. An
  empty file becomes a database at the first `Lock`, keeping its
  permissions, and another Log that had it open starts again on the new
  file. Leftover `.new-` files that can be locked go at the first `Lock`,
  and a locked one stays, as does every name of another shape.
- **The planted bugs are caught.** `sh scripts/planted.sh` reports 11 of
  11, the five new ones among them, in 41 seconds:
  - `logfile/no-inode-check`, the device and inode check left out, caught
    by six tests;
  - `logfile/one-try`, flock tried once without waiting, caught by four;
  - `logfile/any-marker`, a whole marker taken for the batch before it
    whatever batch it names;
  - `logfile/marker-before-sync`, which `TestAFailedCommitStopsAppends`
    catches too, since the marker of a batch whose sync failed is there;
  - `logfile/no-read-check`, the check that what was read is still in the
    file left out.
- `go vet ./...`, `go test -short ./...`, `go test -race` on `fsys` and
  `logfile` with and without `-short`, and `sh scripts/check-beta.sh` pass.
  `logfile`'s tests take 3 seconds with `-short`, 9 with the race detector,
  and 13 in full, since the 10-second wait runs on its own at the end.

## Decisions settled

**The log's API.**

| Call | What it does |
|---|---|
| `Open(files fsys.FS, path string, t Target, o Options) (*Log, error)` | opens the database, or creates it, and reads its header and every marked batch, handing each to `t` |
| `(*Log) Lock() error` | the write lock, the checks once it's held, and the read on to the end of the log |
| `(*Log) Append(changes []format.Change) error` | one commit, holding the lock: the batch, a sync, the marker |
| `(*Log) Unlock() error` | flock, then the mutex |
| `(*Log) Close() error` | closes the file, once a commit under way has ended |

- `Target` has `Apply(seq uint64, changes []format.Change) error`, called
  for each marked batch in order, and `Reset()`, called when another file
  has taken the path, before that file's batches. The log calls it from
  `Open` and `Lock` only, one call at a time. An error from `Apply` is
  damage: a `*errs.Damage` naming the batch and its offset.
- The transaction runs between `Lock` and `Append`, so `Lock` catches up
  first, as 0.x's BEGIN IMMEDIATE does. `Append` doesn't hand its own
  changes to the Target, which holds them already. A transaction with no
  changes, or whose function fails, calls `Unlock` alone. Each `Append`
  under one lock is a commit of its own.
- `Options.Wait` sets the wait, which is 10 seconds when it's 0. The tests
  use waits of 200 ms to 1 second, and one waits the real 10 seconds.
- A timeout says the path and the wait; `Lock` after `Close` gives
  `errs.ErrClosed`.

**The lock.**

- The mutex is a channel holding one token, so the wait for it can time
  out. It belongs to the Log. Two Logs on one database each have an open
  file of their own, and flock keeps them apart as it does two processes.
- flock is tried with `TryLock` after pauses of 1 ms, doubling up to 16
  ms, until the deadline, which covers the mutex and flock together. The
  last try comes at the deadline.
- Holding both, `Lock` compares the fstat of the locked file with a stat
  of the path. When they differ, the old file goes, the Target is reset,
  the file at the path is read from its start, and the loop locks that
  one. A restart keeps the first deadline. With nothing at the path, the
  commit fails.
- Then the check that what this Log has read is still there: the file is
  at least as long, and the 20 bytes of the last marker read, or the 68 of
  the header when no batch has been read, are as they were. A difference is
  damage, as FORMAT.md's "Writing" says.

**Creating a database.**

- A new database gets 0o644 less the umask, as SQLite gives 0.x's
  databases. `FS.Create` sets exactly what it's given, so the log takes the
  umask away itself. When `/proc/self/status` can't be read, the umask is
  taken as 0o077.
- The `.new-` name is the database's path with `.new-` and 12 random
  lower-case letters. The creator makes it with O_EXCL, locks it, and
  checks by stat that the name still leads to it, since a writer removing
  leftovers can take it in the moment before the lock. Then come the
  header, a sync, `RenameNoReplace`, the folder's sync, and only then the
  unlock.
- When the folder's sync fails, the creator removes the new database's
  name again. Nobody can have committed to it, since its lock was held
  throughout.
- An empty file stays empty at `Open`. The first `Lock` makes a database
  of it, under its lock, with its permissions, and its owner where `Chown`
  is allowed. If the folder's sync fails after that rename, the Log keeps
  the new file's lock until `Close`, and `Lock` returns an error that wraps
  `errs.ErrStuck`, as BETA.md has compaction do.
- Leftover `.new-` files are looked for at the first `Lock` of each Log. A
  name counts when it's the database's name, `.new-` and ASCII letters
  only. Such a file goes when it's a regular file, it can be locked, and
  its name still leads to the file locked.

**Reading.**

- The log is read through a window of up to 1 MiB, so a log of many small
  batches takes few read calls. A longer batch is read whole. The window is
  emptied after each read on, since what lies past the end of the log can
  change.
- A batch that counts is decoded even when there's no room for a marker
  after it, so changes in it that break the rules are damage, marked or
  not, as FORMAT.md says.
- A short read without the lock ends the log there for now, since the
  holder of the lock may have cut the file.

**What F2 leaves.** F2 reads to the end of the log and stops. Under the
lock, when the file runs on past the end of the log, `Append` refuses with
an error that wraps `errors.ErrUnsupported` and names F3, and nothing is
cut. The bytes a failed write or sync in `Append` leaves are such a tail,
until F5.

## Notes for later tasks

- **F3, recovery:** the check goes in `lockFile`, after `readOn`, in place
  of `l.tail = l.end < info.Size`. Open's try at the lock without waiting
  goes at the end of `Open`'s loop. `l.end`, `l.seq`, `l.last` and `l.hdr`
  say where the log ends. A batch the check writes again and marks goes to
  the Target too, before the transaction runs.
- **F4, damage:** the look past the end of the log goes where `readOn`
  stops, and at the end of `Open`. `readOn` takes a marked batch that fails
  its checksum for the end of the log; F4 reads it again under the lock.
  Two cases in `TestReadingStopsAtTheEndOfTheLog` become damage then: "a
  marked batch that fails its checksum" and "a marker naming the batch
  before".
- **F5, failed commits:** `failed` in `log.go` is the one place. `stuck`
  already keeps a Log's lock until `Close`: `Lock` returns it, `Unlock`
  leaves flock alone, and `Close` clears it. `TestAFailedCommitStopsAppends`
  pins F2's behaviour, which F5 changes.
- **F6, following:** `readOn` is the reading on. F6 adds the follower's
  order, head, marker, then the rest, and the stat before each read. The
  Log's read position belongs to the mutex's holder, and a follower can
  skip reading on while the mutex is held, since nothing can be committed
  then.
- **F7, the file rules:** in `Open`, before its loop. `Open` takes the
  path as given, and a FIFO at the path would block its reads.
- **F8, compaction:** the wait past the deadline goes in `flock`. The
  switch to the compacted file can use `fresh`, `use` and the steps of
  `adopt`.
- **F9, reloading:** `reopen` is the reload, and the garbage collection
  goes between `Reset` and `load`.
- **G1:** `Target.Apply` takes the copy's lock for each batch (BETA.md,
  "Other processes"), and `Reset` swaps in an empty store. `Update` is
  `Lock`, the transaction, `Append` when there are changes, then `Unlock`;
  when `Append` fails, the undo list puts the copy back. `Close` waits for
  the mutex, so the public package's `Close` mustn't run inside `Update`.
- **T1 and T2:** the log uses only the 18 calls of the two interfaces, and
  `fsys.Umask`, which isn't a file call.
- **T3:** `logfile/marker-before-sync` is planted in the real log, and
  T3's toy log can plant its own.
- **CI:** the 10-second test runs in parallel, and is skipped with
  `-short` and while a planted bug is switched on. The planted job grows by
  about 25 seconds.
