## The contract

From BETA.md: SQL writes: `INSERT`, `UPDATE` and `DELETE` through the same
checks as `Put` and `Delete`, with row counts. Done when 0.x's in-scope
write cases pass.

## What's there already

- **The rules,** in `beta/SQL.md`: "Writes", with INSERT, UPDATE, DELETE
  and "For all three", and "Errors and their kinds", whose table makes a
  function's error in a write "invalid".
- **The parser** (Q3) reads INSERT, UPDATE and DELETE into the tree, with
  each field named once and one value for each field in each row.
- **The planner** (Q5), in `beta/internal/query`: `Prepare` and `Run` can
  give a write's records, with the key lookups, the terms worked out once
  and the subqueries worked out once, as SQLite plans a write's WHERE.
  Q5.md's note says how to build the `*Select` for an UPDATE or a DELETE,
  and an INSERT's rows as a Select without a FROM, one for each row.
- **The store's writes** (S1 to S3): a `store.Tx` with `Put` and `Delete`,
  and `Mark` and `RollbackTo`, which `tx.go` keeps for SQL's statements.
  SQL writes go through the store's `Put` (S1.md's note).
- **The corpus** (A4): the write statements marked in, with 0.x's answers,
  and the 18 queries it runs after a write, which `planQuery` in
  `plan_corpus_test.go` can answer once the write is in.

## To settle, and write down in this file

- **The entry point** for a write: a parsed statement, its arguments, the
  statement's Frame and a `store.Tx`, giving the row count, so G4 has one
  call to make, as Q5's `Query` is for a SELECT.
- **INSERT:** each row's values through the same conversions and checks as
  `Put`, a blob for `vec` made a vector first (S1.md's note), and a key
  that's there already refused as 0.x refuses it.
- **UPDATE and DELETE:** the records read whole before the first write, in
  key order (P2.md's and S4.md's notes), the SET values worked out in 0.x's
  order, which shows in which error comes first (Q5.md's note), and what a
  key that changes does.
- **A failed statement** undoes its own changes only, with `Mark` before it
  and `RollbackTo` when it fails, and the transaction carries on (P5.md's
  and S2.md's notes).
- **Errors and their kinds:** a function's error is "invalid" in a write,
  the planner's errors stay "error" (Q1.md's and Q5.md's notes), and the
  refusals of `Put` and `Delete` keep theirs.
- **What's left for G4:** `Exec` and `Query` through the driver and the
  public package, with the row counts.
- **The tests:** 0.x's in-scope write cases from the corpus, then the 18
  queries after them, through the entry point on a real store, giving 0.x's
  answers: the closing test. Beside them, random writes against 0.x through
  `zerox`, in a file built only with cgo.
- **Planted bugs,** such as an UPDATE that writes as it reads, or a failed
  statement that takes the whole transaction back, each with a line in
  `beta/plants.txt`.
