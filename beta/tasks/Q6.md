# Q6: SQL writes

Status: done, 12 October 2026.

## The contract

From BETA.md: SQL writes: `INSERT`, `UPDATE` and `DELETE` through the same
checks as `Put` and `Delete`, with row counts. Done when 0.x's in-scope
write cases pass.

## What was built

All of it is in `beta/internal/query`, in files of its own, and it uses the
store's API as it is. These files that were there changed, each a little:

- `check.go`: the parser no longer refuses an INSERT without `key`. 0.x
  works out a row's values before the key's NOT NULL check, so
  `INSERT INTO docs (title) VALUES (vector('x'))` is invalid in 0.x, from
  vector(), where the parser gave "error". Exec now gives "NOT NULL
  constraint failed" as the first row goes in. `parse_test.go` lost its case
  for the old refusal, and `corpus_test.go`'s `refusedHere` lost
  statement-0205, which parses now and fails in Exec, as the closing test
  shows.
- `doc.go`: the package comment has a clause on `Exec`.
- `beta/plants.txt`: twelve new lines.

The new files:

- **`write.go`:**
  - `Exec(tx, s, f)` runs an INSERT, UPDATE or DELETE inside a `store.Tx`,
    with `f.Args` for the `?` marks and `f.Now` as the statement's moment,
    and gives the count of changed rows. It marks the transaction before the
    statement and rolls back to the mark when the statement fails, so the
    transaction carries on.
  - INSERT: each row of values is a SELECT without a FROM, all of them
    prepared before any runs, then all run, then each row checked and put.
  - UPDATE: its WHERE is the plan of `SELECT key FROM t WHERE ...`, which
    gets the planner's key lookups, terms worked out once and subqueries
    worked out once. Its SET values are the result columns of
    `SELECT ... FROM t`, a plan prepared and never run, whose compiled
    columns work out a record's values over a row filled from the record.
  - DELETE: the same plan of its WHERE, then the store's `Delete` for each
    key.
  - `before`: the transaction as an UPDATE's second pass reads it, with the
    records the UPDATE matched as they were.
- **Twelve planted bugs,** in `plant_write_on.go`, whose `init` switches
  them on, so the other plant files stay as they were:
  `query/statement-takes-all-back`, `query/func-error-kept`,
  `query/insert-values-as-written`, `query/insert-row-by-row`,
  `query/taken-before-statement`, `query/key-of-any-table`,
  `query/set-in-written-order`, `query/update-in-one-pass`,
  `query/update-writes-as-it-reads`, `query/key-change-let-through`,
  `query/count-every-record` and `query/delete-as-it-reads`.
- **Tests:**
  - `write_corpus_test.go`: the closing test.
  - `write_test.go`: `writeCases`, 85 writes on the fixture, each with its
    answer and the rows of a query after it; a failed statement in the
    middle of a transaction, its change list included; writes over 600
    records put in a random order, whose changes go in key order; the
    messages 0.x's tests look for; a vector's bits through a write; and the
    statements of the named test PlainSQLFollowsTheRules through `Exec`.
  - `write_sqlite_test.go`, built with cgo only: `writeCases` against 0.x,
    and random writes against 0.x.

## The result

- **0.x's in-scope write cases pass.** `TestTheCorpusWritesGive0xsAnswers`
  runs the corpus's 36 writes through `Exec`, each in a transaction on the
  fixture in a real store, rolled back after. The 29 marked in give 0.x's
  answers: 20 counts and 9 errors of the same kinds. The 18 queries the
  corpus runs after a write give 0.x's rows, through `Query` inside the same
  transaction. The 7 marked out are refused by the parser. Once every
  transaction is rolled back the store holds the fixture as it was. No case
  marked in is left out.
- **The write cases agree with 0.x:** 85, of which 82 give 0.x's answers
  and rows after, and 3 differ on purpose, as under "Decisions settled".
- **Random writes agree with 0.x.** `TestRandomWritesAs0x` runs 4 runs of
  400 random INSERTs, UPDATEs and DELETEs over three tables, with keys that
  are new, taken, another table's or broken, vectors good and bad, values
  that fail on some rows, and WHEREs that fail on some rows, each write
  followed by four reads, inside one transaction in each engine. The
  counts, the error kinds and the rows are the same. With `-short` it runs
  2 runs of 150. Eighty more seeds, run once by hand, gave 32,000 writes
  more with no difference.
- **The planted bugs are caught,** all twelve, one at a time with
  `-failfast` as `scripts/planted.sh` runs them, by the tests with cgo and
  by those without it. With the tag and no bug switched on, the package's
  tests pass.
- `sh scripts/check-beta.sh`, `go vet ./...`, `go test -short ./...`,
  `go test -race -short` on the package, and the package's tests with
  `CGO_ENABLED=0` pass. The write tests take about 1.3 seconds with
  `-short` and 5 without, with cgo, and a tenth of a second without cgo.

## Decisions settled

**The entry point** (`write.go`):

- `Exec(tx *store.Tx, s Statement, f *Frame) (int64, error)`. `f.Args` fill
  the `?` marks, exactly one for each, checked as `Run` checks them, and
  `f.Now` is the statement's moment.
- The count: the rows an INSERT added; the records an UPDATE's WHERE
  matched, whether a value changed or not, `SET key = key` included; the
  records a DELETE deleted.
- A statement that fails goes back to the mark `Exec` takes before it, with
  `RollbackTo`, and the transaction carries on. On a transaction that has
  ended, `Exec` gives the store's error, which wraps `errs.ErrClosed`.
- A SELECT is an `*Error`: it goes through `Query`.

**The order of work,** as 0.x's SQLite does it, each step checked against
0.x. 0.x's record tables have triggers after INSERT on the key and on vec,
before UPDATE OF key, after UPDATE OF vec and after DELETE, and they decide
SQLite's plan:

1. Every name is found and every expression compiled first: the table, the
   fields an INSERT or a SET names, and the names in the WHERE and the
   values. So those errors come before any value is worked out.
2. An INSERT works out every row's values before the first row goes in, as
   SQLite fills a temporary table first for a table with triggers. One
   row's values are worked out in the order of the table's columns, key
   first, as `sqlite3Insert` codes a single row of VALUES; several rows'
   are worked out row by row, each in the order written.
3. Then each row in turn: a NULL key, an INSERT without `key` included, is
   "NOT NULL constraint failed"; a key the table has, one put earlier in
   the statement included, is "UNIQUE constraint failed"; then a key that
   doesn't fit the table, a `vec` the table doesn't take, and what else
   `Put` refuses. Another table's key is no UNIQUE failure, since SQLite's
   index is the table's own, so it fails the key's check.
4. An UPDATE's WHERE goes through the planner as a SELECT's does, over the
   records in key order. Its SET values are worked out in the order of the
   table's columns, key first, as `sqlite3Update` codes them. When the SET
   names neither `key` nor `vec` and the WHERE holds no subquery once
   `x AND 0` is folded, SQLite takes one pass, and each record's values are
   worked out as the WHERE passes it. Otherwise it takes two: the WHERE goes
   over every record, then each record in turn has its values worked out,
   its key checked and its changes put, before the next record's values.
5. Then each record: a key set to a value other than the one it has,
   exactly, which is text with the same bytes, is "a key never changes",
   once all the record's values are worked out; then a `vec` the table
   doesn't take; then what else `Put` refuses. A SET that names `key` alone
   puts nothing.
6. A DELETE's WHERE goes over every record, then the records are deleted in
   key order, as SQLite takes two passes over a table with a trigger on
   DELETE. So `DELETE FROM docs WHERE walk('docs:2', 1) <> '[]'` deletes
   every doc in both.

**Values:**

- `vec` takes NULL, bytes made a vector with `value.VectorBits` when they're
  whole float32 values, or a record's vector, from `vec` or the one-record
  subquery. Each is checked with `rules.Vector`, and against the table's
  size as it is at that row, which an earlier row of the statement may have
  set. Anything else, text holding a JSON array included, is refused with
  0.x's message.
- A record's vector going into any other field goes in as bytes, as SQL
  reads it.
- A key is text that starts with the table's name and a colon, as
  `rules.TableOf` takes it.

**Errors and their kinds:**

- distance(), vector() and walk() refusing their arguments, a `*FuncError`
  anywhere in a write, give `fmt.Errorf("%w: %s", errs.ErrInvalid, msg)`,
  which is 0.x's text.
- The three refusals 0.x's triggers raise keep their words after
  "hypercrux: invalid: ".
- NOT NULL and UNIQUE are `*Error`, of kind "error", with SQLite's
  messages. The planner's and the evaluator's `*Error` stay "error", and
  `Put`'s refusals come back as they are.

**The data as it was before:** a statement reads the data as it was before
it changed anything, as SQL.md says, and in its second pass an UPDATE's
subqueries read the records it matched through `before`, as they were.
0.x's SQLite reads the records an UPDATE has changed already, in either
pass, so a one-record subquery that no record reaches until then gives the
changed value: `UPDATE docs SET n = coalesce(n * 2, (SELECT n FROM docs
WHERE key = 'docs:1'))` gives docs:4, whose n is NULL, 3 in the Beta and 6
in 0.x. Two write cases pin it, and the random writes keep clear of it.

**A plan of 0.x's the Beta doesn't follow:** an OR whose every branch names
records by the key, such as `key = 'docs:1' OR key > 'docs:2' AND ...`, can
make SQLite read the key's index once for each branch, and then its UPDATE
takes two passes where the Beta takes one. It shows only in which of a
WHERE's error and a SET's comes first. A write case pins it, and the random
writes keep clear of it.

**Where SQL.md is silent or unclear,** settled as 0.x's SQLite behaves and
checked against 0.x. The wording for SQL.md:

- "INSERT", in place of "The list of fields must name `key`, and may name
  any of the table's fields, each once.": "The list of fields may name
  `key` and any of the table's fields, each once. An INSERT without `key`
  fails on its first row, "NOT NULL constraint failed", once every row's
  values are worked out."
- "UPDATE", after "`key` may only be set to the value it has, exactly.":
  "That's text with the same bytes, so NULL, bytes or a number changes it.
  A SET that names `key` alone changes nothing, and counts the records it
  matched."
- "For all three", a new bullet after the one on `vec`: "A record's vector
  written into any other field goes in as bytes, as SQL reads it."
- "For all three", a new bullet after "A statement is all or nothing.": "A
  write's errors come in 0.x's order. An INSERT works out every row's values
  before it puts the first row: one row's in the order of the table's
  fields, key first, and several rows' row by row, each as written. Then
  each row in turn: a NULL key, then a key the table has, one put earlier
  in the statement included, then a key that doesn't fit the table, then a
  `vec` the table doesn't take, then the other values `Put` refuses. An
  UPDATE's SET values are worked out in the order of the table's fields,
  key first. When the SET names neither `key` nor `vec` and the WHERE holds
  no subquery, each record's values are worked out as the WHERE passes it.
  Otherwise the WHERE goes over every record first, and then each record in
  turn has its values worked out, its key checked, its `vec` checked and
  its changes put, before the next. A DELETE's WHERE goes over every record
  before the first is deleted."
- "What gets worked out", at the end of the bullet on WHERE: "0.x's SQLite
  can also take two passes over an UPDATE where the Beta takes one, for a
  WHERE it answers from the key's index more than once, such as
  `key = 'a' OR key > 'b'`, so a test shouldn't count on which of a WHERE's
  error and a SET's comes first there."
- "Where the Beta differs from 0.x", a new bullet: "A one-record subquery in
  an UPDATE's SET that no record reaches until the UPDATE has changed a
  record reads that record as it was before the statement. 0.x reads the
  change, so `UPDATE docs SET n = coalesce(n * 2, (SELECT n FROM docs WHERE
  key = 'docs:1'))` gives docs:4, whose n is NULL, the n docs:1 had in the
  Beta, and the n the UPDATE gave docs:1 in 0.x."

## Notes for later tasks

- **G4, slice 3:**
  - A write is one call: `query.Exec(tx, st, &query.Frame{Args: args, Now:
    now})`, with `tx` the Update's `store.Tx`, `args` made with `query.Arg`,
    exactly one for each `?` mark, and `now` read once for the statement. It
    gives the count for `RowsAffected`. `LastInsertId` returns an error.
  - Outside `Update`, a write is a transaction of its own: an Update around
    `Exec`, which commits when `Exec` succeeds. When it fails, `Exec` has
    taken its changes back, and the Update rolls back nothing more. Inside
    `Update`, a failed statement leaves the transaction as it was before
    it, and the Update goes on.
  - `Query` and `QueryRow` of a write run `Exec`, and give no columns and
    no rows. The public `Exec` of a SELECT runs it through `Query` and drops
    its rows, since `query.Exec` refuses a SELECT.
  - Kinds: an error from `Exec` that wraps `errs.ErrInvalid` is "invalid".
    Through `SQL()` every error is of kind "error", and a broken rule reads
    as 0.x's does there, "hypercrux: keys in table docs ..." without
    "invalid: ", so the driver behind `SQL()` gives a plain error with
    "hypercrux: invalid: " made "hypercrux: " for those.
  - On a `store.Tx` that has ended, `Exec` gives `errs.ErrClosed`, and
    `Query` gives "no such table", since the Tx finds no table. The public
    Tx can check for itself.
  - The named test PlainSQLFollowsTheRules passes through `Exec`, as
    `TestPlainSQLFollowsTheRulesThroughExec` shows, and the command's SQL
    section looks for "keys in table docs are text that starts with docs:",
    which `Exec` gives word for word after "hypercrux: invalid: ".
  - Once SQL runs through the driver, the corpus's writes can go through
    `sqlcorpus.Replay` on the engine, as A4.md's note asks.
- **R1, long runs:** `TestRandomWritesAs0x` takes its seeds from the run's
