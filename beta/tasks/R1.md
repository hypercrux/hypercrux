# R1: Long runs

Status: next, alone in its round, as the owner chose on 13 October 2026.
Planned at 3 hours. It needs I1, G5, G7 and Q6, which are done.

## The contract

From BETA.md: long runs: hours of fuzzing and crash runs on both
architectures, every planted bug tried. Done when every job runs green for
its full length, and every planted bug is caught.

## What's there already

- **The knobs for a long run:** `HYPERCRUX_CRASH_SEEDS` for the crash
  suites, `HYPERCRUX_PROCS_TIME` for the many-process harness,
  `HYPERCRUX_DIFF_SEQUENCES` for the differential harness, the fuzz targets
  `scripts/fuzz.sh` runs, the planted bugs `scripts/planted.sh` runs, 233 of
  them, and the knobs the records name under R1.
- **CI:** `.github/workflows/beta.yml` runs the rules, the tests on arm64
  with the race detector, every fuzz target for 30 seconds and every
  planted bug, on each push to main. Since V2, `scripts/fuzz.sh` stops the
  fuzzer minimising a new input after 2 seconds: `FuzzDecodeBatch` had
  spent half of its 30 seconds that way (V2.md's note under R1). The
  planted job took about 33 minutes after G5, and 18 after V2 with ten bugs
  more, so its time varies with the runner. `test.yml` runs every test on
  ubuntu and macOS.
- **The runners:** `ubuntu-latest` for amd64 and `ubuntu-24.04-arm` for
  arm64, each job up to six hours.

## To settle, and write down in this file

- **The long runs:** a workflow of their own that runs by hand, and on a
  schedule if that suits, with jobs on both architectures for hours of
  fuzzing, crash seeds, the many-process harness, the differential harness
  and every planted bug. How long each job runs, and what it keeps when one
  fails, such as a fuzz input or a seed.
- **The push workflow's planted job,** 18 to 33 minutes in its last runs:
  split across jobs run side by side, or a quick part on each push with the
  rest in the long runs, as long as every planted bug is still tried on
  both architectures.
- **The first full run:** a workflow has to be on main before it can run,
  so the coordinator starts it once the round has merged, and writes what
  it finds into this file. A test that fails only because a run is long or
  the machine is busy is fixed in the test; a real bug is fixed with a
  test, and named in the record.
