# R1: Long runs

Status: done, 14 October 2026. The first full run, on 13 October, passed
every job but the two `fuzz-2` jobs, whose `FuzzParse` found a bug, fixed
on 14 October. The second run, of `fuzz-2`, `crash`, `diff` and `planted`
at their new lengths, passed every job on both architectures.

## The contract

From BETA.md: long runs: hours of fuzzing and crash runs on both
architectures, every planted bug tried. Done when every job runs green for
its full length, and every planted bug is caught.

A workflow has to be on main before it can run, so the closing test is the
first full run, which the coordinator starts once this round has merged,
and writes into this file. This round built what it needs: the workflow,
the scripts behind it, each job's command run here at a short length and
green, and the notes below on starting a run and reading it. The push
workflow's planted job runs in shards side by side now, so a push tries
every planted bug in a fraction of the time.

## What was built

- **`.github/workflows/long.yml`**, the workflow `long`, started by hand
  with `workflow_dispatch`, from the Actions tab or through the REST API.
  It has no schedule. One job runs as a matrix of twelve, the same six
  jobs on `ubuntu-latest` (amd64) and on `ubuntu-24.04-arm` (arm64), all
  side by side, with `fail-fast` off, so every job runs its full length
  whatever another finds:
  - `fuzz-1` and `fuzz-2`: half the fuzz targets each, `fuzz_time` a
    target, through `scripts/fuzz.sh`'s shards. With the six targets there
    are, `fuzz-1` runs `FuzzDecodeBatch`, `FuzzDecodeMarker` and 0.x's
    `FuzzReader`, and `fuzz-2` runs `FuzzDecodeHeader`, `FuzzParse` and
    0.x's `FuzzLine`.
  - `crash`: the tests of `beta/internal/crash`, `beta/internal/logfile`
    and `beta/hypercrux` with `HYPERCRUX_CRASH_SEEDS` set to
    `crash_seeds`, so every crash point runs from that many seeds, and the
    packages' other tests at full length, with `HYPERCRUX_COMPACT_RECORDS`
    at 100,000 for F8's measure of a compaction.
  - `procs`: the tests of `beta/internal/procs` with `HYPERCRUX_PROCS_TIME`
    set to `procs_time`. Five runs take their time from it: the toy log's,
    the real log's (T4), the followers' (F6), the followers' through
    reloads (F9) and the public package's (G5). The 200 kills through the
    package keep their own length, at least 10 seconds and until 200
    writers have died mid-commit, as in every full run.
  - `diff`: `TestZeroxAgainstTheBeta` with `HYPERCRUX_DIFF_SEQUENCES` set
    to `diff_sequences`.
  - `planted`: every planted bug.

  The inputs, with their defaults: `fuzz_time` 70m, `crash_seeds` 3840,
  `procs_time` 42m, `diff_sequences` 800000, `minutes` 270, and `only`,
  empty. `minutes` is each job's limit. The run step's limit is 10 minutes
  inside it, and go test's `-timeout` 20 minutes inside it, so a test that
  hangs prints its goroutines, and a run that overruns fails and keeps its
  files, before the job itself is stopped. `only` names the jobs to run,
  such as `crash,procs`, and the others pass within a minute without
  running. A failing job uploads the artifact `long-<job>-<arch>`, such as
  `long-crash-arm64`. Its `concurrency` group lets one long run go at a
  time, and a second waits for it.
- **`scripts/long.sh`**, each long job's command, which runs here as CI
  runs it, at any length: `sh scripts/long.sh fuzz 70m 1/2`, `crash 3840`,
  `procs 42m`, `diff 800000` or `planted`, with a shard for the last too.
  The output goes to the terminal and to `output.txt` in the folder
  `LONG_OUT` names, or a new temporary one, and the tests' temporary files
  go in its `tmp` folder, by `TMPDIR`, as a real path, since the log's
  tests compare their files' real paths (F7.md). When a job fails, the
  folder keeps what replays it: `output.txt`; `found/`, the files the tests
  wrote into the tree, such as a failing fuzz input in its package's
  `testdata/fuzz` or a sequence the differential harness saved in
  `beta/difftest/testdata`, with their paths; and `tmp/`, what a test left
  there, such as the database of one that go test's timeout stopped before
  its cleanup. Under GitHub Actions, the lines that say what failed become
  an error annotation, or the output's last 20 lines when none does, as
  when a build fails, and a saved sequence's JSON another when it's under
  4 KB. What the job did becomes a notice: each package's result and time,
  each fuzz target's last count of executions, and the compaction's rate.
  `LONG_TIMEOUT` sets go test's `-timeout` for the crash, procs and diff
  suites.
- **`scripts/fuzz.sh`** takes a shard after the time: `sh scripts/fuzz.sh
  70m 2/3` runs targets 2, 5, 8 and so on, in the order go list and the
  test files give them. A target that fails no longer stops the ones after
  it: the script runs them all, then fails, naming the targets that failed.
  Under GitHub Actions each failure is an error annotation, with the
  failing input itself, and the command that replays it, when the input is
  4 KB or less, or with the build's error when the target doesn't build.
- **`scripts/planted.sh`** takes a shard: `sh scripts/planted.sh 2/5` runs
  the bugs on lines 2, 7, 12 and so on of the list, after the baseline for
  the packages they name. Every bug's line says how long its run took, and
  the count says how long the shard took. A run that fails without a line
  starting with FAIL, which go test prints whenever a test fails, never got
  to its tests, and is "BROKEN", which fails the shard: before, it counted
  as caught. Under GitHub Actions a missed or broken bug is an error
  annotation, and so is a baseline that fails, naming the tests that
  failed, and the count is a notice.
- **`.github/workflows/beta.yml`**: the `planted` job is a matrix of five
  shards, `1/5` to `5/5`, side by side on `ubuntu-latest`, with
  `fail-fast` off, so one shard's miss doesn't stop the others. The fuzz
  job's comment names the long workflow.
- **`beta/internal/crash`**: `HYPERCRUX_CRASH_SEEDS` raises a point's
  seeds and never lowers them (`run.go`, and `Options.Seeds`' comment in
  `crash.go`). It used to take the place of a test's own seeds, so a value
  below them weakened that test, and failed one that needs its seeds:
  with `HYPERCRUX_CRASH_SEEDS=8`, `TestTheDriverCatchesMarkerBeforeSync`
  failed, since it asks for 256 seeds and a cut catches its bug in a few
  per cent of them. T3.md's note under R1 says the knob raises the seeds,
  which is what it does now. `TestTheEnvironmentSetsSeedsAndReplays` checks
  that a test asking for more keeps them, and the planted bug
  `crash/seeds-overridden` puts the old behaviour back, which that test
  catches. `beta/plants.txt` has its line, so there are 234 planted bugs.
- **`beta/internal/procs`**: the two many-process runs that move backups
  into place, F9's `TestFollowersSeeEveryCommitThroughReloads` and G5's
  `TestManyProcessesThroughThePackage`, would run out of memory in a long
  run, so they failed only because a run is long. Each restore begins an
  era, and the history keeps every era's commits, and the readers' first
  sight of each, until the run ends, so its memory grows with the eras
  times the file's length. At their gaps of 50 to 250 milliseconds, the
  first held 1 GB after 4 minutes here, 327 eras of up to 9,905 commits,
  and a run of 42 minutes would need several times a runner's 16 GB. Now
  `restoresFor`, in `reload_test.go`, stretches the gaps of a run longer
  than 30 seconds in step with its time, a step for each 15 seconds, so a
  long run moves about as many backups into place as a run of 15 seconds
  does, each into a longer file: gaps of 8.4 to 42 seconds for a run of 42
  minutes. A run of 30 seconds or less is as it was.
  `TestLongRunsSpaceTheirRestores` checks the gaps.

  nothing. A column printed alone now goes in parentheses when its text is
  all such white space (`columnText`, in `print.go`): the parser drops

  since SQLite reads a quoted name that isn't a column as text.

## Decisions settled

**Six jobs on each architecture, side by side.** The contract's five kinds
of run, with the fuzz targets in two halves, so each target runs for over
an hour in about three and a half hours. GitHub's free plan runs 20 jobs
at once. A push during a long run needs nine: its eight beta jobs and the
test workflow's Linux job. So one of them waits, until the long planted
jobs end.

**Lengths,** at the defaults:

| Job | Its length | Expected on the runners |
|---|---|---|
| `fuzz-1`, `fuzz-2` | 3 targets of 70 minutes | about 3 hours 35 minutes |
| `procs` | 5 runs of 42 minutes | about 3 hours 35 minutes |
| `crash` | 3,840 seeds a point, raised from 1,280 after the first run | 1 h 42 min on amd64 and 2 h 21 min on arm64 in the second run |
| `diff` | 800,000 sequences, raised from 320,000 after the first run | 2 h 51 min on amd64 and 2 h 12 min on arm64 in the second run |
| `planted` | every bug, 235 since the first run | 16.5 to 24 minutes there |

The fuzz and procs jobs run for the time they're given. The crash and diff
jobs run a count, which takes as long as the runner needs, so their counts
take about 2 hours here: on a runner whose core is 0.6 times as fast, they
end within go test's limit of 250 minutes. The runners' cores haven't been
timed yet, and the first run's notices give each package's time, from
which the counts can grow. The whole run takes about three and a half
hours, within the job limit of 4.5 hours, `minutes` 270.

**No schedule.** A scheduled run that fails mails whoever last changed the
schedule, and the owner takes no part in CI. A long run starts when the
coordinator starts one, for this task, and for R4's last overnight run.

**Annotations carry what a failure needs.** A Claude cloud session can't
read a job's log or download its artifact: the egress proxy refuses
`results-receiver.actions.githubusercontent.com` and the blob storage the
artifacts sit in, with 403, as tried in this round. The REST API's check
runs show annotations, though, so the scripts print the lines that matter
as annotations: each failing test's lines, crash points, seeds, missed
bugs, and the failing fuzz input or saved sequence itself when it's 4 KB
or less. The artifact keeps all of it, and the whole output, for the owner
or anyone with a browser.

**What a failing job keeps:** the output, which names every crash point,
many-process seed and missed bug; the files the tests wrote into the tree,
which are failing fuzz inputs and saved sequences; and whatever a test
left in its temporary folder. No suite leaves a database behind when it
fails: the crash driver's disks live in memory, and a point replays its
file exactly, while the harness and the differential harness remove their
folders as their tests end. A test stopped by go test's timeout doesn't
get to, so `tmp/` keeps its files, as the check above shows.

**The crash knob raises seeds and never lowers them.** Every test that
uses the driver gets at least its own seeds, whatever a run sets, so the
short check `crash 1` runs the crash tests as an ordinary full run does,
and a long run can only add seeds. The seeds a long run adds are the next
ones after a test's own, from the same starting seed, so a long run tries
the same seeds each time it runs on the same code. A knob for the starting
seed would give each run new ones; it's left for later.

**The records' other knobs.** `HYPERCRUX_COMPACT_RECORDS` is 100,000 in
the crash job, so `TestTheRateACompactionWritesAt` compacts 160 MB once on
each architecture, and the notice gives its rate. The other sizes the
records name for R1 are numbers at the top of their tests, with no
variable a run can set: T1's and T2's fault-layer runs, F5's cut back and
stuck batch, F9's commits through reloads, I1's 200 kills, G7's random
steps, Q6's random writes and G2's three seeds. All but I1's kills use
fixed seeds, so running them again finds nothing new. The kills draw a
seed of their own each run, and the procs job's five long runs kill
thousands of processes besides. Those in the crash and procs jobs'
packages run there at their full sizes, and the rest run in full on every
push, as before. Giving each a variable is a change to those tests, for a
later task if the owner wants it.

**Long runs space their restores.** The two runs that move backups into
place would run out of memory in a long run, as above. Stretching their
gaps in the two tests is the smallest way to keep them within a runner's
memory: a run of up to 30 seconds is as it was, so every push runs them as
before, and the history and its checks are untouched. A long run moves
fewer backups into place, about 40 in 4 minutes here and about as many in
42, each into a longer file. Making the history keep less is the larger
fix, and it's in the notes for R2.

**The differential harness runs 0.x against the Beta alone.** 0.x against
itself is A3's check of the harness, which every push runs. The script
checks the test still exists before it runs, since `-run` with a name that
matches nothing passes.

**Planted bugs in five shards of every fifth bug.** `beta/plants.txt` lists
bugs in runs by task, so taking every fifth line gives each shard a share
of every package's bugs: the shards' bug runs took 359 to 423 seconds
here, and nothing needs keeping up when bugs are added. Each shard runs
its own baseline, the tests of its packages with the tag and no bug, so
its "caught" stands on its own. The baseline takes 2 to 3 minutes here,
mostly `beta/hypercrux`'s full tests. Each shard took 8 to 9.5 minutes
here, on two cores, where the whole job took 36 minutes, and the runners
took 18 to 33 for the whole job, so five shards should take about 5 to 10
minutes there, a little more than the arm64 and fuzz jobs. A push uses
eight jobs at once, and more shards would each pay the baseline again. The
push tries every bug on amd64, and the long run tries every bug on both
architectures, so arm64 gets them whenever a long run goes.

**A run's limits sit inside each other:** go test's `-timeout` 20 minutes
inside the job's limit, and the run step's 10 minutes inside it. A test
that hangs gives a goroutine dump at go test's limit. A run that overruns
fails at the step's, and its artifact goes up before the job's own limit
stops it. GitHub's expressions can't subtract, so a small step works out
the step's limit.

**Times in the planted output.** Each bug's line says how long it took, so
a slow bug, or a shard grown unbalanced, shows in the output.

**A planted run that never starts is no catch.** go test prints a line
starting with FAIL whenever a test fails, a build fails or a test binary
dies, so a run that fails without one never reached its tests. It's
"BROKEN", and fails the shard. Before, any failed run counted as caught.


    jobs. The planted jobs end within about 40 minutes, and the crash and

  - **Reading it:**

    ```sh
    # the run
    gh api "repos/hypercrux/hypercrux/actions/workflows/long.yml/runs?per_page=1" \
      --jq '.workflow_runs[0] | "\(.id) \(.status) \(.conclusion) \(.head_sha[0:7])"'
    # its twelve jobs, with their times and ids
    gh api "repos/hypercrux/hypercrux/actions/runs/<run id>/jobs?per_page=20" \
      --jq '.jobs[] | "\(.name)\t\(.conclusion)\t\(.started_at)\t\(.completed_at)\t\(.id)"'
    # a job's annotations
    gh api repos/hypercrux/hypercrux/check-runs/<job id>/annotations \
      --jq '.[] | "\(.annotation_level) \(.title): \(.message)"'
    ```

    The run is done when all twelve jobs are green, each `long <job>`
    notice gives what the job ran and how long it took, and both planted
    jobs' notices say "235 of 235 planted bugs caught". A job's log and its
    artifact can't be fetched from a cloud session, so the annotations are
    the record. Write each job's time and its notice's figures into "The
    result", and the status line becomes "done".
  - **When a job fails:** its error annotations say what failed, and how
    to replay it here:
    - a crash point: `HYPERCRUX_CRASH_POINT='<point>' go test -count=1
      -run '^<Test>$/^<subtest>$' ./<package>`, with the subtest from the
      "--- FAIL" lines, where spaces become underscores, or `-run
      '^<Test>$'` for a test without subtests. The variable replays every
      driver run in the process, so the run has to name the one subtest.
    - a many-process run: `HYPERCRUX_PROCS_SEED=<seed>
      HYPERCRUX_PROCS_TIME=<the run's time> go test -count=1 -run
      '^<Test>$' ./beta/internal/procs`. The seed repeats the random
      choices, and the processes' timing won't replay, so it may take a few
      runs.
    - a fuzz input: write the annotation's text to the file it names and
      run the command it gives. With the fix, the file stays in
      `testdata/fuzz` as a seed.
    - a saved sequence: write its JSON to the file it names in
      `beta/difftest/testdata` and run `go test -count=1 -run
      '^TestSavedSequences$' ./beta/difftest`. It stays there as a test.
    - a missed planted bug: `HYPERCRUX_PLANT=<name> go test -tags
      hypercrux_planted -count=1 <packages>` passes, where it should fail:
      a gap in the tests.
    - a timeout: the annotation names the tests still running. Their
      goroutines are in the artifact's `output.txt`, and their files in its
      `tmp/`, which the owner can download from the run's page.
    - a procs job that ends with "signal: killed" and no problem named: the
      runner ran out of memory, from the many-process history above.
      `restoresFor` should prevent it; if not, run procs alone with a
      shorter `procs_time`, such as 20m, and say so here.

    A test that fails only because a run is long or the runner is busy is
    fixed in the test. A real bug is fixed with a test, a planted bug for
    it goes in `beta/plants.txt`, and both are named in this file. Then
    the failed jobs run again at full length, on the new main, with `only`.
    GitHub's "re-run failed jobs" would run the old commit.
