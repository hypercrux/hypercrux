# L1: 0.x's limit on text and bytes

Status: done, 15 October 2026.

## The contract

From BETA.md: 0.x's limit on text and bytes, which the owner chose after
R2's second part: a text or bytes value of more than 1,000,000,000 bytes is
refused as 0.x refuses it, wherever one comes in. Done when Put, SQL's
writes and arguments and Import refuse a value one byte over the limit with
0.x's error and take one at the limit, a batch holding a longer value is
damage, and the specs say so.

The owner chose it on 14 October 2026, option B of R2.md's part 2, first
question, and put it before R3, so the docs describe the limit as it is. No
byte of the format changes, and the format stays version 1.

## What was built

- **`beta/internal/rules`**, the one place the limit lives:
  - `MaxLength`, 1,000,000,000, SQLite's `SQLITE_MAX_LENGTH`, which 0.x has
    from go-sqlite3.
  - `Length(n)`, which gives SQLite's error for a text or bytes value of n
    bytes past the limit: "string or blob too big", one error value that
    wraps neither `ErrInvalid` nor `ErrNotFound`, so it's of kind "error",
    as 0.x's `sqlite3.Error` is.
  - `plant_off.go` and `plant_on.go`, new to the package, with two planted
    bugs.
- **`beta/internal/store`**, `write.go`:
  - `fits`, which held text and bytes to the u32's 4,294,967,295 bytes with
    `ErrInvalid` in the store's words, is gone. `lengths` holds each text and
    bytes value of a put to `rules.Length`, after the put's other checks:
    the key, the field names, the values, the number of fields and the
    vector's size, as 0.x has them. Every way into a put goes through it,
    in `putFields` and `applyPut`: `Put` and a transaction's `Put`, and
    `Apply`, a transaction's `Apply`, `ApplyBatch` and `LoadBatch`.
  - `keepAll` and `keep` are split in two. `checkAll` and `check` check a
    put's values and copy nothing, and `own` gives each text and bytes value
    a copy of its own once every check has passed. So the store never copies
    a value it refuses, the long one included.
  - Three planted bugs, in `plant_on.go`.
- **`beta/internal/query`**:
  - `values.go`: `maxLength`, where SQL's own values stop, is

  - `args.go`: `Bind`, new, holds a statement's arguments to the limit, as

  - `plan_walk.go` and `plan_scope.go`: `walk()` as a function refuses JSON

  - Three planted bugs, in `plant_limit_on.go`, new.
- **`beta/hypercrux`**:

## The result

**What 0.x does, each way in.** Found from 0.x's code and go-sqlite3's,
and run by hand on 0.x from a scratch module, with values from the page of
zeros. 0.x's text costs it nothing to refuse, so
`TestTheLimitOnTextAndBytesAs0xHasIt` runs those cases on 0.x on every run.
The import, the long statement and the long filter took 0.x 2.9, 2.0 and
3.9 GB, so they were run once, and their answers are pinned on the Beta.

| Way in | 0.x, one byte over | Kind | Where 0.x refuses it | The Beta |
|---|---|---|---|---|
| `Put`, on `DB` and `Tx` | `string or blob too big`, go-sqlite3's `sqlite3.Error` | error | at the bind, after Put's other checks, after it has made the table and the new fields, and after the vector's size | the same, after the same checks, changing nothing |
| INSERT and UPDATE, through `Exec`, `SQL().Exec` and a `Tx` | the same | error | at the bind, before anything runs, so before NOT NULL, UNIQUE and the triggers on key and vec, and even when no record matches | the same, before anything runs |
| An argument of a SELECT, through `Query`, `QueryRow` and `Exec` | the same | error | at the bind, even under `WHERE 0 AND ? IS NULL` | the same |
| An argument of `Nearest`'s filter | the same | error | at the bind, before the terms worked out once, so `0 AND t = ?` refuses too. Without a filter the arguments go unbound, and a table with no vectors gives no hits before the filter | the same |
| `Import` | `line 4 of the export: docs:2: string or blob too big` | error | after the record's conversions and the vector's size, before "there twice". The import is one transaction, so nothing stays | the same |
| A statement's text | `statement too long` | error | before SQLite reads any of it, NUL bytes included, unless the text ends in a NUL | the same |
| `Nearest`'s `where` | `statement too long`, when 0.x's query passes the limit | error | as for a statement. A `where` of NUL bytes that fills 0.x's query exactly is `incomplete input` | the same |
| `walk()`'s JSON text | `string or blob too big`, by SQLite's `sqlite3_result_text` | error | as the statement runs | the same |

0.x's bind takes a value at the limit: `SELECT length(?)` of 1,000,000,000
bytes gives 1000000000, and the Beta gives the same. A statement of
1,000,000,000 bytes is read up to its first NUL on both.

**0.x's limit on a stored record.** 0.x's `Put` of exactly 1,000,000,000
bytes fails, with the same error. SQLite holds every record it stores to
the limit as well, with its key and every field in SQLite's own form, in
`OP_MakeRecord`. For `docs:1` with one text field the record is the text's
bytes and 13 more, so 999,999,987 bytes is the most 0.x's `Put` takes there,
which the run confirmed: 999,999,987 went in and 999,999,988 didn't. A
longer key, more fields, or other values in the record leave less. The
Beta holds each value to the limit, as the contract has it, and takes a
value of exactly 1,000,000,000 bytes. "Decisions settled" has why, and the
question for the owner.

## Decisions settled

**One limit, in `rules`.** The number lives in `rules.MaxLength`, and every
check of a value's length goes through `rules.Length`, apart from SQL's own
values, where concatenation and `replace()` compare their result's length
with `maxLength`, which is `rules.MaxLength`, and `walkJSON` takes it as an
argument. `rules` imports nothing but `errs`, so the store, SQL and the
public package can share it.

**0.x's error, of kind "error".** S3 gave the store's check `ErrInvalid` in
the store's words. 0.x gives go-sqlite3's error, whose text is SQLite's
alone, "string or blob too big", and which wraps neither of 0.x's errors.
The Beta gives that text and that kind everywhere a value is too long:
`Put`, SQL's writes and arguments, `Nearest`'s filter, `walk()` and a
batch's reason for its damage. `Import` puts the line and the key in front,
as 0.x does. A statement too long reads "statement too long", as 0.x's
does. The text doesn't start with "hypercrux: ", so the error isn't one of
`errs`' values, whose test wants that start.

**Last in `Put`'s order.** 0.x makes its checks in Go first, the key, the
names, the values, the table and its new fields, and the vector's size,
and SQLite refuses a value too long only as 0.x binds the put's values. So
the store checks lengths last, and a put that breaks another rule as well
gets that rule's error, of kind "invalid", as in 0.x. The store's checks
copy nothing, so a value too long is never copied, which the tests' memory
shows.

**Arguments at the driver's bind.** 0.x binds once SQLite has prepared the
statement, so its "no such table" and "no such column" come before a value
too long. The Beta's names are found by the planner, after the driver has
bound the arguments, so the Beta gives "string or blob too big" there.
Both are of kind "error", and SQL.md lets messages differ, so the check
stays in one place before anything runs. A `Nearest` filter is planned
first, as in 0.x, so its names come first.

**Statements: SQLite's limit on a statement.** R2 counted a statement's
length among the limits the Beta keeps, and it didn't. A literal can't be
longer than the statement it's in, so with the statement held to 1,000,000,000
bytes no literal passes the limit on values, as in 0.x. The rule is what
SQLite does with the text and the length go-sqlite3 hands it: more than
1,000,000,000 bytes is "statement too long" before any of it is read, NUL
bytes included.
A text whose last byte is a NUL is read up to its first NUL, as SQLite
reads it then, and its bytes up to there count. Past the limit that's
"string or blob too big" in the Beta, where SQLite gives a syntax error
first when it meets one; both are of kind "error". For `Nearest`, 0.x's
query is `SELECT key, vec FROM "table" WHERE vec IS NOT NULL AND (where)`,
52 bytes and the table's name around the filter, and `FilterLength` holds
that to the limit, before the filter is parsed, as 0.x's query reaches
SQLite.

**What SQL makes.** Concatenation and `replace()` stopped at the limit
already, as SQLite's `OP_Concat` and `replaceFunc` do. `walk()` as a
function didn't, and 0.x's does, since SQLite refuses a function's result
past the limit. So `walkJSON` refuses its text past the limit, with an
`*Error` at the call, of kind "error" in a SELECT and in a write alike, as
in 0.x. The subset's other functions give a number, a date's short text,
`vector()`'s 262,144 bytes at most, or text and bytes no longer than an
argument of theirs.

**A batch: damage, at the limit itself.** The number of fields is held to
the format's 65,535 in a batch, so `MaxFields` can rise without a change to
the format. Text and bytes are held to 1,000,000,000 in a batch too, as the
owner chose, so no build from L1 on takes a longer value in. FORMAT.md's u32
stays as it is, and the codec's own checks stay at it. A file holding a
longer value could only come from a build before L1, none of them released,
and builds from L1 on report it as damage.

**Where the Beta can't match 0.x, and why:**

- **0.x's limit on a whole record.** As above: 0.x's SQLite refuses a
  record whose stored form passes 1,000,000,000 bytes, so it takes a little
  less than the limit in a value, and less again in a record with more in
  it. Matching it means working out each record's size in SQLite's own
  form, with every field of the table counted, a NULL as a byte. 0.x's
  table can hold fields the Beta's hasn't got, after a failed `Put`; a
  multi-row INSERT meets the limit on its temporary table, before any row's
  own checks; and an SQL write meets it after NOT NULL and UNIQUE and before
  the triggers on key and vec. So it can't be matched exactly, and the
  contract asks for the limit on a value. The question for the owner is
  below.
- **A failed `Put` inside an `Update` that goes on to commit** leaves the
  Beta's tables as they were, as every failed write does. 0.x keeps the
  table, when the `Put` made it, and the new fields, which it adds before
  SQLite refuses the value. SQL.md lists the same difference for a vector
  of the wrong size, and the wording below widens it.
- **A statement with a name that isn't there and an argument too long:**
  the message differs, as above, and the kind is the same.
- **A statement of 2 GiB or more:** go-sqlite3 hands SQLite the length as a
  C `int`, which wraps there, so 0.x's own answer for such a text is
  go-sqlite3's accident, and can even run part of it. The Beta refuses
  every statement past 1,000,000,000 bytes.
- **The cost of a `[]byte` argument too long:** the Beta's conversion
  copies every `[]byte` argument, as `query.Arg` makes a value of its own,
  so one past the limit is copied before `Bind` refuses it. 0.x's bind
  refuses it without a copy. The answer is the same.
