# L1: 0.x's limit on text and bytes

Status: next, alone in its round. The owner added L1 on 14 October 2026,
after R2's second part, from its first question, and put it before R3, so
the docs describe the limit as it is. Planned at 1 hour, on top of the
plan's 133. It needs S1, S3, G4, G6 and Q6, which are done.

## The contract

From BETA.md: 0.x's limit on text and bytes, which the owner chose after
R2's second part: a text or bytes value of more than 1,000,000,000 bytes is
refused as 0.x refuses it, wherever one comes in. Done when Put, SQL's
writes and arguments and Import refuse a value one byte over the limit with
0.x's error and take one at the limit, a batch holding a longer value is
damage, and the specs say so.

## What's there already

- **The limit today:** the store's `fits`, in
  `beta/internal/store/write.go`, refuses text and bytes of more than
  4,294,967,295 bytes, the most FORMAT.md's u32 can give, with
  `errs.ErrInvalid` in the store's words (S3.md). `keep` calls it for every
  text and bytes value a put writes, so `Put`, SQL's writes and `Import` go
  through it, and so do a follower's `ApplyBatch` and an opening's
  `LoadBatch`. `TestFits`, in `store/changes_test.go`, holds it to its edge
  without a value of that size.
- **0.x's limit:** SQLite's, 1,000,000,000 bytes, which go-sqlite3 builds
  with. A longer value fails at its bind, with SQLite's "string or blob too
  big", in `Put`, in SQL's statements and their arguments, and so in an
  import.
- **SQL's own values:** the Beta's SQL already stops a value it makes at
  1,000,000,000 bytes with "string or blob too big", as SQLite does
  (`maxLength`, in `query/values.go`).
- **The option the owner chose,** in R2.md, part 2's first question, B:
  take 0.x's limit in the store's `fits`, with 0.x's error. FORMAT.md's u32
  stays, so no byte of the format changes, and the format stays version 1
  until the release, as the owner chose after R2's first part.
- **FORMAT.md's "Names and limits"** has room for it: "HyperCrux's own
  limits can be lower: a put can't take a table past 1,999 fields, which is
  0.x's limit."

## To settle, and write down in this file

- **Each way a value comes in:** `Put`, SQL's INSERT and UPDATE, the
  arguments of a statement and of `Nearest`'s filter, `Import`, and a batch
  in the file. Each refuses a value one byte over the limit, with 0.x's
  error and its kind in the differential harness's terms, and takes one at
  the limit.
- **A batch that holds a longer value:** damage, as a batch that breaks the
  state's other rules is (S3), so no build after L1 takes one in.
- **The tests,** on the checks themselves, since a value of a gigabyte
  takes a gigabyte of memory.
- **Planted bugs,** such as the old limit put back, or a way in that skips
  the check, each with a line in `beta/plants.txt`.
- **The wording** for FORMAT.md, SQL.md and EXPORT.md, and for
  `beta/README.md` if it needs any, for the coordinator.
