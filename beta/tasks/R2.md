### Findings

Most serious first.

**1. A batch that counts could make a reader allocate far more than its
length. Fixed.**

- **Where:** `format/batch.go`, `decodeChanges` and the decoder's `block`.
- **Why it matters:** FORMAT.md has a reader check a batch's length
  against the file before it reads or allocates anything for it, and the
  log does. What decoding the batch then allocated had no bound of the
  kind. A vector block's count of vectors was taken as it came: each key
  read added a 32-byte `Vector`, so a block claiming 4,294,967,295 vectors
  over a batch of zeros took 32 bytes for every 2 bytes of the batch, and
  about five times that while the array grew, before the bytes ran out: 89
  MB for a batch of 1 MB. And every batch's arrays grew an append at a
  time, which Go does by about a quarter once they're large, so a batch
  cost about five times its arrays in allocations: 137 MB to decode a batch
  of 4.4 MB holding 100,000 small puts, in 125 ms. Damage whose checksum
  still fits, or a crafted file, could take a process down wherever it
  reads the file.
- **The fix:** `countChanges` walks a batch's syntax once, allocating
  nothing, and `decodeChanges` makes each array the size it counts. When
  the walk finds the syntax broken, the decoder reads as before, to name
  the damage. A vector block whose count can't fit in the bytes left, at
  each key's length and its values at least, is damage before a key is
  read. The batch of 100,000 puts now decodes in 30 ms with 29 MB, a batch
  of 1,000 in 0.31 ms where it took 0.57, and a batch of one put in 0.52 µs
  with one allocation fewer. The crafted block is damage at its first byte.
- **Tests,** in `format/count_test.go`: `TestTheCountsAreTheDecodersOwn`
  holds the counts to what the decoder reads, on 3,000 random batches;
  `TestADecodedBatchsArraysAreMadeOnce` wants 4 allocations at most for a
  batch of 10,001 changes, where growing took 44; `TestAVectorBlocksCountMustFitItsBytes`
  wants the crafted block's damage at its offset, with less than four
  times the batch allocated.
- **Planted bugs,** in `format`'s new `plant_off.go` and `plant_on.go`:
  `format/changes-grown`, which the second test catches, and
  `format/block-count-trusted`, which the third catches, each in about a
  second.
- **What's left:** a change in memory is one struct of 152 bytes for every
  kind (P3), so a batch of the smallest changes, 4-byte drops, still takes
  about 38 times its length in changes. That's bounded, it's the change
  list's design, and compaction's batches stop at 1,024 changes. It stays.

**2. A compaction can put the old data back over a backup moved into place.
Answered, with wording for BETA.md.**

- **Where:** `logfile/compact.go`, `Compact`, between its stat of the path
  and its rename; BETA.md, "Compaction", step 4, and "Rules for the file".
- **Why it matters:** BETA.md says the check keeps a backup moved into
  place meanwhile from ever being replaced. It narrows the window to the
  moment between the stat and the rename, tens of microseconds, and a `mv`
  landing there is replaced by the compacted file of the old data, so the
  restore is undone without an error. F9.md knew of it, and its harness's
  restores take the lock for that reason.
- **Answer:** closing it would take `renameat2` with `RENAME_EXCHANGE` and
  a look at what came out, a new call in `fsys.FS`, which is an interface
  change for every caller in P3's sense, the fault layers among them, and
  the swap itself leaves a moment with the compacted file at the path. The
  code stays, and BETA.md should say what it does: the coordinator's note
  has the words.

**3. A torn sector that reads back as an error leaves the database
unopenable. Answered.**

- **Where:** T1.md's list of the ways the fault layer is kinder than some
  disks; `logfile/read.go`, `readOn`, and `damage.go`, `markerPast`.
- **Why it matters:** a drive can leave a sector its interrupted write tore
  failing its own check, and a read of it fails with EIO until something
  writes it again. In the torn end of the log, that fails every Open and
  every check with the read's error, so nothing cuts the end, and no
  process can open the database until the file is cut back by hand.
- **Answer:** it fails safe, as BETA.md has damage do: nothing is lost or
  cut. Taking an unreadable end for a torn one when no marker past it can
  be read would move FORMAT.md's line between damage and a crash, which is
  the coordinator's to weigh, after the Beta. The other gaps T1.md and
  T2.md list hide nothing in the log. Pages dropped from the cache after a
  failed sync are covered by the writing again that covers pages marked
  clean, since every sync of the database file comes after the last
  marker is written again, or is a commit's, whose failure is cut back
  that way. A 4 KiB page written whole puts the rest of the page on the
  drive as well, which only helps. A failed truncate or name call that
  took effect leaves the log stuck, or checked again, and both are safe.

**4. The rules for the file assume a file system that never shows a file's
old blocks at its end. Answered, with wording for BETA.md.**

- **Where:** BETA.md, "Rules for the file"; FORMAT.md, "Writing".
- **Why it matters:** ext4 mounted with `data=writeback` can commit a
  file's new size before its data, and after a power cut show whatever its
  new blocks held before. A batch cut back after a failed commit leaves
  just such blocks, at the place the next commit writes, under the same
  sequence number. If the power goes before that commit's sync, the old
  batch can read back whole and count, and the check marks it: a commit
  whose error said it wasn't in the file would be in it. ext4's default,
  `data=ordered`, XFS and btrfs never show a file's old blocks.
- **Answer:** nothing in the log can tell those bytes from a batch its
  writer left, so it's a rule for the file, with words in the
  coordinator's note.

**5. F6.md says a kill can't leave half a batch. Answered.**

- **Where:** F6.md's result: "A kill can't leave half a batch, since a
  batch goes in one write".
- **Why it matters:** Linux's write path looks for a fatal signal between
  pages, so SIGKILL can stop a write of more than a page partway, and the
  file keeps the pages already written. The many-process suites' commits
  fit in a page or two, so their kills seldom land in one.
- **Answer:** the log needs nothing, since half a batch fails its checksum
  and the next check cuts it, as `logfile`'s tests and the crash driver's
  cuts show. The record's sentence is wrong, and this one corrects it.

the same way: its next try or Close lets go. No change.

### Questions for the owner

**1. When to compact.** BETA.md's rule compacts at the end of a commit once
the file has grown to twice the size its last compaction left it at, and by
a megabyte at least. A database that only grows is compacted at each
doubling, which G5 measured doubling the batched put, from 14 µs to 26.

- **A, the rule as it stands.** Every process reads it from the file alone,
  and the log past a compacted part is never longer than the part, or a
  megabyte, so opening stays bounded. A database that only grows rewrites
  its data about once more in all, with a pause for writers and a reload in
  every other process at each doubling.
- **B, counting dead bytes, as G5.md suggests.** Each process counts what
  the batches since the last compaction have made dead, a put's old values,
  a deleted record with its links, a dropped table, a removed link, and a
  compaction comes once that's half the file and a megabyte. Every process
  agrees, since every process applies the same batches to the same state.
  It costs a count in both of the store's paths, applying a batch and a
  transaction, BETA.md's rule and tests, about two hours. A database that
  only grows is never compacted, so its log of commits grows without limit:
  at 2.6 µs a commit, a million small commits take about 2.6 seconds to
  open.
- **C, B with a limit on the commits past the compacted part,** such as
  100,000, about a quarter of a second to open here, which every process
  reads from the sequence numbers. A database taking commits of 1,000
  records reaches it at 100 million records, so the batched put loses the
  doubling, and opening stays bounded. It costs B's work and a number to
  choose.
- **Recommendation: C,** as a small task of its own before R4 records the
  benchmarks. Until then A is safe, and costs time alone.
- **The owner's answer,** on 14 October 2026: C, as task C1, which runs
  before part 2, so part 2 reviews its code.

**2. The format version with vector blocks.** A build from before V2 reads a
vector block as a change of a kind it doesn't know, which is damage, so it
refuses a compacted file holding vectors and calls it damaged, and reads
every other file as before. FORMAT.md's opening says so.

- **A, keep version 1.** No build misreads a file. The cost is the word
  "damaged" from builds that were never released.
- **B, version 2 now.** A build from before V2 refuses every newer file as
  a newer format, and this build refuses every file such a build wrote,
  which are test files alone. It costs FORMAT.md, the headers of every
  fixture in `format/testdata` and `logfile/testdata/damaged`, and the
  tests that build a header by hand, about an hour, for a clearer word to
  builds nobody has.
- **C, version 2 only in a compacted file holding a vector block, with
  both versions read.** Older builds refuse exactly the files they can't
  read, with the right error. It costs two versions in the reader and the
  writer, and a rule in FORMAT.md tying the version to what a file holds.
- **Recommendation: A.** The version starts to matter at R4, when a build
  goes out: from then on every change to the format raises it, and the
  released format is version 1.
- **The owner's answer,** on 14 October 2026: A, version 1 until the
  release. BETA.md's "Decisions" says so.

### Findings

Most serious first.

**1. Export's writer can hang if it calls the database. Answered, in
Export's comment.**

- **Where:** `hypercrux/export.go`, `Export`, which writes to `w` inside one
  read of the copy (`readStore`, in `glue.go`).
- **Why it matters:** the read holds the gate shared, and the copy's read
  lock, while `w` runs. A `w` that calls the database, a `Get` for each line
  say, takes both again inside the export. Go's locks hold a new reader
  back while a writer waits, so once an `Update` in another goroutine
  reaches its first change and waits for the export's read to end, or a
  reload waits for the gate, the read inside `w` waits for it, it waits for
  the export, and the export waits for `w`. None of them ends. 0.x's
  export reads on a connection of its own while writers carry on, so the
  same `w` works there. `Update`'s comment says the like of a goroutine
  that its function waits for, and Export's said nothing.
- **Answer:** the export has to hold one point in the log while `w` runs,
  so the read stays, and Export's comment now says that `w` mustn't call
  the database, and why. It's the one place where a caller's code runs
  inside a read: the driver reads every row of a statement before its read
  ends, and `Get`, `Scan`, `Neighbours`, `Walk` and `Nearest` hand back
  what they read. A check by goroutine, as for `ErrInsideUpdate`, would
  catch a `w` that calls on its own goroutine and miss one that hands the
  call to another, the case `Update` leaves to its comment too.

**2. The filtered search and the walks miss their targets. Answered,
measured.**

- **Where:** BETA.md's "Targets", against the recorded run after C1: the
  search of 100,000 records with 384-value vectors, a tenth through a
  filter, 16.3 ms against 12; a walk one link out, 3.65 µs against 3; and
  three links out, 56.4 µs against 40. Here they took 13.8 to 16.3 ms,
  3.28 to 3.67 µs and 53.8 to 55.8 µs, in three runs each.
- **Where the time goes,** from a profile of each in `beta/bench`:
  - The filtered search: 46 per cent goes on the filter, about 68 ns a
    record against the basis's 50, and 40 per cent on the dot products of
    the tenth that pass, at about 2.6 GB a second, the rate the basis
    gives. Of the filter's time, a third fills the record's row, a third
    works out the condition, and a fifth takes the row from a pool and puts
    it back, since a search can call the filter from several goroutines.
  - One link out: two fifths go on the `stat` each read makes to follow
    other processes (F6), and the rest on the walk, with the lookup of the
    record it starts from.
  - Three links out, 155 records a walk: 45 per cent goes on sorting each
    round's records by key, as 0.x orders them, and 28 per cent on
    reaching the records.
- **Answer:** none has a small fix. The filter's pool is about a tenth of
  the search and filling its row a sixth. Taking out the pool and halving
  the fill would bring the search to about 12.5 ms here, still short of the
  target, and the fill is the path every scan in SQL takes. Splitting one
  search across the cores, which BETA.md's "Left out of the Beta" leaves
  for later, would about halve it on two. The `stat` is what every read
  pays to see other processes' commits. A cheaper sort for the
  deep walk, such as one that compares a few bytes of each key kept beside
  it before the key itself, wants a task with tests of its own, and what it
  would save isn't measured here. They stay for R4 to record, with the
  second question below.

- **Where:** `hypercrux/check.go`, `readLog`, with `logfile/applied.go` and
  `follow.go`, which tell Check how far this process has read the file.
- **Why it matters:** `readLog` took the database's ID and generation from
  the header it read, and checked the batches against them up to the end
  this process had read. Another database's file of the same length,
  copied over the file in place, keeps the inode and passes every one of
  those checks, and so does another copy of the same database whose last
  commit differs from this one's. The process reads on from a copy the
  file no longer holds, and Check called the file sound. G7.md notes that
  the next writer's check of its last marker finds it, and Check is the
  call meant to.
- **The fix:** `logfile.Applied` gains the header and the marker that ends
  the log, as this process read or wrote them, and the last batch's
  number, which the log publishes with the end. `readLog` wants the same
  header and, after that many batches, the same last marker. A commit
  copies 96 bytes more into the spot it publishes already.
- **Test,** in `hypercrux/check_test.go`:
  `TestCheckFindsAFileCopiedOverInPlace` copies two files of the same
  length over an open database's file in place. One is another database
  made by the same calls, which Check names as damage at offset 0, the
  header. The other is a copy of the same database with another last
  commit, which it names as damage at batch 5's marker. Reads carry on in
  both, as before.
- **Planted bug,** in `hypercrux/plant_on.go`:
  `hypercrux/check-copy-over-unseen` takes both checks away, which the test
  catches.
- **What's left:** two copies of one database whose batches part before
  the last and end with the same batch, byte for byte, still look alike to
  Check. A running checksum of the batches' checksums, kept beside the
  last marker, would tell them apart, at a line or two in each place the
  log moves its end. It's left, since it takes two writers making the same
  last commit after different ones.

**SQL's own nearest search copied every record's vector into its filter's
row (G4.md). Fixed.**

- **Where:** `query/plan_run.go`, `filter`, which fills a row for each
  record with `RowSource.Fill`, in `ops.go`, before it works out the
  filter's terms.
- **Why it matters:** the row held every field the statement reads, and a
  statement of the nearest shape always reads the vector, for its `ORDER
  BY distance(vec, ?)`. So the filter made a copy of each record's vector,
  two allocations of 1.5 KB, though none of its terms read it. `SELECT key
  FROM docs WHERE grp = ? AND vec IS NOT NULL ORDER BY distance(vec, ?)
  LIMIT 10` on 100,000 records took 145 to 166 ms here, in six runs, where
  `Nearest` with the filter `grp = ?` takes 12 to 15.
- **The fix:** `fill` leaves the vector's place NULL unless the filter's
  terms read it, which `readsVec` finds from their names, since a term's
  subqueries can't use fields (SQL.md, "The one-record subquery").
  `NearestFilter` hands the plan its terms as well, so a filter of
  `Nearest`'s that reads the vector still gets it, which
  `TestNearestFiltersAs0xHasThem` checks against 0.x. The same statement
  now takes 13.3 to 15.1 ms, the two builds taking turns three times, and
  13.7 to 16.1 ms in the benchmark's final form, beside 12.1 to 14.9 ms for
  `Nearest`.
- **Tests,** in `query/plan_test.go`:
  `TestASearchsFilterCopiesNoVectorItDoesntRead` wants the filter to
  allocate nothing for a record when its terms don't read the vector,
  counted with `testing.AllocsPerRun`, and a copy when they do, as
  `length(vec) = 12` and `distance(vec, '[0, 1, 0]') < 2` do. Three filters
  that read the vector have to give the search the answers the sort gives,
  which `+ 0` after the distance turns it into.
- **Planted bugs,** in `query/plant_plan_on.go`:
  `query/filter-copies-every-vector` puts the copy back, which the test
  catches, and `query/filter-drops-the-vector` leaves the vector out when a
  term reads it, which `TestRandomPlannedQueriesAs0xHasThem` catches first,
  and the new test as well.

**A condition that ends in a comment (R1.md, found with its fix to the
printer). Fixed.**

- **Where:** `query/parse.go`, `ParseCondition`, which reads `Nearest`'s
  `where`.
- **Why it matters:** 0.x puts the filter in parentheses at the end of its
  own query, so a `--` comment with no line feed after it, or a `/*` with
  no `*/`, takes in the closing parenthesis, and SQLite gives "incomplete
  input". The Beta took `n > 0 -- the rest` as `n > 0`. SQL.md's rule
  behind it settles the case, since a statement in the subset gives an
  error of the same kind where 0.x gives one, so the code was wrong.
  SQL.md's sentence on a NUL byte in the filter is the same case, and the
  coordinator's note has one for this beside it.
- **The fix:** `closed` lexes the condition with a closing parenthesis
  after it, as 0.x writes it, and a condition whose parenthesis doesn't
  come out as a token of its own at its end is "incomplete input" there.
- **Tests:** `TestFiltersThatEndInACommentAs0xHasThem`, in
  `query/plan_sqlite_test.go`, runs 13 filters through 0.x's `Nearest` and
  through the Beta's planner. Six fail in both, among them a `--` comment
  ended by a carriage return alone and `/* the rest *`. Seven work in both,
  among them a comment closed by a line feed or by `*/`, and `--` and `/*`
  inside quotes. The kinds of error and the hits have to agree.
  `TestConditionsOfSpaceNames`, from R1, now wants `c + "--"` to be
  incomplete input, and runs its round trip on `c + "--\n"`, and
  `FuzzParse` has two seeds of that kind.
- **Planted bug,** in `query/plant_on.go`: `query/comment-takes-in-nothing`
  takes the check away, which both tests catch.

**The batched put, against its target of 5 µs (C1.md's note for R4).
Answered, measured.**

- **The time:** 9.8 to 11.0 µs a put here, in three runs, and 10.1 in the
  recorded run after C1.
- **Where it goes,** from a profile of `BenchmarkPutBatch_384dims` on the
  Beta. Writing and syncing each batch's 1.6 MB takes 2.9 to 3.5 ms on this
  disk, timed with `dd`, so about 3 µs of a put is the sync, while the
  processor waits. Of the processor's time on the goroutine that puts, a
  fifth goes on the public package's conversion, most of it turning the
  vector into its bits and checking it, half on the store's put, and a
  fifth on the commit's batch and its write. In the store's half, copying
  the vector into the array's fresh memory is an eighth of the whole, the
  map of records a tenth with its growth, and the key order a fifteenth.
  The collector's marking took a quarter as much again, on the other core.
- **Answer:** each vector is checked three times, by the public package,
  the store and the codec, and copied four times: into its bits, out of
  them into the store's buffer, into the array and into the batch. Leaving
  out the public package's check and the codec's, which repeat the
  store's, and the copy through the store's buffer, would take about a
  tenth off, by this profile. With the sync at 3 µs, the target leaves the
  processor about 2 µs a put, so no change of that size reaches it. The
  second question below asks whether to accept the miss.

**Part 1's notes on the store and the gate. Answered.**

- **A batch applied whole or not at all (S3).** `ApplyBatch` applies a
  batch in a transaction of its own, and rolls it back at the first change
  that breaks the rules, with a `*errs.Damage`. `LoadBatch`, for a store
  nobody else reads, leaves the changes before that one, so an open that
  fails throws the copy away, and a reload that fails sets `DB.unread`,
  which every read gives back until a reload works. Both hold.
- **Nothing of a vector block kept once `Apply` returns
  (`Options.BlocksInPlace`).** Only a batch of blocks alone comes straight
  from the read buffer, and the store's other paths copy what they keep:
  names with `strings.Clone`, text and bytes in `keep`, vectors into the
  arrays.
- **Decoded slices with no room past their length (F1.md).** The store
  copies what it keeps, and sorts a clone of a put's fields, so nothing it
  does to a decoded slice reaches the batch.
- **The store's put:** above.
- **No read that takes the gate shared while it holds it.** None does
  through the package. `Export`'s writer was the one way a caller's code
  could, which is the first finding.

**Vector arrays never shrink while a process runs (V1.md). Answered.** A
put takes a freed slot before a new one, and a search passes a free slot
at the cost of reading a nil owner. The memory comes back when an array is
built afresh, at a reopen, or at the reload that follows another process's
compaction. Since C1, deleting half of what a database holds makes about
half its file dead, so a compaction follows, and every other process
reloads. The process that compacted keeps its copy, arrays and all.
Shrinking an array in place would move vectors between slots under the
undo list, for memory a reopen gives back, so it stays.

**An export carries 0.x's differences (G6.md). Answered.** An export holds
what its engine holds. A field that a failed `Put` left in a table of
0.x's is in 0.x's export, and an import brings it into the Beta like any
other field. That's 0.x's state, which an export is there to keep, and the
difference G2 settled is in `beta/README.md`'s list. No change.

**C1's notes. Answered.** The count of dead bytes is the same in every path
that changes the copy, a transaction, `ApplyBatch` and `LoadBatch`, and
the log starts it again at each compaction and reload, as C1.md sets out.
`Due` reads it holding the log's mutex, and `Pending`, which doesn't, is
the tests' alone. The count costs a put a few additions, which the profile
above doesn't show. Small commits whose framing outweighs what they make
dead are compacted at the limit alone, in a file of a few MB, and the
hold-off after a failed compaction is each process's own, which changes
only when each tries again. The limit on commits stays fixed, as the owner
chose.

### Questions for the owner

**1. How long text and bytes may be.** The Beta takes values up to
4,294,967,295 bytes, the most FORMAT.md's u32 gives, and 0.x up to
1,000,000,000, SQLite's limit. So a database of the Beta's can hold a value
0.x refuses, and its export then doesn't import into 0.x. Neither SQL.md
nor S1 settles it (S3.md).

- **A, keep 4 GB.** It costs a line in `beta/README.md`'s differences from
  0.x and one in EXPORT.md, both below. Such a value takes more than a
  gigabyte of the copy in memory, and an export writes bytes in base64, a
  third longer.
- **B, take 0.x's limit,** in the store's `fits`, which `Put`, SQL's
  writes and `Import` all go through, with 0.x's error. FORMAT.md's u32
  stays as it is, so no byte of the format changes. About an hour, with a
  test of `fits` itself, since a test with a value of a gigabyte would take
  a gigabyte.
- **Recommendation: B.** The Beta keeps SQLite's other limits, such as a
  statement's length, 1,999 fields a table and the 1,000,000,000 bytes SQL
  can make, an export is meant to move either way, and nothing the Beta is
  for needs a single value of more than a gigabyte.

**2. The speed targets still missed.** Four of BETA.md's targets stay
missed, each answered above with where its time goes: the batched put,

and 56.4 µs against 3 and 40. None has a small and safe fix.

- **A, accept them for the Beta.** R4 records each beside its target, with

- **B, a task of about three hours before R4,** for one check of each
  vector and one copy fewer in a put, and no pool in the filter: about a
  tenth off the batched put and a tenth off the filtered search, by these
  profiles. Neither would reach its target.
- **Recommendation: A.** Each misses by twice its target at most. Apart
