# S2: Transactions

Status: done, 8 October 2026.

## The contract

From BETA.md: transactions: the undo list; begin, commit and roll back; the
copy's lock taken at the first change; the error for a call through the
database inside `Update`. Done when random transactions with random
rollbacks match the model under the race detector.

## What was built

- **`beta/internal/store`**, in the new `tx.go` and `goroutine.go`, with
  changes to `store.go` and `write.go`:
  - `Store.Begin`, which starts a transaction, a `Tx`, one at a time, and
    notes the goroutine that began it.
  - The `Tx`'s writes, `Put`, `Delete`, `Drop` and `Apply`, which are the
    store's own inside the transaction. Each adds its changes to the
    transaction's change list, and one that fails takes back whatever it
    changed.
  - The `Tx`'s reads: it implements `Reader`, and sees its own changes.
  - `Mark` and `RollbackTo`, for a statement that fails inside a transaction
    (Q6).
  - `Commit(write)`, which hands the change list to `write` with the copy
    still locked, and `Rollback`.
  - The undo list: an entry before each change to the store, from the six
    small functions that make the changes, and the walk back.
  - The copy's lock, a `sync.RWMutex`. `Store.Read(fn)` holds it shared, and
    a transaction takes it alone at its first change.
  - The goroutine check: `goroutine()`, from the first line of
    `runtime.Stack`. `Begin` and `Read` check by themselves, and
    `Store.Outside` is the check the public package calls before the write

  - Five planted bugs, in `plant_on.go` and `beta/plants.txt`:

## The result

- **Random transactions with random rollbacks match the model under the
  race detector.** `TestTransactions` runs 12 seeds of 300 transactions, or
  3 of 150 with `-short`.
  - A transaction holds one to five statements of one to three steps. A
    step is a put, a delete, a drop or an applied create, with the bad keys,
    names and values of S1's generator, or a get through the transaction.
  - A statement with a write that failed is taken back to its mark half the
    time, and one in eight of the rest are too. Then the transaction
    commits, or commits with a write that fails, or rolls back.
  - Every answer must agree with the model's, and a write that fails must
    leave the change list as it was. After each transaction the store must
    hold what the model holds, and so must a replica that applies each
    committed change list through a transaction of its own.
  - Two readers read the whole store throughout, and every state they see
    must be one that a commit left.
  - Seed 1 alone makes 1,468 writes, a third of which fail, 305 statement
    rollbacks, 182 commits, 53 commits whose write fails and 58 rollbacks.
    Its readers make 1,000 to 2,000 reads each and see about 150 different
    states.
  - It takes 1.0 seconds, 5.1 with `-race`, and 0.1 and 0.8 with `-short`.
    The store's tests take 3.8 seconds, 20 with `-race`, and 0.9 and 3.6
    with `-short`.
- **Readers wait only after the first change.**
  `TestReadersWaitOnlyAfterTheFirstChange` checks it by trying the lock and
  with a read on another goroutine. Before the first change, and after
  writes that failed and changed nothing, reads go ahead. From the first
  change, through a `RollbackTo`, until the commit or the rollback, they
  wait, and then see what the transaction left.
- **The goroutine check** fails at once on the goroutine running the
  transaction, and leaves other goroutines to wait. `TestInsideUpdate` runs
  the transaction on a goroutine of its own, so a call that waits for itself
  fails the test after 10 seconds instead of hanging it.
- **Bugs planted by hand,** one at a time: 17 in the transaction code, all
  caught. The 14th, clearing the number of the transaction's goroutine after
  releasing the writer's mutex, got through until
  `TestOneTransactionAtATime` made transactions wait more than a millisecond
  for each other. Go's mutex then hands the store straight to the next
  transaction, which is when that bug bites. `sh scripts/planted.sh` reports
  11 of 11 caught, in about a minute.
- `go vet ./...`, `go test -short ./...`, `go test -race` on `store`, and
  `sh scripts/check-beta.sh` pass.

## Decisions settled

**The undo list.**

- There's an entry before each change to the store, made by the function
  that makes the change: `newTable`, `add` and `setSize` in `store.go`, and
  `put`, `remove` and `drop` in `write.go`. Each calls `changing` with the
  entry first, so nothing changes the store without one.
- An entry holds the whole earlier state of one part of the store. There
  are seven kinds:

| Kind | Made before | Holds | Put back by |
|---|---|---|---|
| `undoNoTable` | a new table | its name | deleting the name |
| `undoHadTable` | a drop | the table | putting it back in the map |
| `undoFields` | a field added | the table, and how many fields it had | cutting the list back, with the index and the vector field's place |
| `undoSize` | the vector size set | the table, and its size | setting the size again |
| `undoNoRecord` | a new record | its key | deleting the key |
| `undoHadRecord` | a record removed | the record | putting it back in the map |
| `undoRecord` | a put on a record that was there | the record, its fields and its vector | setting them again |

- A rollback walks the list newest first, so each entry finds the store as
  its own change left it. Since each holds a whole state, an entry whose
  change a panic cut short still puts things right.
- A put replaces a record's field slice whole (S1), so `undoRecord` keeps
  the old slice without a copy. A new record needs no `undoRecord`, since
  `undoNoRecord` takes it whole. A drop leaves the table and its records as
  they were, so undoing it puts each back in its map.
- A field list cut back by a rollback has no room past its end, so a field
  added later never lands in the array an earlier read handed out, and S1's
  promise about reads holds across rollbacks.

**Begin, commit and roll back.**

- `Begin() (*Tx, error)` waits while another transaction is open, on the
  store's `writer` mutex, so one runs at a time.
- `Tx` has the store's writes as `Put(key, fields)`, `Delete(key)`,
  `Drop(name)` and `Apply(c)`, which return only an error, since the change
  list is the transaction's. Its reads are `Reader`'s, and take no lock.
- `Commit(write func([]format.Change) error) error` hands the change list
  to `write` while the copy is locked, so readers in this process see the
  changes only once `write` has put them in the file. `write` isn't called
  for a transaction with no changes, since a batch holds at least one, and
  it's nil for a batch applied from the log. If `write` fails or panics,
  `Commit` rolls back and returns the error, or panics again. The list is
  `write`'s to keep.
- `Rollback()` does nothing once the transaction has ended, so a caller
  defers it straight after `Begin`. After the end, the other methods fail
  with an error that wraps `errs.ErrClosed`, `Table` finds no table, and
  ranging over `Snapshot` panics.
- The store's own `Put`, `Delete`, `Drop` and `Apply` stay as S1 made them,
  for a goroutine that has the store to itself, such as S1's tests. They
  panic while a transaction is open, since a write around it would change
  the copy without the lock or the undo list.

**A write that fails** runs inside a mark of its own, and is rolled back to
it, so it leaves the transaction as it was, whatever it changed first. The
store's writes check everything first, so for now they change nothing when
they fail, and the transaction doesn't count on that. `Mark()` and
`RollbackTo(m)` give Q6 the same for a whole statement. A transaction keeps
the copy's lock through `RollbackTo`.

**The copy's lock.**

- It's a `sync.RWMutex` in the store.
  `Store.Read(fn func(Reader) error) error` calls `fn` with the store, under
  the lock held shared. A transaction takes it alone in `changing`, at its
  first change, and releases it at its end. A write that fails before it
  changes anything takes no lock.
- The transaction reads without the lock. It's the only writer, and until
  its first change it reads beside the readers.
- Go's RWMutex lets a waiting writer in ahead of new readers, so a stream
  of reads can't hold a transaction off. `TestAWaitingWriterGoesFirst`
  holds the store to that.
- The order of locks: the log's write lock (F2) first, then the store's
  `writer` (`Begin`), then the copy's lock (the first change). Readers take
  the copy's lock only. Nothing takes the log's lock while it holds either
  of the store's.
- A read changes nothing in the store, a cache included.

**The goroutine check.**

- `goroutine()` reads the number in the first line of `runtime.Stack`,
  "goroutine 18 [running]:". It panics if the line doesn't start that way,
  which `TestGoroutineNumbers` would show on a new Go. A call costs about
  1 µs on a shallow stack and 8 µs at 20 frames, since `runtime.Stack` walks
  the whole stack even into a small buffer.
- `Begin` notes the number in `owner`, an atomic, and `held` says when the
  transaction holds the copy's lock. Only a goroutine itself can make
  `owner` its own number, so the check can't go stale while it runs.
- Three calls fail with `errs.ErrInsideUpdate` on the transaction's own
  goroutine: `Begin` at any time, before it waits for `writer`; `Read` after
  the first change; and `Outside` at any time, for the public package. With
  no transaction open, each costs one atomic load, and `runtime.Stack` runs
  only for a call that would wait anyway.
- The check lives in the store, since the store holds the transaction and
  knows when its first change comes. So the store's own `Read` and `Begin`
  can't wait for themselves, whoever calls them.
- It goes by the goroutine that began the transaction. A read on that
  goroutine fails after the first change even when another goroutine made
  the change through the `Tx`. A call from a goroutine that `fn` starts and
  waits for can't be caught, as BETA.md says.

**The planted bugs:** `store/undo-oldest-first`, a rollback that walks the
list oldest first; `store/changes-kept`, a `RollbackTo` that leaves its
changes in the list; `store/readers-not-held`, a first change that takes no
lock; `store/readers-in-early`, a `Commit` that lets readers in while it
hands the list on; and `store/inside-unchecked`, a `Read` that skips the
goroutine check. The last takes 10 seconds a test to catch, since it's a
read that waits for itself.

## Notes for later tasks

**G1:** `Update` goes like this, with `Outside` before the write lock:

```go
if err := db.store.Outside(); err != nil {
	return err
}
// take the write lock and catch up (F2, F6)
stx, err := db.store.Begin()
if err != nil {
	return err
}
defer stx.Rollback()
if err := fn(&Tx{...}); err != nil { // the public Tx, over stx
	return err
}
return stx.Commit(appendBatch) // the batch, its sync and its marker
```

- Every write through `DB` is an `Update`, so `Outside` covers them all.
  `Compact` calls it too, and so can `Close`, which would wait for the
  `Update` as well.
- Reads through `DB` go through `db.store.Read`, which checks by itself, and
  copy out what they keep before the callback returns.
- The public `Tx`'s methods call the store `Tx`'s. Once `Update` has
  returned, the store `Tx` gives `errs.ErrClosed`.
- The store returns `errs.ErrInsideUpdate` unwrapped.

The rest:

- **Q6:** `tx.Mark()` at the start of each statement, and
  `tx.RollbackTo(m)` when it fails. The transaction carries on.
- **S3:** a batch applied whole is `Begin`, `Apply` for each change,
  `Rollback` at the first that fails, and `Commit(nil)`. `Tx.Apply` adds
  each change to the transaction's list too. Opening a file can apply with
  the store's own `Apply`, outside a transaction, since a batch that fails
  ends the open anyway. That saves `Begin`'s call to `runtime.Stack`, which
  would cost a fraction of a second over 100,000 commits of one put each.
  The snapshot is ranged over inside `Read`'s callback.
- **S4:** a key joins its table's order where `put` makes a record, and
  leaves it in `remove`. On a rollback, `back` puts that right for
  `undoNoRecord` and `undoHadRecord`. A drop that leaves its table's order
  whole needs nothing more for its own records.
- **S5:** undo kinds for a link added and a link taken out, made where the
  lists change. A delete takes a record's links out before the record, so
  a rollback puts the record back first and its links after.
- **V1:** a vector changed in its slot needs its old values copied into the
  undo entry, since the slot itself changes. A slot that a delete or a drop
  frees stays out of the free list until the commit, or its undo has to
  take it back. Norms are worked out at the write, since a read changes
  nothing.
- **F2 and F5:** `write` runs with the copy locked, under the log's write
  lock. A cut after a failed commit, and `ErrStuck`, happen inside it. The
  store rolls back on any error it returns.
- **F6:** a commit grows the file in this process too. The point the
  process has applied has to move inside `Commit`'s `write`, while the
  transaction is still open, and a follower checks it again once its
  `Begin` returns, or it applies its own process's commit twice. A follower
  applies through a transaction, so it waits for an `Update` under way, and
  it takes no log lock while it's in one. During an `Update` the file can't
  grow, so a read inside `fn` finds nothing to apply.
- **F8:** the snapshot comes through `Read` after the commit that set the
  compaction off, under the log's write lock still.
- **F9:** a reload takes the store's `writer` and then the copy's lock, in
  that order, as a transaction does.
- **The coordinator:** `beta/README.md`'s line for `internal/store/` can
  end: "Reads share it through `Read`, and writes go through a transaction
  from `Begin`, which holds readers off from its first change until it
  ends, and puts the copy back with its undo list when it rolls back."
  `beta/plants.txt` has five new lines for the store.
