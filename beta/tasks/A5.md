# A5: The search loop

Status: done, 7 October 2026.

## The contract

From BETA.md: 8 running sums in plain Go. Done when amd64 and arm64 return
the same bits on random and awkward vectors.

## What was built

`beta/internal/vecmath`, Linux only like the rest of `beta/`:

- `Dot(a, b []float32) float64`: each value widened to float64, products
  into 8 running sums with value i in sum i mod 8, unrolled by 8. The tail
  of a vector whose length isn't a multiple of 8 goes to the sums in turn
  too.
- `Wide` and `Widen`: a query widened to float64 once. `Wide.Dot` gives the
  same bits as `Dot` on the float32 values it came from, and saves the
  query's conversions on every vector.
- `Norm(a)`: the square root of `Dot(a, a)`.
- `Distance(dot, normA, normB)`: one minus `dot / (normA * normB)`, kept
  between 0 and 2, and 1 when a norm is 0. That's 0.x's formula, from
  `cosine` in `vectors.go`.
- The combining order is `((s0+s1)+(s2+s3))+((s4+s5)+(s6+s7))`.
- Tests:
  - `TestSameBitsEverywhere` checks 36 pairs against
    `testdata/golden.txt`, recorded on amd64. The pairs are random vectors
    of lengths 1 to 17, 31 to 33, 384, 1,536 and 65,536, and awkward ones:
    subnormals, values near float32's largest, big and small together,
    -0, one ulp apart, the same, opposite, orthogonal, all zeros, and one
    big value among many small ones.
  - `TestTheLoopsMatchTheReference` compares both unrolled loops, bit for
    bit, with the loop written as plainly as possible, on those pairs and
    on 2,000 vectors of random bits.
  - `TestCloseToZerox` compares distances with 0.x's arithmetic on 5,000
    random pairs.
  - `TestDistanceEdges` covers the edge cases, and benchmarks set the loop
    against BETA.md's targets.
- CI: a new job, `arm64`, on `ubuntu-24.04-arm` runs this package's tests.

## The result

- **Same bits:** the `arm64` job passed on 7 October (run 37645948853), so
  linux/arm64 gives the 36 pairs' recorded bits, as linux/amd64 does.
  Built for arm64, Go fuses the main loop's 8 multiply-adds into `FMADDD`
  instructions, which BETA.md expected. Since the products are exact, the
  bits don't change.
- **Close to 0.x:** the largest difference from 0.x's distances was
  1.67e-15, where `conformance.DistanceBound` allows 1e-9.
- **Speed,** on this two-core cloud machine:

| Benchmark | Time | BETA.md's target for a whole search |
|---|---|---|
| The loop over 100,000 vectors of 384 values | 56 to 61 ms | 65 ms |
| The loop over 10,000 vectors of 1,536 values | 20 to 22 ms | 26 ms |
| One dot product of 384 values, in cache | about 300 ns | |

A scan of 100,000 vectors of 384 reads 154 MB and runs at about 2.7 GB/s,
so memory sets its pace more than the arithmetic does: one dot product in
cache takes half the time of one in the scan. That leaves 4 to 9 ms of the
first target for the heap, the filter and the rest of a search. V1 should
measure it, and the open question about V2 stands.

## Decisions settled

- **The shape:** slices, not a flat array. V1 can pass sub-slices of its
  vector array without copying.
- **The query:** widened once with `Widen`. A `Wide` made from anything but
  float32 values loses the promise of equal bits, since its products are no
  longer exact. The type's comment says so.
- **Test vectors** use only `Float32` from `math/rand/v2` and operations
  every processor rounds the same way. `NormFloat64` can reach `math.Exp`,
  whose bits aren't guaranteed to match across processors.
- **Distance** rounds `normA * normB` on its own line, so nothing can fuse
  across it.
- **Recording again:** `HYPERCRUX_VECMATH_RECORD=1 go test -run
  TestSameBitsEverywhere ./beta/internal/vecmath`, on amd64, only when the
  loop is meant to change.

## Notes for later tasks

- **V1:** keep each table's vectors in one flat `[]float32` and the norms
  beside them. A search widens the query once and calls `Wide.Dot` on each
  live slot. Then `Distance(dot, queryNorm, norm)`.
- **P1:** the `arm64` job runs only this package. P1 widens it to the whole
  of `beta/`, and can plant a bug here (4 sums, or another combining
  order), which `TestSameBitsEverywhere` and the reference test catch.
- **Later speed-ups**, from BETA.md: Go assembly that keeps the 8 sums and
  the combining order gives the same bits. Splitting a search across cores
  only changes which vectors each core reads, not any dot product.
