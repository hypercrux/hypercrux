# S1: Records, fields and rules

Status: done, 7 October 2026.

## The contract

From BETA.md: records, fields and rules: the hash table, field lists, each
table's field order, and 0.x's rules for keys, fields, link types and
vectors. Done when a random model test and 0.x's rule cases pass.

## What was built

- **`beta/internal/rules`**, a new package: 0.x's rules as checks on plain
  Go values, with 0.x's errors and messages.
  - `TableOf` checks a whole key and gives its table, as 0.x's does.
    `Table`, `Field`, `LinkType` and `Vector` check a table's name, a
    field's name, a link's type and a vector. `Text` and `Real` check the
    text and reals a field stores.
  - `IsVec`, `Fold` and `SameName` match names regardless of ASCII case.
    `CaseClash` and `VectorElsewhere` are 0.x's errors for one field in
    two spellings and for a vector outside `vec`.
  - The limits: 0.x's `MaxKeyLen`, `MaxTableLen`, `MaxFieldLen`,
    `MaxLinkType` and `MaxDims`, with `MaxFields` and `FormatMaxFields`.
- **`value.FromGo`**, in `beta/internal/value/fromgo.go`, in place of the
  stub: 0.x's `encodeField`, `toVector` and the parsing in `ParseVector`,
  quirks included. A pointer in `vec` is refused, as in 0.x, and so is a
  `[]any` of ints there.
- **`beta/internal/store`**:
  - `Store` and `New`: the hash table from key to record, each record's
    fields by place, each table's field list with its index by folded
    name, the vector field's place and the vector size.
  - The read side: `Table`, `Get`, and `Table.Find`, the lookup that
    matches names regardless of case. `Scan`, `Neighbours`, `Walk` and
    `Nearest` return an error that matches `errors.ErrUnsupported` and
    names their task, and ranging over `Snapshot` panics, until S3, S4, S5
    and V1 write them.
  - The write side: `Put`, `Delete` and `Drop`.
  - `Apply`: one change of a change list, checked by FORMAT.md's rules,
    for CreateTable, Put, Delete and Drop.
  - Four planted bugs, in `plant_on.go` and `beta/plants.txt`:
    `store/nulls-kept`, `store/drop-keeps-records`, `store/spelt-as-given`
    and `store/size-unchecked`.
- **Tests:**
  - `rules`: 0.x's cases for keys, names, link types and vectors, the
    messages that tests look for, and two tests against 0.x itself. 20,000
    random keys go through both `TableOf`s, which must give the same table
    or the same message. Random field names, link types and vectors go
    into 0.x's `Put` and `Link`, which must take each one exactly when the
    rule does.
  - `value`: the values of PutAndGetRoundTrip and MoreFieldTypes, the
    refusals of KeyAndFieldRules, and 150 awkward Go values put into 0.x
    and given to `FromGo`. Both must refuse a value with the same message,
    or `FromGo` must give what 0.x's `Get` gives back, bit for bit.
  - `store`: the model test, the rule cases and a test against 0.x, with
    tests of the change lists, `Apply`, the field limit, `Find`, and the
    copies the store keeps.
- `beta/README.md` lists `rules`, and says what `store` and `value` hold
  now.

## The result

- **The random model test passes.** `TestTheModel` runs 20 seeds of 4,000
  steps, or 4 of 2,000 with `-short`, against a model of plain maps: puts
  with field names in mixed case, nulls, vectors and values that break the
  rules, and gets, deletes and drops. Every answer must agree with the
  model's. A write that fails must give no changes and leave the store as
  it was. Every write's changes go through `Apply` into a second store,
  which must come out the same. Each kind of step has to come up working
  and failing.
- **0.x's rule cases pass** against the store's checks: KeyAndFieldRules,
  PutAndGetRoundTrip, MoreFieldTypes, RulesForLongKeysAndLinkTypes and
  TableNamesLikeHyperCruxsOwn, from 0.x's tests and the conformance suite,
  with PutKeepsFieldsItIsNotGiven, GetAndDeleteMissing, NewFieldsShowAtOnce,
  Vectors and DropTable beside them. The parts that go through SQL check
  the same rules on the store, and link types go through `rules.LinkType`
  until S5. `TestTheStoreAgrees0x` runs 3,000 random steps with Go values
  on 0.x and on the store side by side. Both must give the same errors
  with the same messages, the same records, and each table's fields in
  the order of 0.x's `SELECT *`.
- **Bugs planted by hand,** one at a time: 24 in the store, of which 23
  made its tests fail. The 24th changed nothing, since a cleared vector
  sets the size to `len(nil)`, which is 0. Three rules broken in `rules`
  and three conversions broken in `FromGo` failed their tests too.
  `sh scripts/planted.sh` reports 6 of 6 caught.
- `go vet ./...`, `go test -short ./...`, `go test -race` on `rules`,
  `value` and `store`, and `sh scripts/check-beta.sh` pass. The store's
  tests take about 3 seconds, with `-race -short` too.

## Decisions settled

**The layout.**

- The hash table is a Go map from key to `*record`. A record holds its
  key, its table, its fields and its vector, with room marked for S5's
  links.
- A record's fields are `[]FieldValue`, by place, with nulls and the
  vector left out, as `Record.Fields` hands them out. A put builds a new
  slice and never changes one in place, so a slice a read handed out stays
  as it was, and S2 can undo a put by putting the old slice back.
- A table holds its field list in its fixed order, an index from each
  name folded to lower case to its place, the vector field's place (-1
  until a put names it) and the vector size (0 until the first vector).
  The list only grows until the table is dropped, so places never move.
  Room is marked for S4's keys and V1's array.
- Until V1, each record holds its vector as a `[]float32`, which
  `Record.Vec` hands out without a copy. V1 moves it into the table's
  array and keeps the slot's number there.
- Reads hand out slices whose capacity ends at their length, so appending
  to one never writes into the store.
- Names match with their ASCII letters folded to one case and nothing
  else, as SQLite matches names, so the Kelvin sign never matches a k.
- The store keeps its own copy of every string it holds: keys, names,
  text and bytes. A decoder can slice values out of one string per batch,
  and the store never keeps the batch alive.
- Drop looks at every record to find its table's, until S4 keeps each
  table's keys.
- A `Store` is for one goroutine at a time. The lock is S2's.

**The write side.**

- `Put(dst, key, fields)`, `Delete(dst, key)` and `Drop(dst, name)` each
  return `([]format.Change, error)`. They append the changes the write
  amounts to to `dst`, the transaction's change list, and return it, so a
  transaction keeps one list for all its writes.
- Each checks everything before it changes anything. On an error the
  store is as it was and `dst` comes back as it went in.
- A first put into a table gives a `CreateTable` with no fields and size
  0, then the `Put`. The `Put` spells each field as the table does, in
  byte order of those spellings, which can differ from the order of the
  names given: `Zed` sorts before `title`, and `zed` after it. Its values
  are the ones the store keeps.
- `Put` takes the fields in any order, and neither keeps the slice nor
  changes it. Its errors come in 0.x's order: the key, the names, the
  values in byte order of name, the number of fields, then the vector's
  size.
- `Apply(c)` makes one change of a change list, checked by FORMAT.md's
  rules for changes, and shares the code that changes the store with the
  writes. S3 applies whole lists on top of it, with S2's undo.
- `Table.Find` is new in the read API, a method on `Table`, so no caller
  changes. It looks through `Fields`, so it works on a fake store's tables
  too.

**Where the rules live:** in `beta/internal/rules`, which imports only
`errs`. `value` imports it for `FromGo`, and `store` for everything. The
public package and the codec can import it too without a cycle. The store
couldn't be the home, since `format` can't import `store`, and the public
package would have had to reach into the store for checks that hold no
state.

**The limit on fields:** a put can't take a table past 1,999 fields
besides its key. That's 0.x's limit, from SQLite's 2,000 columns, so every
table moves between 0.x and the Beta both ways. `Apply` holds a change
list read from a file to FORMAT.md's limit of 65,535, so the limit on puts
can rise later without a change to the format, and an older build still
opens a newer build's file. A put that adds no fields works on a table past the
limit.

**Where the Beta differs from 0.x,** on purpose: two broken rules give
`ErrInvalid` where 0.x gives a plain error. One is a link type that starts
with a zero byte, which 0.x's `Link` refuses through its trigger without
wrapping the error. The other is a put past 1,999 fields, where SQLite
says "too many columns". P5 settled the error of `vector()` the same way.

**FromGo and the public `Vector`.** `value` can't import the public
package, so `FromGo` knows its `Vector` by package path and name, through
reflection. It takes the type in `vec` and refuses it, and a pointer to it,
in any other field, as 0.x does with its own `Vector`. A test pins the path
against the value package's own, so moving the tree moves both.

**New messages,** where 0.x has none: the field limit, a value of the
wrong kind for `vec`, which only SQL can give, and each way a change list
can break FORMAT.md's rules.

## Notes for later tasks

- **P4 and G1:** the public `TableOf`, `MaxKeyLen` and `MaxDims`, and the
  check behind `ParseVector`, can be `rules`'s. `Put` checks the key with
  `rules.TableOf` and the names with `rules.Field` and `rules.CaseClash`
  first, then converts each value with `value.FromGo` in byte order of
  name, then calls the store's `Put`, which keeps 0.x's order of errors.
  `putGo` in `store/cases_test.go` does exactly that. `Get` turns a record
  into `Fields` with `Table.Fields` and `Value.Go`, and `Record.Vec` into a
  `Vector`. A test in the public package should put its `Vector` through
  `FromGo`, in `vec` and in another field.
- **S2:** each change to the store is easy to undo. A put replaces a
  record's field slice (put the old one back), may create a record or a
  table (delete it), may append fields to a table (cut the list back and
  delete their index entries) and may set the vector size (set it back to
  0). A delete takes a record out, and a drop its table and its records
  (put them back). The transaction is the store itself, as a `Reader`.
- **S3:** emit what `Put`, `Delete` and `Drop` append. Applying a list
  whole is `Apply` on each change with S2's undo. The model test's second
  store is a start on S3's closing test.
- **S4:** keys come and go in `put` and `remove`, in `write.go`, and
  `drop` can then look at its table's keys alone.
- **S5:** `Apply` refuses Link and Unlink until then, and `remove` is
  where a record's links go. 0.x's `Link` checks the type with
  `rules.LinkType` before the keys. 0.x's `Unlink` checks neither its keys
  nor its type, and says "not found" for a bad one.
- **V1:** `record.vec` becomes the slot's number. Drop takes the table's
  array with it, so a new table of the same name starts at size 0.
- **F1:** the decoder's checks on names and values can call `rules`.
- **Q6:** SQL writes go through the store's `Put`. A blob for `vec`
  becomes a vector with `value.VectorBits` first, when its length is a
  whole number of float32s, and SQL.md's message for `vec` takes the place
  of the store's.
- **The coordinator:** P3.md's table of packages needs a row for
  `beta/internal/rules` (0.x's rules, S1, importing `errs`), and `value`
  now imports `rules` and `errs`. FORMAT.md's "Names and limits" can name
  the Beta's own limit of 1,999 fields.
