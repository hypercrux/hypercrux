# A3: Differential harness

Status: done, 7 October 2026.

## The contract

From BETA.md: random sequences of operations run on two engines and
compared, with distances within the stated bound and failing sequences kept.
Done when 0.x against itself passes, and a deliberately broken 0.x fails.

## What was built

`beta/difftest`, Linux only like the rest of `beta/`:

- `ops.go`: a step (`Op`) is plain data: a call, or an `Update` holding up
  to five calls. Values carry their type in JSON, with floats written by
  their bits, so a sequence saves and loads exactly. `Generate(seed, n)`
  makes the same sequence from the same seed every time. It can leave kinds
  of step out (`Kinds`, where "where" stands for Nearest's filters).
- `run.go`:
  - `Replay` runs a sequence on a new database for each engine and compares
    every answer. It then compares the whole database.
  - `Find` runs sequences until two engines disagree, and shrinks the one
    they disagree on.
  - `Save` and `Load` keep failures as JSON.
- Tests:
  - `TestZeroxAgainstItself` runs 0.x against itself. A failure is saved
    into `testdata`.
  - `TestSavedSequences` replays every file in `testdata`.
  - `TestABrokenEngineIsCaught` runs 0.x against six broken copies of
    itself.
  - The other tests check values and sequences: they save and load
    exactly, they repeat from the same seed, and kinds left out stay out.
- `conformance.CompareHits`: `sameHits` from A1 as a function that returns
  an error, so the suite and the harness share one rule for ties.

## The result

0.x agreed with itself on 2,000 random sequences of 5 to 80 steps. The run
takes about 40 seconds, or 300 sequences under the race detector in about 19.
Each broken copy was caught within its first 11 sequences, and every failure
shrank to between one and five steps:

| Broken copy | Steps after shrinking |
|---|---|
| `Unlink` with a type removes every type | 4 |
| `Nearest` leaves out its last hit | 3 |
| `Scan` with a limit returns one record fewer | 3 |
| `Put` stores -0 as 0 | 1 |
| `Walk` leaves out the furthest record | 5 |
| A `Put` inside an `Update` survives the rollback | 1 |

## Decisions settled

- **The mix of steps,** out of 100:
  - put 26, link 20;
  - walk 8, nearest 8, update 8, sql 7;
  - get 6, scan 5;
  - unlink 4, neighbours 4;
  - delete 3, drop 1.
  - A third of the Updates roll back.
- **Keys:** three tables (`docs`, `people`, `t_1`) and fourteen ids, some
  odd, such as `é`, `a b`, `😀` and `x/y`. Keys `Put` refuses come up now
  and then.
- **Values:**
  - awkward integers and reals (extremes, -0, subnormals), text in several
    scripts with NUL and control characters, empty and random bytes, and
    booleans;
  - now and then a value `Put` refuses (infinity, NaN, or text that isn't
    UTF-8), a field name it refuses, or the same field spelt in two cases.
- **Vectors:** each table's size is set by its first vector, and about one in
  ten vectors is wrong: the wrong size, all zeros, or holding NaN. Vectors
  gather in `docs` and `t_1`.
- **The generator's memory:** it keeps a rough idea of what the database
  holds, so most steps can succeed, but it never looks at the database. It
  remembers keys and vector sizes only from `Put`s the rules allow. It
  forgets what a rolled-back `Update` did.
  - Links mostly join recently put records, and a third extend a chain.
  - Walks and neighbours start from records with links.
  - Searches go to tables with vectors.
  - Without that tuning, only 2 walks in about 1,000 reached a second
    record. Now, in 300 sequences of 80 steps, 126 of 1,902 walks did, and
    128 of 1,869 searches found two hits or more.
- **SQL:** a fixed list of seven statements, every query with
  `ORDER BY`. There are reads, a count with a sum, a walk joined to a
  table, an ordered search, an `UPDATE`, a `DELETE` and an `INSERT`.
- **Comparing:**
  - An error matches by kind: ok, not found, invalid, rolled back or other.
    Messages are only shown in the report.
  - Values are shown with their type, floats and vector values with their
    bits.
  - Nearest's hits go through `CompareHits`.
- **The whole database** is compared after each sequence. That covers every
  record of the three tables through `Scan`, `Get` (with its vector) and
  `Neighbours` out of it, plus Check's counts and its number of problems.
- **Shrinking:** the steps after the first mismatch go first. Then halves,
  quarters and so on down to single steps, then single steps inside each
  `Update`, then single fields of each `Put`.
- **Run length:** 2,000 sequences, or 300 with `-short`.
  `HYPERCRUX_DIFF_SEQUENCES` sets any number, for long runs. The databases
  go in `/dev/shm` when it exists, since this harness doesn't test what
  survives a crash.

## Notes for later tasks

- **P1:** CI already runs the harness through `go test ./...`. It adds about
  40 seconds on Linux, and about 19 for the race job. The broken copies in
  `broken_test.go` show one way to plant bugs.
- **G2:**
  - Add a test running 0.x against the Beta. The `check` helper in
    `difftest_test.go` needs an `Options.Leave` of "sql" and "where" until
    G4.
  - `TestSavedSequences` replays with 0.x on both sides. Once the Beta
    exists, it should replay with 0.x against the Beta.
- **G4 and P5:**
  - SQL errors such as "no such table" count as "other" in 0.x. If the
    Beta reports them as `ErrInvalid`, the harness will flag every one. P5
    should settle which kind they are.
  - The ordered search in the SQL list compares keys only. Distances that
    differ in the last bits between engines could swap two keys whose
    distances are near enough equal. If that happens, compare those rows
    within the bound.
- **R1:** long runs use `HYPERCRUX_DIFF_SEQUENCES`.
- **Left out:** many processes (T4) and crash safety (T1 to T3).
