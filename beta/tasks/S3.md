# S3: Change lists

Status: next, in one round with T2 and T3. Planned at 2 hours. It needs S2,
which is done.

## The contract

From BETA.md: change lists, emitted as a transaction runs, applied whole or
not at all, and a snapshot for compaction. Done when store A's change lists
applied to store B, and A's snapshot loaded into store C, both give back A.

## What's there already

- **The store's writes** (S1) append the changes each one amounts to, and
  `Apply` makes one change of a list by FORMAT.md's rules.
- **Transactions** (S2): `Begin`, the `Tx`'s writes and `Apply`, `Commit`
  handing on the change list, and `Rollback`. S2.md's note under S3 says how
  to apply a batch whole, and that opening a file can apply with the store's
  own `Apply`, outside a transaction, to save `Begin`'s cost.
- **The snapshot** (P3): `Reader.Snapshot()`, an `iter.Seq[format.Change]`
  in FORMAT.md's order for a compacted part, still a stub. P3.md says a
  put's `Fields` slice is used again for the next put.
- **The log's side** (F2): `logfile.Target`, with `Apply(seq, changes)` and
  `Reset()`, which G1 joins to the store.

## To settle, and write down in this file

- **Emitting:** what a commit hands on is what the writes appended, in
  order, keeping FORMAT.md's rules for what a writer emits, which
  `format.Change`'s comment repeats and `AppendBatch` checks.
- **Applying a list whole:** the store's call for one batch from the log,
  all of it or none, inside a transaction or outside one on opening, and
  what it returns when a change breaks the rules: damage, since a batch
  that counts can't hold such a change.
- **The snapshot:** written, streaming one change at a time, from inside
  `Read`, in FORMAT.md's order: tables by name with their vector size and
  whole field list, each table's records by key, then the links (none
  until S5).
- **The tests:** random workloads on store A; A's change lists applied to
  B, and A's snapshot loaded into C; then A, B and C compared, through the
  read API and the snapshots themselves.
