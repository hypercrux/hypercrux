# T2: Fault layer for names

Status: done, 8 October 2026.

## The contract

From BETA.md: the fault layer for names: create, rename, remove and
directory sync, each kept or lost at a cut. Done when a rename without a
directory sync can vanish and one with it can't.

## What was built

All of it is in `beta/internal/fault`, on T1's disk. T1's API is as it was:
no exported name was added, changed or taken away.

- **`names.go`:** the journal, which holds each change to names, or to an
  owner, that the drive may not hold yet, in call order, with the folder or
  folders it's in. `syncDir` puts a folder's changes on the drive, with
  the changes they lean on, and `settleNames` is what a cut does to names.
- **`disk.go`:** `Disk` keeps two sets of names, the ones the calls see and
  the drive's, with the journal between them. A cut settles names first,
  then data. The folders `Mkdir` makes are on the drive at once. `Disk`'s
  comment sets out the model for names beside T1's for data.
- **`fs.go`:** `Create`, `Rename`, `RenameNoReplace` and `Remove` put their
  change in the journal, and so does `Chown`, as a change in the folder
  that holds the file's name. A cut in one of these calls comes once the
  change is made. `SyncDir` puts its folder's changes on the drive.
- **`inode.go`:** a file's owner and group as the drive holds them, beside
  the ones the calls see.
- **Six planted bugs,** in `plant_on.go` and `beta/plants.txt`, each making
  the disk kinder than its model or breaking its order:
  `fault/names-always-kept`, `fault/names-out-of-order`,
  `fault/sync-keeps-name`, `fault/one-sync-for-all`,
  `fault/cut-before-names` and `fault/chown-lasts`.
- **Tests:**
  - `rename_test.go`: the closing test; the same for a creation and a
    removal; compaction's switch and the creation of a database as BETA.md
    and FORMAT.md set them out, with the power cut in each of their calls;
    files whose names a cut took or gave back; owners and permissions; a
    SyncDir of one folder of two; a rename between folders; a cut in each
    kind of call that changes names; a failed SyncDir.
  - `order_test.go`: an oracle for names, written from `Disk`'s comment
    alone, that holds every cut in long random runs to the states the model
    allows, and the same seed leaving the same names.
  - T1's tests, which pass with five changes where they leaned on names
    lasting without a SyncDir (under Decisions).

## The result

- **A rename without a directory sync can vanish, and one with it can't.**
  `TestARenameVanishesWithoutASyncDir` renames a file over another, as
  compaction switches files, and to a free name with `RenameNoReplace`, as
  a database is created, then cuts the power, in 200 seeds each way. Both
  files' data and names were synced before the rename. Without a SyncDir
  after it, the rename vanished in 109 seeds and lasted in 91, for each
  kind of rename. With one, it lasted in all 200. Each name held one whole
  file every time.
- **The same for a creation and a removal.** A file made, written and
  synced, its data and not its name, was gone after the cut in 109 seeds,
  data and all, and there in 91; with a SyncDir it was there in all 200. A
  removed file was back in 109 seeds with its data; with a SyncDir it was
  gone in all 200. When one change is pending, the seed's first draws
  decide it, so every test of that shape splits its 200 seeds the same way.
- **Compaction's switch,** in `TestCompactionSwitches`: NAME.compact made
  with the database's permissions, locked, given the database's owner,
  written, synced and renamed over the database, then the folder synced and
  the lock let go, with the power cut in each of the 9 calls and after the
  last, in 60 seeds: 600 cuts. The path always held a whole database, the
  old one or the new one, and the new one always had the owner, group and
  permissions it was given, and one name. A cut in the rename, or
  in the SyncDir, left the old file in 36 seeds and the new in 24. Once the
  SyncDir had returned, it was the new file in every seed.
- **Creating a database,** in `TestCreatingADatabase`: a `.new-` file made,
  locked, checked, given a header and synced, renamed with
  `RenameNoReplace`, then the folder synced and the lock let go, with the
  power cut in each of the 10 calls and after the last, in 60 seeds: 660
  cuts. After every one the path held nothing or the whole header. 164
  cuts left a `.new-` file, always beside nothing. A cut in the rename or
  in the SyncDir left the database in 27 seeds and nothing in 33; after the
  SyncDir, the header was there in every seed. A creator that found a
  database already at the path removed its own file: after a cut the other
  database was there in all 200 seeds, and the removed file was back in 20.
- **Files whose names were lost:** a file made and synced, whose name
  wasn't, was gone in 60 seeds of 100: `Stat` and `Open` found nothing,
  `List` left it out, and a new file at the name started empty. A file a
  lost rename had replaced came back in 60 seeds of 100, with its data and
  one name. A removed file came back in 60, with what was written to it
  after the removal, through a handle still open, and synced.
- **Order,** in `TestNamesKeepTheirOrder`: 8 runs of 4,000 random steps in
  two folders, making files, renaming them both ways, removing them,
  changing owners, syncing folders and files, with the power cut between
  calls or in one, and rules failing calls: 3,117 cuts, every one leaving
  a state the oracle allowed. Every pending change was kept at 1,043 cuts,
  every one lost at 951, and the changes up to a point kept at 424. At 126
  a synced change lasted while an earlier one in the other folder was
  lost. The change the power was cut in lasted at 420 cuts and was lost at
  646.
- **Owners:** a Chown followed by its file's Sync was kept in 91 seeds of
  200 and lost in 109; with its folder synced, kept in all 200. With a
  Chown and then a rename pending, the rename lasted in 100 seeds, always
  with the Chown. A file there after a cut had the permissions it was made
  with.
- **Folders:** with a file made in each of two folders and the second
  folder synced, the second file was there after the cut in all 200 seeds,
  and the first gone in 109. A file moved between folders was at exactly
  one of its names after every cut; with either folder synced, at the new
  one in all 200 seeds. A file made in one folder and moved to another
  lasted once the second folder was synced, in all 200.
- **Cuts in calls:** with the power cut in a `Create`, a `Rename`, a
  `RenameNoReplace`, a `Remove` or a `Chown`, each returned `ErrCut`, and
  its change lasted in 91 seeds of 200. A cut in a `SyncDir` lost the
  creation before it in 109. After a failed `SyncDir` the file made before
  it was gone in 109 seeds, and with a good one after the failure it was
  there in all 200. A rename a rule failed never showed after a cut.
- **The same seed leaves the same names:** 8 seeds through 1,500 random
  steps each, run twice, left the same names and owners after every cut,
  and no two seeds left the same.
- **T1's results stand.** `TestUnsyncedDataLostOrTorn` and `TestFailedSync`
  give T1's counts to the sector, since a cut with no change to names
  pending draws nothing from the seed. `TestSyncedDataSurvivesEveryCut` ran
  its 4,368 cuts; 47 of them took a file away with its name, and 97 found a
  file whose `Create` the power was cut in, which the test now requires.
  `TestSyncedDataSurvivesLongRuns` ran 1,786 cuts, with 5,167 failed calls.
- **The tests catch a wrong disk.** The six planted bugs are caught, and
  `sh scripts/planted.sh` reports 27 of 27. Of 18 bugs put in by hand one
  at a time, such as a SyncDir that leaves out the other folder of a
  rename, a cut that keeps the end of the journal, a SyncDir that leaves
  what it stored in the journal, a cut in a SyncDir that comes after the
  sync, a failed SyncDir that syncs all the same, a Chown in no folder,
  owners left as the calls saw them after a cut, and Mkdir's folders left
  pending, the tests caught all 18.
- `go vet ./...`, `go test -short ./...`, `go test -race` on
  `beta/internal/fault` with and without `-short`, and
  `sh scripts/check-beta.sh` pass. The package's tests take about 1.7
  seconds, 6.3 under `-race -short` and 24 under `-race`.

## Decisions settled

**What ext4 does,** with its default journal, data=ordered, the model the
brief names:

- Every change to names and inodes goes into the journal's running
  transaction, and the journal commits its transactions in order, each
  whole or not at all. A commit comes every 5 seconds by default, on an
  fsync that needs one, and when the journal fills. So for calls made one
  after another, a power cut keeps every change up to some point in call
  order. A later change never lasts while an earlier one is lost, in one
  folder or across folders.
- A rename is one journal handle, so it lasts or is lost whole.
- An fsync on a folder commits the journal, which makes every earlier
  change last, in every folder. Linux promises less. Its fsync(2) page says
  that a file's fsync doesn't promise the file's entry in its folder, and
  that the folder needs an fsync of its own.
- An fdatasync on a file whose size has grown commits the journal up to
  that change, so a new file's name usually lasts with its data. Linux
  doesn't promise it.
- A chown is a change to the inode in the same journal. fdatasync doesn't
  flush it, since reads don't need it, and the next commit does.

**What a cut does to names.** The disk keeps the names the calls see, the
drive's names, and between them a journal: each `Create`, `Rename`,
`RenameNoReplace`, `Remove` and `Chown` that worked, in call order, with the
folders it's in.

- At a cut the drive keeps the journal's changes in call order up to a
  point, and loses the rest. A third of the time it keeps them all, a
  third of the time none, and otherwise the point is picked among all of
  them, either end included. That's the cruellest outcome ext4's order
  allows, since a commit can fall between any two calls. It loses
  everything since the last sync as often as it keeps it, and it can keep
  a creation and lose the rename after it.
- **May a later change in a folder survive while an earlier one is
  lost?** On ext4, no. In the model, no, within a folder. Across folders
  the model is crueller than ext4, through SyncDir, below.
- A file left without a name is gone after the cut, data and all, as on
  ext4, where its creation and its inode's allocation are in one
  transaction. A file whose removal is lost, or the rename that replaced
  it, is back with one name, and its data as T1's model settles it.
- Names settle before data, and a cut with an empty journal draws nothing
  from the seed, so with every name synced, a seed's data outcomes are
  T1's.

**What a SyncDir promises:** the names in its folder as the calls left
them. It puts on the drive every change in the journal made in its folder,
with the earlier changes those lean on. A rename between two folders is a
change in both, so syncing either takes the earlier changes in the other
with it, and so on from there. That's Linux's promise. ext4 keeps more,
since that fsync commits the whole journal. The model doesn't count on it:
a SyncDir of one folder leaves another folder's earlier changes to the cut,
so a later change can last while an earlier one elsewhere is lost. A file
system that logs each fsync on its own, as btrfs does, can do the same.
The engine keeps its names in one folder, beside the database, so only a
test with two folders sees it.

**What a file's Sync does for its name:** nothing. Linux promises nothing
for the name with fdatasync, so the model doesn't keep it, where ext4
usually would.

**Owners and permissions.** A cut can lose an unsynced `Chown`. A `Chown` is
a change in the journal, in the folder that holds the file's name, so it
keeps its place in call order, and the SyncDir that makes the name last
makes the owner last too, as ext4's commit would. A file's Sync doesn't,
as fdatasync doesn't flush an owner. A `Chown` on a file with no name is in
no folder, and only a cut can keep it, which shows only if the cut gives
the file its name back, and then the removal came before the `Chown`, which
is lost with it. There's no chmod call: the permissions `Create` sets are
part of the creation, kept or lost with it.

**Cuts in calls on names.** A cut in a `Create`, a `Rename`, a
`RenameNoReplace`, a `Remove` or a `Chown` comes once the call has made its
change, so the change is pending at the cut and can last though the call
returned `ErrCut`, as on ext4, where a commit can take it before the power
goes. T1's cut came first, which is still one of the outcomes. A cut in a
`SyncDir` comes first, so it puts nothing on the drive. In one folder that
covers a cut after the sync as well, since keeping every change is one of
the outcomes.

**Failed calls on names** change nothing, as in T1, so a failed `SyncDir`
puts nothing on the drive, and a good one after it does. On ext4 a failed
commit stops the journal, and every later fsync fails; a rule whose
`Times` is -1 gives that.

**Folders.** `Mkdir` is for a test's setup, so the folders it makes go on
the drive at once, as if the folder above each were synced straight after,
with whatever was pending there. No call makes a folder, and `Rename` and
`Remove` refuse one, so folders never change after that.

**Where the model is kinder than ext4.** These are left out, for a later
task to add if the engine needs them:

- the permissions the real `Create` sets with fchmod, a change of its own
  after the open, which ext4 can lose while keeping the creation, leaving
  the umask's permissions;
- a failed call on names that took effect all the same, which T1 left out
  too;
- a folder whose own creation is lost.

**T1's tests.** Their checks are T1's. Five changes were needed where they
leaned on names lasting without a SyncDir, which T1's model gave:

- `cut_test.go`'s world syncs "/" after each creation, as a step of its
  own, chosen without drawing from the steps' generator, so its other
  steps are T1's. Its oracle lets a file whose name wasn't synced be gone
  after a cut, and then forgets it, and lets a file whose `Create` the
  power was cut in be there, empty, where T1's said it mustn't be.
- `TestUnsyncedDataLostOrTorn`, `TestCutInAWrite`, `TestCutInATruncate`,
  `TestCutKillsTheProcess`, `TestFailedSync` and the cut in `TestRuleTimes`
  make their file with `mustCreate`, which syncs its folder.
- `TestFlockAcrossOpens` syncs "/" before its cut.
- `TestNames` syncs both its folders before its cut, where T1 held names
  that weren't synced to last.
- `TestSyncedDataSurvivesEveryCut` requires, without `-short`, a cut that
  takes a file away with its name, and one that leaves a file whose
  `Create` the power was cut in.

## Notes for later tasks

- **T3, in this round:** a file whose folder isn't synced after its
  creation can vanish at a cut, data and all, and a cut in a `Create` can
  leave the file there, empty. T3 was written against T1's names, so its
  toy log should sync its folder after making its file, as FORMAT.md's
  creation does, or its checks should allow the file to be gone. The
  tests' `mustCreate` does the first.
- **F3, recovery:** after a cut, a `.new-` file or a NAME.compact that its
  writer removed can be back, and so can one it never finished, empty,
  part written or whole. The file at the database's path always holds a
  whole header, since the header is synced before the rename.
- **F8, compaction:** until the SyncDir after the switch returns, a cut can
  leave either file at the path, with NAME.compact beside the old one.
  Whenever the rename lasts, the new file has the owner its `Chown` gave
  it, since the `Chown` came first. When the SyncDir fails, the rename stays
  pending, and a later cut can leave either file, so the writer is right
  to keep the lock. `TestCompactionSwitches` is the sequence on the bare
  disk.
- **F9, reloading:** a backup moved into place is a rename like any other,
  and lasts only once its folder is synced.
- **F7, file rules:** the permissions `Create` gives are part of the
  creation.
- **R1, long runs:** `TestNamesKeepTheirOrder` takes its sizes from the
  numbers at its top, as T1's long runs do.
- **Tests on the disk:** sync the folder after making a file whose name
  must last a cut. A folder `Mkdir` makes lasts, and so does whatever was
  pending in the folder above it then.
- **Shared files:** `beta/README.md`'s entry for `internal/fault` needs a
  line on names (the report gives wording). No interface changed.
