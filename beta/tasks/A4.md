# A4: SQL corpus

Status: done, 7 October 2026.

## The contract

From BETA.md: statements inside and outside the subset, a few thousand
generated expressions and date cases, with answers recorded through 0.x.
Done when it replays clean on 0.x twice.

## What was built

`beta/sqlcorpus`, Linux only like the rest of `beta/`:

- `corpus.go`:
  - `Case` and `Answer`, the format.
  - `Fixture`, the fixed data every case runs on, built through the
    conformance API so any engine can build the same database.
  - `Run` runs one case on any engine. A statement that may write runs in an
    `Update` that's then rolled back, so the data never changes.
  - `Same` compares two answers, and `Replay` runs a whole corpus on an
    engine. `Save` and `Load` write and read it as JSON lines.
- `cases.go`: `Build()` makes every case from code, the same each time:
  - the hand-written statements;
  - the expression generator, from a fixed seed;
  - the date cases;
  - the cases on `'now'`.
- `testdata/`: the corpus with 0.x's answers.
  - `statements.jsonl` holds 289 statements, 235 guessed in and 54 out.
  - `expressions.jsonl` holds 3,000 expressions.
  - `dates.jsonl` holds 608 date cases and 14 on `'now'`.
- Tests:
  - `TestRecord` writes the corpus, but only when
    `HYPERCRUX_CORPUS_RECORD=1` is set.
  - `TestCorpusMatchesItsSource` fails when the code that makes the cases
    has changed and the corpus hasn't been recorded again.
  - `TestReplayTwice` is the closing test.
  - `TestTheCorpusIsBroad` checks the sizes, and that the answers hold
    every kind of value and error.

## The result

All 3,911 cases replayed clean on 0.x twice, each time on a new database, in
about 0.3 seconds. The answers held:

| Kind of value | How many |
|---|---|
| Integers | 2,005 |
| Text | 1,843 |
| NULL | 615 |
| Reals | 294 |
| Bytes | 98 |
| Text that isn't UTF-8 | 5 |
| Errors of kind "error" | 40 |
| Errors of kind "invalid" | 6 |

## Decisions settled

- **The data** (`Fixture`): three tables.
  - `docs` has 8 records, mixing integers, reals, text, bytes, JSON text
    and 3-value vectors. One `n` holds text, one score is -0, and one
    vector is shared by two records, so searches tie.
  - `people` has 4 records with dates as text.
  - `t_1` has 5 records with 2-value vectors.
  - 13 links join them, with two cycles. The order of the Puts sets each
    table's field order, which `SELECT *` shows.
- **Statements:** written by hand from BETA.md's "Queries and SQL", each
  with a first guess, `in`, for P5.
  - In: plain reads, 99 single conditions under `WHERE`, aggregates over
    the whole result, both of 0.x's walk forms, the one-record subquery,
    `distance` and `vector`, writes, and mistakes.
  - Out: `GROUP BY`, joins, `CASE`, `WITH`, window functions, compound
    selects, other subqueries, `date` on a stored date, PRAGMA, DDL and so
    on.
  - Every query that can return more than one row orders its rows.
- **The Beta's own forms:** a statement only the Beta takes, such as walk
  as a table, carries `via`, the 0.x statement its answer is recorded from.
  `Run` takes a flag saying whether the engine has the Beta's forms. The
  walk table's columns are still for P5: the cases select only `key`, which
  0.x can answer.
- **Writes** run in a rolled-back transaction, with an optional `after`
  query read inside it, so the answer shows what the write did. The count
  of changed rows is recorded only for INSERT, UPDATE, DELETE and REPLACE.
  After anything else, SQLite's count is left over from an earlier
  statement.
- **Expressions:** 3,000 random trees, up to three levels deep, run as
  `SELECT <expression> AS v`.
  - The literals cover every type, with -0, the extremes, an integer just
    past 64 bits, 1e999, Unicode and blobs. About one leaf in 14 is a `?`
    with an argument.
  - The operators are arithmetic, comparisons, `AND`, `OR`, `NOT`, `||`,
    `IS`, `BETWEEN`, `IN` and `LIKE`.
  - The functions are BETA.md's candidate list, plus `CAST` and `nullif`,
    which P5 should take or leave.
  - About a third of the operators go without parentheses, so SQLite's
    precedence is in the answers too.
- **Dates:** 600 random `date` and `datetime` cases from 18 fixed dates, with
  one or two modifiers of days, months or years, singular and plural, and
  8 odd ones. The subset has them only on `'now'`: these are for Q2's
  arithmetic, and are marked out.
- **Cases on `'now'`:** 14, marked in. They have no recorded answer.
  `Replay` compares them with a reference engine at the same moment, on its
  own copy of the data, and tries again when a second ticks over.
- **The format:**
  - one case a line;
  - values in A3's tagged form (`difftest.Value`), so floats keep their bits;
  - errors by A3's kinds, with 0.x's message kept for reference and never
    compared;
  - `close` marks the cases whose reals are distances, which an engine may
    get within `conformance.DistanceBound` of.

  - Settle the functions, `CAST` and `nullif` among them.
  - Decide whether the scalar `walk()` form stays in. The statements on it
    say so in their `note`.

  - Settle the kind of error for "no such table" and the like. 0.x gives
    "error", and so does the corpus.
- **Q1 and Q4:** replay `expressions.jsonl` and the aggregates with
  `Replay(beta, zerox, cases, dir, true)`. Every expression should match
  exactly. Among other things that means SQLite's text for reals, as in
  `CAST(0.1 AS TEXT)`, which gives `0.1`.
- **Q2:** `dates.jsonl` gives the Beta's date arithmetic its expected
  results on fixed dates. The `'now'` cases check the SQL form against 0.x
  at the time.
- **Q3:** a statement marked out should be refused, with an error rather
  than a wrong answer.
- **Recording again:** run
  `HYPERCRUX_CORPUS_RECORD=1 go test -run TestRecord ./beta/sqlcorpus`
  after changing `cases.go`. The SQLite inside 0.x sets the answers, so a
  go-sqlite3 upgrade can change some; record again and read the diff.
