## The contract

From BETA.md: compaction by dead bytes: a compaction comes once the
batches since the last have made half the file dead, and a megabyte, or
once 100,000 commits follow the compacted part, counted alike by every
process. Done when every process takes the same choice from the same file,
a database that only grows is compacted only at the limit on commits, and
the crash suites and the many-process harness pass with the new rule.

## What's there already

- **The rule today,** in BETA.md's "Compaction": a compaction comes at the
  end of a commit once the file has grown to twice the size its last
  compaction left it at, and by a megabyte at least. It's `Due` in
  `beta/internal/logfile/compact.go`, which measures from the end of the
  compacted part, `liveBase`, with `minDead` and `Options.MinGrowth`, and
  holds off after a compaction that failed until the file has grown by as
  much again (`retry`). Every process reads the same from the file, so
  every process agrees.
- **What it costs:** a database that only grows is compacted each time it
  doubles, which G5 measured doubling the batched put, from 14 µs to about
  26 (G5.md's note under R2). The last recorded run gave 15.7 µs against
  the target of 5.
- **The option the owner chose,** in R2.md, part 1's first question, C:
  count what the batches since the last compaction have made dead, a put's
  old values, a deleted record with its links, a dropped table, a removed
  link, and compact once that's half the file and a megabyte, or once the
  commits past the compacted part reach a limit such as 100,000, which
  every process reads from the sequence numbers. Every process applies the
  same batches to the same state, so every process can count the same.
  The review put the count in both of the store's paths, applying a batch
  and a transaction, and opening 100,000 small commits at about a quarter
  of a second.
- **Where the compaction after a commit runs:** `Update` in the public
  package (G5), while it still holds the lock, after a commit that has
  succeeded, when `Due` says so.

## To settle, and write down in this file

- **What counts as dead,** in bytes of the file, and where the count lives:
  in the store, the log, or both, and how it reaches the log's choice. It
  has to be a function of the file alone, so a process that opened after
  the commits, one that followed them, and the one that wrote them reach
  the same count. A compaction starts it again from nothing.
- **The rule:** half the file dead and a megabyte, or the limit on commits,
  with `MinGrowth` and the hold-off after a failed compaction kept, and the
  limit's number settled, with how a test can set it lower.
- **The interfaces:** P3's change only through a task that updates every
  caller at once, so add to them and take nothing away.
- **The tests:** two processes, one that wrote the commits and one that
  opened after them, agreeing on every choice; a database that only grows
  compacted only at the limit on commits; one that overwrites and deletes
  compacted once half is dead; the crash suites and the many-process
  harness passing with the new rule; the closing test among them.
- **Planted bugs,** such as a delete's links left out of the count, a count
  that differs between applying a batch and a transaction, or a limit off
  by one, each with a line in `beta/plants.txt`.
- **The wording** for BETA.md's "Compaction", in place of its first
  paragraph, for the coordinator.
