# C1: Compaction by dead bytes

Status: done, 14 October 2026.

## The contract

From BETA.md: compaction by dead bytes, which the owner chose after R2's
first part: a compaction comes once the batches since the last have made
half the file dead, and a megabyte, or once 100,000 commits follow the
compacted part, counted alike by every process. Done when every process
takes the same choice from the same file, a database that only grows is
compacted only at the limit on commits, and the crash suites and the
many-process harness pass with the new rule.

The owner chose it on 14 October 2026, option C of R2.md's first question,
and put it before R2's second part, so that review takes in its code. No
byte of the format changes.

## Decisions settled

**What counts as dead.** The bytes of changes in the file that no longer
reach the state, which a compaction leaves out:

- a put of a record that's there already: the frame of one of its two puts,
  its kind, key and count of fields, 5 bytes and the key's, since a
  compaction writes one put a record;
- each value a put replaces, with its field's name, and the vector a put
  writes over or takes away;
- each null a put gives, which clears a field and is never kept;
- a delete: the delete itself, and the record, with every link to it and
  from it, a link from the record to itself once;
- a drop: the drop itself, the table's create, and every record of the
  table with every link to it and from it, a link between two of its
  records once;
- a removed link: the remove change, and the add it takes away, which is
  the same size.

Creating a table, a put that makes a record, a new link and a vector block
make nothing dead.

**A batch's head, checksum and marker never count,** nor a vector block's
head. So a database that only grows counts nothing dead, however small its
commits, as the contract wants. A compaction packs the live records into
batches of about a megabyte, so it takes away the framing of commits that
are still live as well, and counting that would make every database count
dead bytes as it grows. The cost falls on commits so small that their
framing outweighs what they make dead. A commit that writes over one
integer field of the record `c:1` is a change of 20 bytes in a batch of 72
with its marker, and makes 20 bytes dead, so at most 28 per cent of such a
file is ever dead. The limit on commits compacts it: 100,000 such commits
take 7.2 MB.

**The measure: each change as a commit writes it,** whatever form the file
holds it in. A table's create counts as a put into a new table writes it,
with no field list, and a vector as a put writes it, with the field's name,
its kind and its count of values. A compacted part writes both in forms of
its own: the create with the table's whole field list, and the vector in a
block, where its record's key takes the place of the field's name. One
measure makes the count a function of the state and the changes alone, so a
store that made a record through commits and one that loaded it from a
compacted part count the same when it goes. That lets the writer that
compacted and a process that opened its compacted file agree without either
reading the file again. Counting the file's own bytes would need each
record to remember the form it came in, a few bytes a record, or the writer
to reload the file it compacted.

**Exact by that measure, and within a few bytes of the file.** For
everything commits write, the count is the file's bytes of changes less
the live state's: the store's test checks it after every transaction, and
the closing test checks it against the file itself after every commit. Two
things differ from the file's bytes. A create that names its fields, as an
import's and a compacted part's do, leaves its field list out of a dropped
table's count, 2 bytes and each name's. A vector loaded from a block counts
7 bytes and its field's name, where the block held 2 bytes and its key's.
For 384 values, 1,536 bytes, and keys of 10 to 20 bytes, that's under 1 per
cent.

**Where the count lives: in the store, with two numbers in the log.** Only
the store knows what a change replaces, a record's old values or a deleted
record's links, so the store counts, in `dead`. It adds at the five places
a change makes something dead, the put, the delete, the drop, `setVector`
and `unlink`, each once its change has taken the copy's lock, and every way
into the store goes through them. The writer's transactions, a follower's
`ApplyBatch` and an opening's `LoadBatch` make the same changes to the same
state (S3), so they count the same. The count only grows, apart from what a
rollback takes back, and never starts again. The log reaches it through
`Counter`, which a Target meets or doesn't, so `Target` is as it was, and a
Target that keeps no state, such as a test's recorder, counts nothing. For
the file it holds, the log keeps what the count said when the file's count
began, `deadAt`, and the sequence number of the compacted part's last
batch, `compacted`. `Dead` is the count less `deadAt`, and `Commits` the
last batch's sequence number less `compacted`.

**The rule.** After a commit, holding the lock, `Due` says yes once
`Commits` reaches the limit, 100,000 or `Options.MaxCommits`, or once
`Dead` is at least the floor, a megabyte or `Options.MinGrowth`, and at
least half the file. The file is the log up to its end, with its header,
its compacted part and every batch's framing. `Due` says no without the
lock, for a stuck Log, for an empty file, and during the hold-off after a
failed compaction.

**The limit: 100,000 commits.** Opening a log of 99,999 small commits takes
about 0.3 seconds here, below the 392 ms the recorded run after R2's first
part gave for opening 100,000 records with 384-value vectors from a
compacted file, so the limit holds a log that makes little dead to about
the open time of a large compacted file. A database taking commits of
1,000 records reaches it at 100 million records. A test sets a lower one
with `Options.MaxCommits`.

**`MinGrowth` and the hold-off stay.** `MinGrowth` keeps its name and type,
since the internal APIs only gain, and sets the floor for dead bytes, which
is what the tests used it for: a small one for a few commits that write
over each other, a very large one for a log that stays as it is. The
hold-off after a failed compaction is F8's: the next isn't due until the
file has grown as much again as it had since its last compaction. It's the
one part of the choice a process keeps of its own, as before C1, so a
process whose compaction failed holds off where another, which saw no
failure, would compact at its next commit.

**A compaction starts both counts again.** The Log that compacts notes the
count at its switch to the new file, and the compacted part's last batch,
and a Log that reads a file from its start, on opening or a reload, notes
the count as it begins and the compacted part's last batch as it reads
past it. So all of them count from nothing in the new file. A reload hands
the public package's target an empty copy, whose count starts at 0, and
the log's subtraction would serve a Target that kept its count too.

**A rollback takes the count back.** A transaction notes the count at
`Begin` and at each `Mark`, and `Rollback` and `RollbackTo` put it back
with the copy, so the count never holds a change that no batch holds. A
call that fails inside a transaction goes back through `RollbackTo`, a
commit whose write fails through `Rollback`, and a batch a follower
refuses through `ApplyBatch`'s own transaction. A batch `LoadBatch`
refuses leaves part of it in the store, as before, and the store is thrown
away.

**The APIs.** The internal packages gain, and lose nothing:
`store.Store.Dead`, `logfile.Counter`, `logfile.Options.MaxCommits`,
`logfile.Log.Dead` and `logfile.Log.Commits`. `store.Mark` gains a field,
unexported like its others, so no caller sees it. `Due` keeps its
signature and the new rule. The public package's API doesn't change.

the writer compacts the file at the end of a commit, still holding the
lock, so the old file never changes again. Dead bytes are the changes in
the file that no longer reach the state, which a compaction leaves out: a
put's old values, a deleted record with its links, a dropped table with its
records, and a removed link with the change that removed it. Each process
counts them in its copy as it applies the changes, and counts the commits
from the sequence numbers. Every process applies the same changes to the
same state, so every process counts the same and takes the same choice from
the same file, and a compaction starts both counts from nothing. A batch's
head, checksum and marker never count, so a database that only grows is
compacted only at the limit on commits, which commits of 1,000 records
reach at 100 million records. The limit keeps opening bounded: a log of
100,000 small commits opens in about 0.3 seconds on a two-core cloud
