# G4: Slice 3, SQL

Status: done, 13 October 2026.

## The contract

From BETA.md: slice 3: SQL through the driver, vector arguments, errors
wrapping `ErrInvalid`. Done when A1's in-scope SQL cases pass, and A3 runs
the crux query on random data against 0.x.

## What was built

- **`beta/hypercrux`**, the public package:
  - `engine.go`, new: `sqlEngine`, the engine behind every DB's driver in
    place of `notYetEngine`, which has gone. A SELECT goes to Q5's
    `query.Query`, and an INSERT, UPDATE or DELETE to Q6's `query.Exec`,
    each with a `Frame` holding the arguments and the statement's moment,
    read once from the DB's clock (`moment`). `glue.go`'s `open` gives each
    DB its engine.
  - `driver.go`: `argument` makes an argument a value through `query.Arg`,
    the one conversion, and the driver's own copy of it has gone. `unnamed`
    refuses an argument with a name, for statements and for `Nearest`.
  - `vectors.go`: `Nearest` takes a filter. `searchable` makes 0.x's checks
    in 0.x's order, `searchArgs` makes the arguments values in database/sql's
    way, and `ParseCondition` and `NearestFilter` plan the filter.
  - `hypercrux.go`: `DB` has a clock, and `Update` returns nil once its
    commit is in the file, even when letting go of flock fails after it.
  - `doc.go` says what works now.
  - Five planted bugs, in `plant_on.go` and `beta/plants.txt`:
    `hypercrux/moment-kept`, `hypercrux/vector-argument-shared`,
    `hypercrux/filter-checks-reordered`, `hypercrux/filter-none-nil` and
    `hypercrux/unlock-error-kept`. `hypercrux/time-layout` moved into
    `argument`, and `hypercrux/filter-ignored` now ignores a filter that
    works.
- **`beta/internal/query/plan_filter.go`:** `NearestFilter` plans the
  caller's condition without 0.x's `vec IS NOT NULL`, which holds for every
  record the search hands it. Its terms, their order and their errors are

- **`beta/conformance`:** betax's `later` is empty. In `process.go` the kill
  test's writer says "ready" once it has opened the database, and the kill
  waits for at least a tenth of its random time after that.
- **`beta/difftest`:** `betaLeaves` is empty, the crux query is among the
  statements in 0.x's form, and the generator keeps the differences SQL.md
  lists out of its sequences (Decisions settled).
- **`beta/bench`:** the filtered search's line has left `later`.
- **Tests:**
  - `beta/hypercrux/engine_test.go`, new:
    `TestStatementsGive0xsAnswersEveryWayIn`,
    `TestEachStatementReadsItsMomentOnce`, `TestVectorArgumentsAreCopied`,
    `TestNearestFiltersAs0x` and `TestAFailedUnlockAfterACommitFailsNoUpdate`.
  - `beta/sqlcorpus/beta_test.go`, new: `TestTheBetaGivesTheCorpusAnswers`.

  Filtered searches ran 4,303 times, 528 with hits. 20,000 sequences, run
  once by hand, agreed too.
- **The corpus through `Replay` on the Beta:** all 3,249 cases marked in

  after each, 3,000 expressions and the 14 cases on 'now', which 0.x
  answers at the same moment. All 662 marked out are refused with errors
  of kind "error". `Replay` needed no change.
- **Every way into the driver gives 0.x's answers:**
  `TestStatementsGive0xsAnswersEveryWayIn` runs 37 statements through up to
  eight ways in, Exec and Query on a DB and on a Tx, and SQL()'s Exec and
  Query with and without a prepared statement: 290 runs on each engine.

- **The moment:** a clock that moves on a second at each read shows one
  read for each statement, all of a query's rows on that moment, one read
  for an INSERT of two rows, one for each statement inside an Update, and
  one for each filtered search.
- **Vector arguments are copies:** a Vector or a `[]byte` written through
  `Exec`, and then changed by the caller, reads back as written, from the
  copy and after a reopen, and so does one changed inside an Update before

- **`Nearest` with a filter agrees with 0.x** on 33 searches: conditions,
  quoted names, the one-record subquery, IN and NOT IN over a walk, terms
  that rule every record out, errors from the filter, broken filters behind

  an Update sees its changes.
- **The filtered search's benchmark** runs with `-benchtime 1x`. Over 10

  16.7 ms, the middle of three, and 0.x 141 ms.
- **A failed unlock:** Update returns nil, the commit is in the copy and in
  a reopen, another handle waits until this one's next Update, and an
  Update whose function fails gives the function's error.
- **The planted bugs are caught,** each by its test, one at a time with

- `sh scripts/check-beta.sh`, `go vet ./...`, `go test -short ./...`, and

  package's tests take 91 seconds, 20 with `-short`, and the new ones 0.3 of

## Decisions settled

**The engine** (`engine.go`): a SELECT is `query.Query(r, s, &Frame{Args,
Now})` on the read the driver hands over, and a write `query.Exec(tx, s,
&Frame{Args, Now})` on its transaction. Each call is one statement and
reads the moment once, before anything of it runs, from the DB's clock,
which is `time.Now` unless a test sets one with `UseClock`. Exec marks and
rolls back a failed statement itself, and the driver's own mark around it
is harmless. The planner's values never share the store's memory, and the
driver hands each vector and each bytes value out in a `[]byte` of its own.
Errors come back as the planner and the writes give them, so their kinds
follow the statement, and `plain` takes `ErrInvalid` off through `SQL()`.

**`Nearest` with a filter**, in 0.x's order:

1. The table's name, the query vector and k, then the table, which must
   exist, then its vector size: a table with none gives nil before anything
   else is looked at, the arguments and the filter included. Then the
   query's size against the table's. These are the store's checks and
   messages, made by hand first, since the store makes them only as it
   searches.
2. The arguments, each through `argument`, with database/sql's handling of
   a `sql.NamedArg` and its words for a value it refuses, "sql: converting
   argument $1 type: ...", which are 0.x's, filter or no filter.
3. `ParseCondition`. Without a filter the arguments aren't used, as in 0.x.
   With one, an argument with a name is refused, and `NearestFilter` takes
   exactly one argument for each `?` mark, and the moment, read once for the
   call. Its `none`, when the terms that use no field rule every record
   out, gives an empty list with no search, as 0.x's query gives no rows.
4. The store's search with the filter.

**One conversion:** `query.Arg`, Q1's, stays, since it's an internal
package's exported API. The driver's `argument` calls it, keeping only the
planted bugs of its own.

**`Update` after a failed unlock:** it returns nil once its function and
its commit have worked, whatever happens to the lock. An error from Update
then still means its commit isn't in the file, unless it wraps `ErrStuck`,
as BETA.md's "Commits" has it, and as an error from 0.x's Update means its
COMMIT didn't happen. The Log lets go of its mutex either way. When flock
is still held, this DB's next Update takes it again, since the file that
holds it can, and lets go of it, or Close does. Meanwhile other processes
wait for the lock, up to its 10 seconds.

**The kill test's timing** (`conformance/process.go`): the kill comes a
random 40 to 200 milliseconds after the writer starts, as before, but never
sooner than a tenth of that after the writer says it's ready. For 0.x,
which opens a file at once, that's the old moment. The Beta reads the whole
file as it opens, about 9 µs a commit for this test's small commits, most
of it the store's apply and the decoding. Counted from the start, 105 of
the 200 rounds committed nothing, their writers killed as they opened the
file, and the test failed its own check that it exercised something.
Counted wholly
from readiness, the Beta, which commits twice as fast as 0.x, grew the file
to 66,000 commits and took three and a half minutes.

**The differential harness:**

- The sum is `SELECT count(*), sum(n) FROM people WHERE typeof(n) =
  'integer' AND n BETWEEN -1000000000 AND 1000000000`, so its answer can't
  hang on the order of the rows, which is key order in the Beta and the
  order of the puts in 0.x (P5.md's note).
- The value an UPDATE writes is never infinite or text that isn't UTF-8,
  which 0.x stores and the Beta refuses (`sqlValue`).
- The crux query is `SELECT d.key, d.title FROM json_each(walk(?, ?)) w
  JOIN docs d ON d.key = w.value WHERE d.n > ? AND d.vec IS NOT NULL ORDER
  BY distance(d.vec, ?) LIMIT ?`, with `d.n` in place of a status, which the
  generator's records haven't got. Half the time, when it isn't a step
  inside another Update, it comes as an Update of its own that puts one to
  three docs with a title, an n and a vector, links them from a record, and
  runs the query from there through the transaction. Otherwise it comes
  once docs has a vector size, a title and an n, as far as the generator
  knows, and one time in ten before.
- A Put that fails its vector's size check inside an Update that commits
  leaves its new fields in 0.x and nothing in the Beta (SQL.md), and SQL
  that names one differs. The generator keeps such Puts out. It knows each
  table's vector size exactly, judging a Put on the values its map keeps,
  taking "[1, 2]" as the vector both engines read it as, and taking any
  size for a table that has none. A vector it knows to be the wrong size
  goes in a Put of its own. `TestTheGeneratorKnowsEachTablesSize` holds
  what it knows to 0.x after every step of 200 sequences, and 3,000 run
  once by hand agreed.

**Where SQL.md is silent or unclear,** settled as 0.x behaves and checked
against 0.x. The wording for SQL.md:

- "Nearest's filter", after its first paragraph: "`Nearest` makes 0.x's
  checks first, in 0.x's order: the table's name, the query vector and k,
  then the table, which must exist, then its vector size, where a table
  with none gives no hits before anything else is looked at, `args` and
  `where` included, and then the query's size against the table's. Then
  each of `args` becomes a value as a statement's argument does, and one
  that database/sql can't take is refused in database/sql's words, as in
  0.x, with a filter or without one. Without one, `args` aren't used. With
  one, they fill its `?` marks, exactly one for each, and an argument with
  a name is an error. When the filter's terms that use no field rule every
  record out, the search gives an empty list, as 0.x's query gives no rows.
  'now' is read once for each call."
- "Where the Beta differs from 0.x", the bullet on more arguments than `?`
  marks: "More arguments than `?` marks is an error, in a statement and in
  `Nearest`'s filter alike, where 0.x ignores the extra ones." And the
  bullet on `sql.Named`: "An argument with a name, from `sql.Named`, is an
  error, in a statement and in `Nearest`'s filter. 0.x leaves the mark it
  falls on NULL."
- The same list, the bullet "An error's kind follows the statement", at its
  end: "And a SELECT it runs through `Exec` reports a refusal of
  `distance()`, `vector()` or `walk()` as "invalid", where the Beta reports
  "error"."
- The same list, a new bullet: "`Exec` of a SELECT works out all its rows,
  so it gives the error any row raises, and gives `RowsAffected` 0. 0.x's
  works them out only as far as SQLite's first step, which is the first row
  unless the query sorts, since go-sqlite3 steps a statement once in
  `Exec`, and its `RowsAffected` is the count of the last write on its
  connection."

## Notes for later tasks

- **G5, the command:**
  - The command's SQL can go through the DB's `Query` and `Exec`, where a
    write's broken rule wraps `ErrInvalid` and reads "hypercrux: invalid:
    keys in table docs are text that starts with docs:, ...", the words the
    command's SQL section looks for. Through `SQL()` the same error reads
    "hypercrux: keys in table docs ..." and wraps nothing.
  - `rows.ColumnTypes` gives "" and `any` for every column, and no answer
    for nullable (G3.md). If the command types its JSON by them, the
    engine can say which column is a table's key or vector.
  - Compaction changes how long a writer takes to open its file, which the
    kill test's timing now allows for. Its file holds about 17,000 small
    commits at the end, which opens in 150 to 200 ms here.
- **R1, long runs:** `HYPERCRUX_DIFF_SEQUENCES` takes the harness as far as
  wanted; 20,000 sequences took 400 seconds here. The ordered SQL compares
  keys only. No two keys swapped in 20,000 sequences; if distances that
  differ in their last bits ever swap two, compare those rows within
  `conformance.DistanceBound`, as A3.md's note says.
- **R2, review:**
  - SQL's own nearest search fills every column the statement reads into
    the filter's row, so with `ORDER BY distance(vec, ?)` it copies each
    record's vector. `SELECT key FROM docs WHERE grp = ? AND vec IS NOT NULL
    ORDER BY distance(vec, ?) LIMIT 10` on the benchmark's 100,000 records
    took 206 ms here, where `Nearest` with the filter `grp = ?` takes 15.
    `filter` in `plan_run.go` could fill a row without the vector unless one
    of the filter's terms reads it.
  - Opening a log of many small commits costs about 9 µs a commit, the
    store's apply about 5 µs of it and decoding about 3. V2 and G5 bear on
    it.
  - After a failed unlock, flock stays held until the DB's next Update or
    Close, and writers in other processes wait for it meanwhile.
