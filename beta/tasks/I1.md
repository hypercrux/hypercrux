# I1: Integration

Status: done, 12 October 2026.

## The contract

From BETA.md: integration: the real store in place of the model in the file
suites, and the 200 SIGKILLs and many processes through the public API.
Done when those suites pass on amd64 and arm64, and opening 100,000 records
is timed against its target, which decides whether V2 runs.

The suites pass on amd64 here, and CI's arm64 job runs them. The figure to
go by for opening is the coordinator's recorded run, under "The recorded
run".

## What was built

- **The crash-point driver through the public package,** in
  `beta/hypercrux/workloads_test.go`, new, with three hooks from inside the
  package in `export_workloads_test.go`, new:
  - Three workloads on the fault layer's disk, each making its commits with
    `Update`: 8 commits on a new database, the same with a compaction by the
    same DB after commit 4, and the same with a compaction by another DB on
    the file, after which the first DB's next Update finds the compacted
    file at the path and reads it. A compaction goes through a DB's own log
    and copy (`CompactThroughTheDB`), as `Compact` will in G5.
  - A state is the copy's snapshot as text, with each record's vector from
    `Get` and its links both ways from `Neighbours` beside its put
    (`StateOf`). A commit tells the driver its state from inside Update's
    function, from the transaction (`TxState`). Reopen opens a DB, reads its
    copy as every read through a DB reads it, following the file first
    (`ReadState`), and needs `Check` to find nothing.
  - `TestThePackagePassesACutAtEveryWrite`, `TestThePackageAfterAFailedCall`
    (once, and on a disk that dies) and `TestCopiesThroughThePackage`
    (whole, and 100 bytes a read).
  - `TestACommitAfterAStuckCompactionLasts`, skipped: the first finding
    under the result.
- **The log's crash suite with the store,** in
  `beta/internal/logfile/crash_test.go`: Reopen opens the database with the
  store as the log's Target (`openDB`, as the compaction tests do), and a
  state is the copy's snapshot as text (`dump`). A file's first batch makes
  the table first (`crashBatchAt`), as a writer's first put does, so the
  store takes every batch.
- **The harness through the public package,** in
  `beta/internal/procs/via_package_test.go`, new: the workloads `packaged`
  and `packagedCompacting`. Writers and readers open the database with
  `hypercrux.Open` and go through nothing else.
  - Commit n, its place in the log, which the writer reads from a counter
    inside its Update, puts a record with the commit's text and a vector
    made from the text, links it to commit n-1 and to one of ten anchors,
    puts a scratch record, deletes the one from 20 commits before at each
    multiple of 7, and moves the counter. So each commit touches every
    handle, as 0.x's KilledWritersNeverLeaveAMess has its writer do.
  - Readers read with `Scan`, `Get`, `Neighbours` and `Check`. At every read
    they check that the newest commit has its vector and its links, that the
    scratch records match the newest of them, and that Check's counts add
    up, each check from one call, which reads one point in the log.
  - `Final`, `Backup` and `Restore` hold the write lock through an Update of
    their own, and Final checks every commit in the file whole. Writers of
    `packagedCompacting` compact after about one commit in 16, through the
    log, since `Compact` is a stub until G5.
  - `TestKilledWritersThroughThePackage`, the 200 SIGKILLs, and
    `TestManyProcessesThroughThePackage`.
- **The harness's runs on the real log with the store,** in `real_test.go`
  and `follow_test.go`: writers commit through a copy in the store
  (`copyOf`, from F9), and readers, followers and Final have the store as
  the log's Target (`readerTarget`). Each tells the harness what the copy
  holds of a commit once its batch has gone in, read back from the copy.
- **The harness,** added to with nothing taken away: `Options.KilledUnderWay`,
  how many writers a run has to kill with a commit under way before it
  ends, and `Report.KilledUnderWay`. One planted bug,
  `procs/killed-under-way-ignored`, with its line in `beta/plants.txt`.
- **Opening,** in `beta/hypercrux/opening_test.go`, new:
  `BenchmarkOpenFile_100k_384dims`, which times Open and one Get as
  beta/bench's `Open_100k_384dims` does, from the log of 20 commits that
  beta/bench builds (`log`) and from that log compacted (`compacted`). With
  `HYPERCRUX_OPEN_DIR` set, the files are built there once and kept, so a
  profile times the opens alone.
- **The batched put,** in `convert` in `beta/hypercrux/records.go`:
  `vectorValue`, for a `Vector` or a `[]float32` in the vector field. Its
  tests are in `vector_value_test.go`, new: `TestAVectorValueIsFromGos`,
  `TestAVectorBufferUsedAgainInAnUpdate` and `BenchmarkVectorValue`. A
  planted bug in it, `hypercrux/vector-bits-shared`, waits for its name in
  `hypercrux/plant_on.go` (Notes).

## The result

- **Crashes through the public package,** in full, on this two-core
  machine with two other agents at work. After every point the DB opened at
  the last commit that succeeded or one begun after it, its copy holding
  that commit's state exactly and Check finding nothing, and after a second
  power cut at that state or a later one:

  | Workload | Calls a run | Cuts, 48 seeds | Failures once, and on a disk that dies, 8 seeds | Copies whole, and 100 bytes a read, 2 seeds |
  |---|---|---|---|---|
  | 8 commits on a new database | 86 | 1,008 | 688 and 688 | 154 and 154 |
  | a compaction by the same DB after commit 4 | 105 | 1,248 | 840 and 840 | 192 and 192 |
  | a compaction by another DB after commit 4 | 133 | 1,248 | 1,064 and 1,064 | 248 and 248 |

  Opens at the last commit that succeeded and at a later one both came up
  under cuts and copies. With one call failing, no open found a commit
  begun after the last that succeeded, so every failed commit was cut back
  out of the file. On a disk that dies, 384 opens in each workload found a
  stuck DB's failed batch, which the next process marked.
- **Two findings,** both in code outside I1's area:
  - **A commit after a stuck compaction can be lost.** When a compaction's
    folder sync fails after its rename, its Log is stuck until Close, as
    BETA.md says. Once it's closed, another DB commits into the compacted
    file and Update returns nil, but the rename may never have reached the
    drive, and a power cut can put the old file back without the commit.
    `TestACommitAfterAStuckCompactionLasts` shows it: with its skip taken
    out, 19 seeds of 40 lost the commit. The workloads keep a stuck DB open
    to the end of the run, as BETA.md has a stuck handle do. Notes has a fix
    for the log.
  - **Update can fail after its commit has succeeded.** When only flock's
    unlock fails, the commit is in the file and in the copy, and Update
    returns "letting go of the write lock after the Update failed". A caller
    would take the commit for a failed one and might make it again. The
    workloads settle such a commit from the copy, which keeps a commit only
    once Append has written, synced and marked it.
- **The log's crash suite with the store** passes as before, each state read
  from the copy: in full, 4,448 cuts in six workloads, 8,496 failures in
  five and 200 copies.
- **The 200 SIGKILLs through the public API.** `TestKilledWritersThroughThePackage`
  runs a writer committing with Update, killed with SIGKILL at a random
  moment in a life of 10 to 100 milliseconds and started again, and a
  reader through `hypercrux.Open`, until 200 writers have been killed with a
  commit under way. In full it took 28 seconds: 447 writers killed, 200 of
  them in the middle of a commit, and 74 of those commits in the file at the
  end, killed once their batch was written; 3,169 commits begun, 2,969 seen
  to succeed and 3,043 in the file at the end. The file held every commit a
  writer saw succeed, and every commit under way at a kill whole, with its
  vector, its links and its delete, or not at all. The reader found every
  commit whole at each of its 3,388 reads. With `-short`, 20 kills in about
  4 seconds.
- **KilledWritersNeverLeaveAMess waits for G4.** With its line taken out of
  betax's `later`, it fails at its first check, a `db.Query`, with "SQL is
  an unsupported operation in the Beta until task G4". Its line stays.
- **Many processes through the public API.** `TestManyProcessesThroughThePackage`
  in full: 2 seconds, 28 writers and 8 readers killed, 381 commits begun,
  370 seen to succeed, 26 compactions, 6 backups moved into place, which
  lost 170 commits of the files they replaced, and 206 commits in the file
  at the end. Every reader saw every commit once and in order in each era,
  the readers agreed with each other and with each era's file, and a
  reader read a backup of a later era 18 times.
- **The harness's runs on the real log with the store** pass as before.
  With `-short`, T4's run made 304 commits and its readers saw 2,122, and
  in F6's, followers marked 6 batches that killed writers left, into their
  copies.
- **Planted bugs.** `procs/killed-under-way-ignored` is caught by
  `TestKilledWritersThroughThePackage`, which ends at its 10 seconds with 96
  writers killed in a commit, short of 200. `hypercrux/vector-bits-shared`,
  with its name put into `plant_on.go` by hand for the trial and taken out
  again, is caught by both of `vector_value_test.go`'s tests: the reopen
  read the buffer's last vector for every record. The crash suites through
  the public package catch, by themselves with `-short`, 10 of 17 bugs that
  other tasks planted in commits, recovery, compaction and the store:
  `logfile/cut-what-counts`, `logfile/sync-without-rewrite`,
  `logfile/marker-before-sync`, `logfile/compact-no-folder-sync`,
  `logfile/compact-rename-before-sync`, `logfile/compact-folder-sync-ignored`,
  `logfile/stuck-lets-go`, `hypercrux/append-error-dropped`,
  `store/undo-oldest-first` and `store/snapshot-no-vectors`. The other seven
  need a batch the store refuses, which no crash makes, or a case their own
  tests set up.
- **Opening 100,000 records,** timed here while the machine was quiet, load
  under 1, `-benchtime 5x -count 3`: 769 ms from the log of 20 commits and
  638 ms from the compacted file, the middle of three runs each, against
  250 ms. Where the time goes, from CPU profiles of 10 opens of each, per
  open, on the goroutine that opens:

  | Where | Log of 20 commits | Compacted |
  |---|---|---|
  | Reading the file through the log's window | 74 ms | 35 ms |
  | The codec: CRC32C | 23 ms | 14 ms |
  | The codec: each batch copied into a string | 161 ms | 106 ms |
  | The codec: the changes decoded and checked, the vectors' check among them | 135 ms (57) | 125 ms (41) |
  | The store: the vectors decoded and their norms | 129 ms | 116 ms |
  | The store: the vector arrays' fresh blocks, and the copy into them | 92 ms | 105 ms |
  | The store: records, keys, fields and the hash table | 155 ms | 129 ms |
  | The store: the rules a put checks again, and applying each change | about 50 ms | about 45 ms |
  | In all | 820 ms | 679 ms |

  The garbage collector took 162 and 144 ms of processor time more per
  open, on the other core. The log's batches of 7.8 MB cost more than the
  compacted file's of about a megabyte: the window grows to each batch and
  is let go after it, and each string copy touches fresh memory.
  - **V2 should run.** Vectors account for about 390 ms of the compacted
    file's 679. Vector blocks read straight into the arrays would save the
    batch copy of their bytes, the codec's check, the store's decode and
    copy, and most of the window's reads, about 270 ms, and would add one
    read into the arrays' fresh blocks, about 30 ms, which those blocks pay
    for however the vectors come. The norms would still be worked out, 38
    ms, unless the format kept them. So vector blocks take about 240 ms off,
    and a compacted file would open in about 440 ms here.
  - **What else opening needs.** That's still nearly twice the target.
    Without the vectors, 100,000 records take about 250 ms of their own:
    each goes through the general put path, with its rules checked again,
    its key inserted where a compacted part gives keys in order, the hash
    table grown by doubling, and each field's place looked up by its folded
    name. A load of a compacted part that appends keys, sizes the hash
    table once and leaves out the checks the codec has made would cut most
    of it, and decoding straight from the read buffer would save the rest
    of the batch copies, since the store copies what it keeps. With V2's
    done-when, "the open target is met", V2 needs those too, or BETA.md's
    target needs another look. The coordinator's recorded run gives the
    figure that decides.
- **The batched put.** Timed with the binaries in turn, four rounds of
  50,000 puts on a machine two other agents were using: 17.7 to 23.1 µs a
  put before, and 16.5 to 19.4 µs after, each round's run after the change
  under the run before it, about a fifth less. `vectorValue` alone takes
  1.83 µs and one allocation of 1,536 bytes for 384 values, where
  `value.FromGo` took 3.73 µs and three allocations of 3,096 bytes. A

  gave 339 to 445 µs before and 394 to 425 µs after, within the sync's
  spread.
- **Times,** with two other agents at work: the new suites take about 8
  seconds with `-short`, and about 55 in full, 28 of them the 200 kills and
  20 to 26 the crash suites through the public package. `hypercrux`'s
  tests take 84 seconds in full and 41 under `-race -short`, `procs`'s 42

## Decisions settled

- **Where the suites live.** The crash suites through the public package
  are external tests in beta/hypercrux, in a file that sorts after the
  package's others, with no `t.Parallel`. Go runs a package's internal tests
  first, and a test paused by `t.Parallel` runs even after `-failfast` has
  seen a failure, so either way the suites would have added about 20
  seconds to the run of each of hypercrux's 26 planted bugs. They need three
  hooks from inside the package, in `export_workloads_test.go`. In procs,
  `via_package_test.go` sorts after `toy_test.go` for the same reason: the
  toy log's planted bugs fail their runs before the 28-second kill test.
- **A state is the whole copy as text.** The snapshot holds every table
  with its vector size and its fields in order, every record with every
  value's bits, and every link. Each record's vector and links are read
  again beside it, with Get and Neighbours, since a compaction writes the
  snapshot, so a snapshot that dropped something would drop it from both
  sides of the comparison. With them, `store/snapshot-no-vectors` is caught.
- **A commit that Update reports as failed counts as done when the copy
  holds it,** since the copy keeps a commit only once Append has written,
  synced and marked it. Without that, a failed unlock would have looked
  like a commit the file shouldn't hold.
- **A stuck DB stays open to the end of the run,** keeping the write lock,
  as BETA.md has a stuck handle do. Closing it at once shows the first
  finding, which is the log's to fix.
- **"In the middle of Update"** is a kill between a commit's Begin and its
  end. Begin comes once the Update holds the write lock and has read the
  counter, and the end once Update has returned, so the span covers the
  changes, the batch's write, the sync and the marker. Each Update takes up
  to a millisecond over its changes, as one that works something out would.
  The kill test has one writer, so no writer waits for another's lock, and
  45 per cent of kills landed in a commit. It counts those, and asks for
  200 of them, where 0.x's test counts every kill.
- **Compaction until G5.** In the harness a writer compacts through a Log
  of its own on the file, and in the crash suites through the DB's own log
  and copy, which is how G5's `Compact` can go.
- **The batched put, in `convert` alone.** `tx.Put` calls `convert` and then
  the store's Put, and isn't I1's, so the store can't be handed the
  `[]float32` this round, and the log calls the codec's encoder, so a
  trusting encoder can't be wired in either (Notes). `vectorValue` does
  what `value.FromGo` did for a vector in one pass: it writes each value's
  bits as it adds up the squares in four running sums, which is the whole
  check, as the store's `checkVector` has it, and calls `rules.Vector` only
  to say what's wrong. The value shares the buffer the bits went into,
  through `unsafe.String`, which nothing else holds, as a `strings.Builder`
  shares its buffer. The bits are little-endian by `binary.LittleEndian`,
  so nothing depends on the processor. Other types still go through
  `value.FromGo`.
- **Opening's benchmark is in hypercrux's tests,** since beta/bench mirrors
  0.1's benchmarks one for one. It compacts a copy of the log as G5's
  Compact will, so the target's file is timed now.

## Notes for later tasks

- **V2:** the target and the shares are above. `BenchmarkOpenFile_100k_384dims/compacted`
  is the measure, and `HYPERCRUX_OPEN_DIR` keeps its files for a profile:
  `go test -run '^$' -bench 'OpenFile_100k_384dims/compacted' -benchtime 10x -cpuprofile cpu.out ./beta/hypercrux`.
  Vector blocks alone leave about 440 ms here, so the records' load path
  and the batch copies belong in V2's plan too, or the target changes.
- **G5:** `CompactThroughTheDB` in `export_workloads_test.go` is the shape of
  `Compact`: the log's Lock, the compaction from a read of the copy, then
  Unlock. Once `Compact` works, the crash workloads can call it in its
  place, `packagedCompacting`'s writers can call `db.Compact()` in place of
  `compactThroughTheLog`, and beta/bench's fixture compacts by itself.
- **G4:** take `KilledWritersNeverLeaveAMess` out of betax's `later` once
  `Query` works.
- **G7:** the crash suites' Reopen and the harness's readers and Final need
  `Check` to find nothing, so once Check checks, it runs after every crash
  point and at every read.
- **R1, long runs:** `HYPERCRUX_CRASH_SEEDS` raises the seeds of the crash
  suites through the public package, and `HYPERCRUX_PROCS_TIME` lengthens
  `TestManyProcessesThroughThePackage`. The kill test takes its count of
  kills from the numbers at its top.
- **The log:** a commit after a stuck compaction has closed can be lost at
  a power cut (the first finding). A fix: before its first commit into a
  file of generation 2 or more, a Log syncs the database's folder once, so
  the name the commit relies on is on the drive however the compaction that
  made the file ended. That costs one folder sync for each process after
  each compaction. Then `TestACommitAfterAStuckCompactionLasts` loses its
  skip. BETA.md, "Compaction", could say, after "no process can write until
  it closes the database": "The next writer in each process syncs the
  folder before its first commit into the new file, so its commits last
  however the folder's sync went."
- **The public package:** when only flock's unlock fails after a commit,
  Update returns an error that says the Update failed, where the commit is
  in the file. It could return nil, or an error that says the commit
  succeeded.
- **The batched put:** what's left of F7's note needs code outside I1's
  area: the store's put taking a `[]float32` beside the fields needs
  `tx.Put` to call it, and an encoder that trusts the store's checks, a new
  function in `format`, needs the log's Append to call it, for commits and
  for compaction (F8.md's note).
- **The coordinator:**
  - `beta/hypercrux/plant_on.go` could add `hypercrux/vector-bits-shared` to
    its list, with the comment: "hypercrux/vector-bits-shared: a Vector put
    in the vector field becomes a value that shares the caller's memory, so
    a caller that fills the same buffer again before the commit changes
    what the batch holds, and the file differs from the copy." Then
    `beta/plants.txt` gets the line `hypercrux/vector-bits-shared ./beta/hypercrux`.
  - `beta/plants.txt` has one new line, `procs/killed-under-way-ignored`.
    The planted job's first run, every package with the tag and no bug,
    takes about 50 seconds more, the full kill test and the crash suites
    through the public package, and the new bug's run about 25 seconds.
  - `beta/README.md`'s line for `internal/procs/` could add: "Runs can
    insist on writers killed in the middle of a commit. Its tests run the
    public package under it: the 200 SIGKILLs, and writers and readers
    through compactions and backups." The line for `hypercrux/` could add:
    "Its tests drive the crash-point driver through it, on the fault layer,
    and time opening a compacted file."
  - No interface in P3's table changed. The harness gains
    `Options.KilledUnderWay` and `Report.KilledUnderWay`. Nothing in
