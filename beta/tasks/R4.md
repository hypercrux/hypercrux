# R4: Release run

Status: built, 15 October 2026. The release goes out once the dry run and the overnight run pass, and the coordinator adds what they found.

## The contract

From BETA.md: release run: static Linux builds for amd64 and arm64 with
smoke tests, a last overnight run, tests and benchmarks recorded beside
0.1's. Done when a dry run passes and the results are written; then raising
the version publishes the release.

R4 ran alone, as the owner chose on 13 October 2026, after R3. On 15 October
2026 the owner said to carry on with it and left the Beta's version to the
coordinator, which chose 0.3.0-beta.1, published as a pre-release (BETA.md,
"Decisions"). R4 changed no Go code apart from `Version` in the release
commit and two comments, on `Version` and on `FormatVersion`, which the
coordinator allowed after the review, and no byte of the format: the
released format is version 1.

## What was built

In the code repository, github.com/hypercrux/hypercrux, on branch `beta-r4`:

- **[.github/workflows/release.yml](../../.github/workflows/release.yml),**
  the workflow that releases 0.x, now releases the Beta too:
  - **When.** It follows a finished `test` or `beta` run on main
    (`workflows: [test, beta]`). Two plan jobs decide, one for each engine,
    so a fault in one engine's version can't hold up the other's release.
    `plan` is 0.x's, after `test` alone, as before. `beta-plan` is the
    Beta's, with `actions: read` on that job alone: after a passing push run
    of either workflow on the commit main is at now, it reads the other
    workflow's runs, and the Beta releases once both have passed, from the
    run that follows the later of the two. Each plan step first checks that
    the commit has `scripts/release-plan.py`: a late or repeated run of a
    commit from before it gets a notice and releases nothing, as main has
    moved on from it, and the run stays green.
  - **0.x's path** keeps its jobs, its files, their names and its notes.
    Its release job takes 0.x's artifacts alone (`pattern: hypercrux_*`),
    since the Beta's can be in the same run and would change SHA256SUMS.
  - **The Beta's builds,** `beta-linux`, a matrix of linux/amd64 on
    `ubuntu-latest` and linux/arm64 on `ubuntu-24.04-arm`, with
    `fail-fast: false` so a dry run shows both:
    `CGO_ENABLED=0 go build -trimpath -ldflags '-s -w'` of
    `./beta/cmd/hypercrux`, then the checks on the machine that built it, a
    notice each: `file` has to say statically linked and the architecture,
    `hypercrux version` has to name the version, and `scripts/smoke.sh` has
    to pass. Then the archive.
  - **Publishing,** `beta-release`, after both builds: SHA256SUMS and the
    notes, then `gh release create --target <commit> --prerelease
    --latest=false`, titled "HyperCrux vX.Y.Z-beta.N", with `contents: write`
    and a `concurrency` group per tag, as 0.x's has. On a release published
    by hand or a rebuild, it attaches the files, and writes the notes if the
    release has none.
  - **Keeping a Beta release a pre-release,** `beta-prerelease`, for a
    release published by hand or a rebuild alone: straight after the plan,
    whatever the builds then do, it makes that release a pre-release if it
    isn't one, with `gh release edit --prerelease --latest=false`, and says
    which in a notice. It and `beta-release` are the Beta's only jobs with
    `contents: write`.
  - **The dry run,** `beta-dry-run`, in place of `beta-release`: SHA256SUMS
    and the notes as the release would have them, uploaded beside the two
    archives as the run's artifacts, with notices for SHA256SUMS, the title
    and tag the release would have, and the notes. The job has the
    workflow's `contents: read` alone, so it can't tag or publish.
  - **The paths by hand:** a release published by hand, or a run by hand
    with `tag`, builds that tag's engine, the Beta's for a tag with `-beta.`
    in it. `tag` is no longer required, since a run by hand takes `tag` or
    `dry_run`.

**The review.** A separate agent reviewed the release workflow and found
nothing that blocks the release. The coordinator sent its points and four
of its own, and each is fixed, in a commit on `beta-r4` after the first,
with the release commit rebased on top:

1. *A Beta release published by hand as a full release could stay the
   latest,* since the step that made it a pre-release ran only once both
   builds and every check had passed. It's a job of its own now,
   `beta-prerelease`, which needs `beta-plan` alone, runs for `mode` attach,
   has `contents: write` to itself, and makes the release a pre-release
   straight after the plan, whatever the builds then do, with a notice. The
   step is gone from `beta-release`, and RELEASING.md says what the job does.
2. *RELEASING.md advised running a failed release run's failed jobs again,*
   which keeps the plans' first answers and checks nothing. It now says to
   run the whole run again (`.../actions/runs/<id>/rerun`), which runs the
   plans again, and that running the failed jobs alone keeps their first
   answer. Its dry run passes when the jobs that run are green, and it names
   the ones skipped.
3. *A push that raises both versions could release the Beta's first,* such
   as 0.x's 0.3.0 with the Beta's 0.3.0-beta.2 when `beta` finishes first.
   The Beta's plan reads 0.x's `Version` in `hypercrux.go` at the same
   commit, and refuses a version whose X.Y.Z isn't above it. A 0.x version
   that 0.x's plan refuses is left to that plan, so a fault in 0.x's can't
   hold up the Beta's. The release, the dry run and the script each have a
   case.
4. *The comment on `Version` said raising it releases nothing,* which stops
   being true once `beta-r4` is on main. It's written for main as it will be
   now, and the release commit writes it again for 0.3.0-beta.1.
5. *A late or repeated `test` or `beta` run of a commit from before R4*
   would fail both plans on the missing script. Each plan step checks for
   `scripts/release-plan.py` first, and without it gives a notice that the
   commit predates the plan script, so nothing is released, writes no
   outputs, and stays green, as the inline plan did for any commit main had
   moved on from.
6. *Cases:* `passed()`'s branch filter alone and its event filter alone, a
   workflow no release waits for, and an empty release tag.
7. *beta/FORMAT.md's third paragraph,* on `beta-r4-release`, says its two
   changes before the release in plain sentences.
8. *beta/README.md's paragraph after the speed table* is wrapped at 76
   columns again, with the paragraph after it.
9. *`scripts/release-plan-test.py` left two files open,* which printed
   ResourceWarnings. It closes them, and so does `release-plan.py`'s
   `read_version`.
10. *This record* has the review, the new job and the advice on running a
    run again, in the coordinator's steps too.

## Decisions settled

**The version: 0.3.0-beta.1, as a pre-release,** settled before the round
by the coordinator, for BETA.md's reasons. The tag `v0.3.0-beta.1` is a
version of the whole module, so a Go program gets the Beta with
`go get github.com/hypercrux/hypercrux/beta/hypercrux@v0.3.0-beta.1`, and
later releases go up as 0.3.0-beta.2 and on. Nothing moves out of `beta/`.

**Two plans, one for each engine.** One plan job for both would stop both
releases in a run when one engine's version fails the plan, so the Beta
could hold up a fix to 0.x. Two jobs keep them apart, and only the Beta's
needs `actions: read`. Both run
`scripts/release-plan.py`, which holds 0.x's rules as the inline script had
them, apart from three small things: a version or tag with an empty part or
a leading zero is malformed now, where `sort -V` ordered it loosely; a
failure to read main's head fails the plan, where the inline script took it
as main having moved on and released nothing without a word; and a tag with
a space or a line feed in it is refused, where it would have gone into
`GITHUB_OUTPUT` as it was. Every version 0.x has used passes as before.

**What the Beta waits for.** The run that finished is trusted from the
event, as 0.x's plan trusts it, and the other workflow is read from the
REST API: its latest run for a push of the same commit to main in this
repository has to have finished with success. A rerun keeps its run's id,
so a failed run that passes when it's run again counts, and so does a newer
run after a failed one. If both finish at once and both plans see the other
passed, both build, and the release job's `concurrency` group and its check
for a release already out publish it once. A release run that fails for a
reason outside the repository runs again whole, which asks the plans again;
running its failed jobs alone keeps their first answer.

**The version's form and order.** X.Y.Z-beta.N, with no part starting with
0 and N from 1, so every tag reads one way. It has to be above the newest
`vX.Y.Z-beta.N` tag, and its X.Y.Z above the newest 0.x tag, so 0.2.0-beta.1
is refused while 0.2.0 is out, since Go orders it below 0.2.0. Its X.Y.Z has
to be above 0.x's `Version` at the same commit as well, so a push that
raises both can't put the Beta's out ahead of a 0.x release that Go orders
after it, whichever workflow finishes first.

**The dry run rehearses a version.** `dry_run` takes the version to
rehearse, such as 0.3.0-beta.1, and keeps the release's rules for it, so the
dry run checks the plan against the real tags too. Main says 0.0.0-beta
until the release commit, so each build sets `Version` to the rehearsed
version in its own checkout, and nothing else, and says so in a notice. The
binaries, the version line, the notes, the title and the tag are then the
release's own, from main as it is otherwise. A dry run of main as it stood,
0.0.0-beta, would rehearse nothing the release does: its notes would name a
tag that can't exist.

**The files.** `hypercrux-beta_linux_amd64.tar.gz`,
`hypercrux-beta_linux_arm64.tar.gz` and SHA256SUMS, with no version in the
names, as 0.x's. Each archive holds `hypercrux`, LICENSE, NOTICE,
THIRD_PARTY_LICENSES.md and beta/README.md as README.md. The Beta's binary
holds no module but HyperCrux's, as `go version -m` shows, so its notices
are the Go runtime's alone: the script makes NOTICE and
THIRD_PARTY_LICENSES.md from the root's, leaving out go-sqlite3 and SQLite,
and refuses a binary that holds any other module, so a new dependency can't
go out without its licence. The archive's own folder entry is 0755, since
tar can give it to the folder it unpacks in.

**A pre-release that never takes the latest.** `--prerelease --latest=false`
on create. A Beta release published by hand by mistake as a full release
would become the latest, and the site's download links, which follow the
latest, would lose 0.x's files. So `beta-prerelease` makes it a pre-release
in a job of its own, straight after the plan, where a build or a check that
fails can't stop it.

**A commit from before the plan script releases nothing,** with a notice
and a green run. Main has moved on from every such commit, so the inline
plan released nothing for them either.

**The Beta's builds don't fail fast,** so a dry run reports both
architectures. 0.x's matrix is as it was.

**The recorded fuzzing takes every target,** through `scripts/fuzz.sh`, the
export format's two with the Beta's four, since the Beta's binary holds the
export reader too (`go list -deps ./beta/cmd/hypercrux`), and the tested post
counts the six.

**The release post's date** is 15 October 2026, the day the release is
meant to go out. If it goes out later, the date moves with it.
