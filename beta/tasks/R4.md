Status: next, alone in its round, as the owner chose on 13 October 2026.
Planned at 2 hours. It needs R1, R2, R3, T5, C1 and L1, which are done. On

## The contract

From BETA.md: release run: static Linux builds for amd64 and arm64 with
smoke tests, a last overnight run, tests and benchmarks recorded beside
0.1's. Done when a dry run passes and the results are written; then raising
the version publishes the release.

## What's there already

- **The release workflow,** `.github/workflows/release.yml`, which A2 set
  up and RELEASING.md explains. When the `test` workflow passes on main and
  `Version` in the root's `hypercrux.go` has no tag yet, it builds and
  checks 0.x's binaries, then tags the commit and publishes "HyperCrux
  vX.Y.Z" with them. It reads nothing in `beta/`, so the Beta's `Version`,
  `0.0.0-beta`, releases nothing. A2.md and BETA.md say the same workflow
  publishes the Beta's release once its version is raised.
- **What the Beta's release waits for:** the `test` and `beta` workflows,
  both passing on the same commit (P1.md). 0.x's releases keep waiting for
  `test` alone, so a slow Beta job can't hold up a fix to 0.x.
- **The binary:** `go build ./beta/cmd/hypercrux` builds with
  `CGO_ENABLED=0`, and `scripts/smoke.sh` passes against it (G5.md).
- **The site's download page** links to `releases/latest/download/...`,
  which gives the files of the newest full release, 0.x's.
- **The overnight run:** the long workflow (R1), started by the coordinator
  on 15 October 2026 at 06:11 UTC on main at `9096d53`, the code R4
  releases, with the lengths in R1.md's notes: `minutes` 355, `fuzz_time`
  105m, `procs_time` 63m, `crash_seeds` 4800 and `diff_sequences` 1000000.
- **The recorded results:** 0.1's in `test/results/` (`tests.txt`,
  `race.txt`, `fuzz.txt` and `bench.txt`, from `scripts/record-tests.sh`),
  and both engines' benchmarks in `test/results/beta-bench.txt` (T5's
  script), recorded by the coordinator on 15 October 2026 at `9096d53`,
  with nothing else running. These are the release's figures.
- **That run's machine** is slower at reading memory than the machines of
  the earlier recorded runs: a search among 100,000 vectors of 384 values
  took 58.7 ms, against 29 ms in the run after L1, and the batched put
  16.1 µs, the middle of 25.3, 16.1 and 12.9, against 9.28. The code isn't
  the cause. On the same machine that morning, the code of 8 and 14
  October searched 100,000 vectors in about 58 ms too, five more runs of
  the batched put took 9.7 to 16.1 µs, and three at L1's commit 8.9 to
  15.8. A plain loop of eight sums read 154 MB of floats there at about
  4 GB/s, and 15 MB, which stays in the cache, at about 5.8. 0.x ran on
  the same machine in the same run.
- **The docs:** R3.md lists every place that says the Beta hasn't been
  released, gives `0.0.0-beta` or sends a Go program to `@main`.

## Settled before the round

- **The version:** 0.3.0-beta.1, published as a pre-release, for the
  reasons under "Decisions" in BETA.md. The tag, `v0.3.0-beta.1`, is a
  version of the whole module, so a Go program gets the Beta with
  `go get github.com/hypercrux/hypercrux/beta/hypercrux@v0.3.0-beta.1`.
  Later releases of the Beta go up as 0.3.0-beta.2 and on.
- **Where the Beta lives:** `beta/`, beside 0.x, which stays the stable
  line. Nothing moves in R4.
- **The order:** the round builds the release's path and a dry run, the
  coordinator records the Beta's tests and the overnight run, and the
  version goes up only once the dry run and the overnight run pass.
