# F9: Reloading

Status: done, 8 October 2026.

## The contract

From BETA.md: reloading: a process that finds a different file at the path
reloads it, and a leftover `NAME.compact` goes after the inode check. Done
when T4 shows every reader seeing every commit in order through
compactions and a backup moved into place.

F8 removed the leftover `NAME.compact` after the inode check, so the work
here was the reload, and joining following and reloading to the public
package's reads.

## Decisions settled

**The log's API** gains two things, and takes nothing away.

| Call | What it does |
|---|---|
| `(*Log) Reload() error` | when another file has taken the path, or the Log holds none, reads the file at the path from its start as Open does, holding fol and the mutex; otherwise reads nothing |
| `Reloader`, a `Target` with `Loaded(err error)` | told once the log is done with a file it read from its start after a Reset, with the error when that failed |

- Reload keeps Follow's place in the lock order: fol, then a try at the
  mutex. When anything but a follower holds the mutex, an Update or a
  Close, Reload returns nil at once, since that would be a wait for an
  Update's function, and the Update's Lock moves to the new file itself.
  Holding fol, it makes other followers wait for it, so no read finds the
  Log half moved.
- Every place that resets the Target drops the old copy and collects
  before it reads (`drop`): Open's loop, Lock's `reopen`, `fill`, and
  Reload. The garbage collection costs a full collection of the heap after
  the Reset, which is small then.
- `Loaded` comes once for each Reset, or once for several when other files
  kept taking the path. Reload and Open call it once they've checked the
  new file; Lock calls it once it has read the new file, before it waits
  for that file's flock, so the public package holds its reads off no longer
  than the read takes. The batches after `Loaded` are the ones Lock and
  Follow read on to. An optional interface, so the Targets in the tests and
  the harness stay as they are.
- A reload that fails leaves the Log holding no file, so Follow reports
  `ErrReplaced` and the next Reload, or Lock, reads the file at the path
  again. The Target holds the batches handed to it before the failure.
- A stuck Log keeps its file and its flock until Close (F5), so its Reload
  fails with an error that wraps `errs.ErrStuck`, and reads through it fail
  while another file is at the path.

**The public package's reads.** `read` checks for `ErrClosed`, follows
(`follow`), holds the gate shared, then reads the copy inside its `Read`.

- `follow` is Follow, then Reload when Follow reports `ErrReplaced`, then
  Follow again, up to 100 turns, which only another file taking the path
  each time could use up. It runs before the store's `Read` and outside it,
  as F6.md's note asked, so a batch Follow applies never waits for the
  read's own hold on the copy.
- Reads through a `Tx` don't follow. Inside an Update's function, Follow and
  Reload return at once, the mutex being held, and the gate is never held
  alone while an Update holds the mutex, so a read there goes ahead before
  the first change and fails with `ErrInsideUpdate` after it, as before.
- With nothing new, a read costs one stat and an atomic load more than
  before, as BETA.md's target for `Get` has it, and a shared lock of the
  gate.

**The copy on a reload.** `DB.gate`, a read-write lock: a reload holds it
alone from the Target's Reset to its `Loaded`, holding the log's mutex, and a
read holds it shared around its look at the copy and nothing else.

- Reset waits for the reads under way, which finish on the old copy, and
  holds new ones off, then puts an empty copy in place. Nothing else keeps
  the old copy then, so the log's collection takes it.
- The order: the log's fol, mutex and flock, then the gate, then the copy's
  locks. A read takes the gate only after following, and nothing that holds
  the gate shared takes the log's locks, so a reload never waits for a read
  that waits for it. The gate was chosen over locks on the new store, which
  can't wait for the reads under way on the old one.
- While the gate is held, batches go straight in (`LoadBatch`), as on
  opening, since no read can reach the new copy. A transaction a batch, as
  `ApplyBatch` makes it, would keep each batch whole when the copy refuses
  it, at a cost measured on 20,400 records with 384-value vectors in 34
  batches of 600: 49 milliseconds and 41 MB allocated straight in, 62 and
  61 MB through a transaction each, so a reload would take about a quarter
  longer than Open.
- So after a reload that failed, the copy is as the batches handed over
  before the failure left it, and when the copy refused a batch, part of
  that batch can be in it. No read sees it: `DB.unread` holds the reload's
  error, which every read gives until a reload works, and an Update's Lock
  reads the file again before its transaction begins. That covers the
  moment after an Update has taken the mutex and before its Lock has reset
  the copy, when a read finds the mutex held and would read the copy as it
  is.

**The harness's eras.**

- **Backups and restores** happen in the run's own process, as Final does,
  through the workload's `Backup(path, to, era)` and `Restore(from, path)`,
  one at a time, at random moments drawn from `Options.Restores`, while the
  run's time lasts. The backup is copied holding the write lock, so it ends
  at a commit, and marked with its era, which every compaction after carries,
  so a reader can say which era it reads. The restore holds the lock of the
  file at the path while it renames the backup over it. That keeps a
  compaction from lying between its look at the path and its rename, a
  window F8 leaves, where the compacted file would replace the backup, and
  it tells the run exactly which commits the restore loses.
- **An era begins** when its restore starts, before the rename, since a
  reader can read the new file, and report it, before the workload's Restore
  returns.
- **The checks, era by era:** a reader's places, and the first sight of
  each, are its era's; the file of each era, the one its restore replaced as
  it found it or the file at the end, holds what the readers saw there,
  begins with the era's backup, and holds the next era's backup as its
  start; no file holds a commit twice or a writer's commits out of order;
  and a commit its writer saw succeed is in the file at the end, or among the
  commits a restore lost, past the backup's in the file it replaced. A
  reader's era only moves on, and an era no restore has begun is the
  workload's fault. A run with restores makes at least 2, and its readers
  have to come to the end of the last era's file.
- **The closing test's workload** puts each commit's record under its place
  in the log, which the writer works out from its copy holding the lock, so
  a reader can work the commits out from the store's state after a
  compaction. Half the followers go through the public package, so the run
  shows its reads following and reloading too. Writers compact at random
  after a commit, about one in 16, since the public package's compaction
  waits for G5.
