# P2: File format

Status: next. Planned at 3 hours. It needs nothing.

## The contract

From BETA.md: the file format, byte by byte, with golden fixtures for the
header, each change, the batch, the marker and the compaction header. Done
when the fixtures check out with Go's CRC32C, and a review agent passes the
spec against this plan.

## What BETA.md already fixes

From its sections "Records", "The file", "Commits", "Recovery",
"Compaction" and "Keys, fields and deletes":

- **One file:** a header, then batches. Once a batch is synced, a marker
  follows it.
- **The header:** a magic number, the format version, a database ID chosen
  at random when the database is created, and the generation. A file
  written by compaction also names the batch it continues from, by
  generation, sequence number and checksum, and where its compacted part
  ends. The Beta doesn't use those last fields yet. They let a later version
  carry on after a compaction without reloading and without a format change.
- **A batch** is one commit: a magic number that's never zero, the
  generation, a length, a sequence number that follows the one before, the
  changes, and a CRC32C over all of it with the standard start and final
  values, as Go's `crc32.MakeTable(crc32.Castagnoli)` computes it. So a run
  of zeros never passes as a batch.
- **The changes:**
  - create a table, with its vector size and its fields in order;
  - put fields;
  - delete a record;
  - add or remove a link;
  - drop a table.
- **The marker** names the batch's sequence number and checksum, with a
  check value of its own, so a half-written marker never counts.
- **What recovery checks** on each batch past the last marked one: the
  magic number, the file's generation, a length that fits, a sequence number
  that follows, and a matching checksum. A header of zeros ends the log at
  once. Opening, and the check before a cut, look past the end of the log
  for a marked batch, to tell damage in the middle from a torn end.
- **Compaction** writes the current state in the same batch format. Each
  table starts with a change that creates it, with its vector size and its
  fields in order, so empty tables and vector sizes come through. Vectors go
  in as ordinary fields of their records.
- **A delete** stores only the delete. Every process works out the links to
  remove from the same state.
- **Values:** null, whole numbers, real numbers, text and bytes, plus the
  vector in the field `vec`, up to 65,536 float32 values.
- **Opening** checks every checksum and works out the vectors' norms, so
  norms aren't stored. The target is 250 ms for 100,000 records with
  384-value vectors.

## 0.x's rules the format has to carry

From `records.go`, `links.go` and `vectors.go`. S1 enforces them; the
format only has to hold whatever they allow, and its limits tell a decoder
what to refuse as damage.

- A key is `table:id`, at most 1,024 bytes (`MaxKeyLen`), clean UTF-8 with
  no NUL.
- A table name is lower-case letters, digits and underscores, starting with
  a letter, up to 63 characters.
- A field name is letters, digits and underscores, starting with a letter
  or an underscore, up to 64 characters. Names match regardless of case, and
  a put's new fields join the table in byte order of their names
  (`sort.Strings` in `records.go`), which sets the order `SELECT *` shows.
- Whole numbers are int64 and real numbers finite float64s. A vector holds
  finite float32s, at most 65,536 of them (`MaxDims`), and isn't all
  zeros.
- A link type is 1 to 200 characters of UTF-8.

## To settle, and write down in the spec

Starting points, to weigh:

- **Where the spec goes:** `beta/FORMAT.md`, since 0.x's `FORMAT.md` and
  `EXPORT.md` stay as they are. R3 makes it the Beta's `FORMAT.md`. Like
  0.x's, it should be complete enough to read a file with nothing else.
- **Byte order:** little-endian, which amd64 and arm64 both use.
- **Integers and lengths:** fixed widths for the header, the batch's own
  fields and the marker, so they're easy to check and to read in a hex
  dump. Inside the changes, varints (`encoding/binary`'s `Uvarint`) would
  make batches smaller; fixed widths decode a little faster.
- **The header:** its layout and size; a checksum of its own, which BETA.md
  doesn't mention, so a damaged header is caught; what the compaction fields
  hold in a file that was never compacted; the database ID's size, perhaps
  16 bytes from `crypto/rand`.
- **The batch:**
  - what the length counts, and the largest allowed. Counting the whole
    batch, from the magic number to the checksum, lets a reader step
    straight to the marker, and a limit keeps a damaged length from making
    a reader allocate gigabytes;
  - whether batches start on aligned offsets, so the look past a bad batch
    can step 8 bytes at a time.
- **The marker:** a magic number of its own, different from a batch's, and
  a check value, perhaps a CRC32C of the marker's other bytes. Whether it
  repeats the generation.
- **Sequence numbers:** where they start in a new file and after a
  compaction, and how the first commit after the compacted part follows on.
- **The compacted part:** whether its batches carry markers, so readers
  keep one rule, or count without them because the whole file is synced
  before the rename. And how big its batches are: bounded batches let a
  compaction of 1.6 GB stream out, where one batch would have to be built in
  memory first.
- **Each change:** a kind byte, then its contents.
  - Create a table: the name, the vector size (0 for none yet), the field
    names in order. Whether an ordinary commit writes one when a put first
    uses a table, or the put implies it. The vector size needs no change of
    its own in an ordinary commit, since the table's first vector sets it
    in the same place for every process.
  - Put fields: the key, then each field's name and value. A put that
    brings a new field has to carry its name, since no change adds a field;
    fields the table has could go by their number in its field list
    instead. A name written as the table holds it saves readers from
    matching case.
  - Delete a record: the key. Drop a table: its name. A link: from, type
    and to.
- **Values:** a tag byte, then the value. Whole numbers as int64; reals as
  float64 bits, so -0 and subnormals come back exactly; text and bytes as a
  length and the bytes, kept apart since the export tells them apart; a
  vector as a count and float32 bits. Null clears a field, as a put of nil
  does in 0.x.
- **Versions:** a reader refuses a newer format version, as 0.x refuses a
  newer `format_version`, and refuses a change kind it doesn't know.

## The fixtures

- One for each thing the contract names: a new file's header, a compaction
  header, a batch for each change, a batch holding several changes, and the
  marker. The put fixtures carry every kind of value, with awkward ones:
  -0, a subnormal, the largest and smallest whole numbers, empty text and
  bytes, text beyond ASCII, a vector.
- Written by hand from the spec, as hex with a comment on each field, so
  the spec alone decides what's right. F1's codec then has to match them
  byte for byte.
- A test reads each fixture, recomputes its checksums with `hash/crc32`'s
  Castagnoli table and compares them, and checks the lengths and magic
  numbers. It also checks CRC32C's standard check value: `0xe3069283` for
  "123456789".
- A home for them: `beta/internal/format/testdata`, with the test beside
  them, in a package F1 then fills with the codec. P3 may want another
  name, and moving them is easy.

## The review

A review agent gets BETA.md and the spec, and checks that the spec covers
everything the plan asks of the file, including recovery's checks and what
compaction and a later carry-on need, and that nothing in it contradicts the
plan. Each finding is fixed or answered in this file.
