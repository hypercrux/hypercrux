# S5: Links and walks

Status: next, in one round with T4 and F4. Planned at 4 hours. It needs S2,
S3 and S4, which are done.

## The contract

From BETA.md: links and walks: link lists, the reverse index, deletes and
drops removing links both ways, breadth-first walks by type and direction.
Done when the model test, 0.x's link and walk cases, and random graphs
against a reference walk pass.

## What's there already

- **The design,** in BETA.md under "In memory", "Keys, fields and deletes"
  and "Links": each record's links as a list of (type, target), a reverse
  index from each record to the links pointing at it, a walk as a
  breadth-first search with a visited set, and a delete or a drop that
  takes links away both ways while the file stores only the delete or the
  drop.
- **The rules for the changes,** in FORMAT.md under "Changes": a link
  needs both records and mustn't be there already; removing one needs it
  there; adding a link twice writes one change; removing every link from
  one record to another writes one remove change for each type, in byte
  order of type. The snapshot's links come after the tables, in byte order
  of the key they're from, then type, then the key they're to.
- **The read API** (P3), in `read.go`: `Neighbours` and `Walk`, with 0.x's
  order for each, and depth from 1 to 32. Both are stubs in `store.go`
  that name S5.
- **The store** (S1 to S4), in `beta/internal/store`. `Apply` refuses Link
  and Unlink until now, `remove` and the loop over a table's keys in `drop`
  are where links go (S4.md), every change has an undo entry (S2), each
  transaction gives its change list (S3), and the snapshot marks the place
  for links (S3).
- **0.x's links,** in `links.go` in the repository's root, with its checks
  and their order.
- **The public package** (G1) counts each Link change in the snapshot as a
  link in `Check`, so links show there without a change to it. Its `Link`,
  `Unlink`, `Neighbours` and `Walk` are G2's.

## To settle, and write down in this file

- **The structure** for the link lists and the reverse index: `Neighbours`
  in 0.x's order without sorting each time, a delete or a drop finding
  every link both ways, and the memory a link takes. G2 times walks at
  100,000 records with 5 links each against targets of 3 µs one link out
  and 40 µs three links out.
- **The writes:** `Tx.Link` and `Tx.Unlink` with 0.x's checks and errors in
  0.x's order, `Unlink` with an empty type taking every link from one
  record to the other, and the changes each emits. `Apply` for Link and
  Unlink, so batches from the log carry links.
- **Deletes and drops** taking links away both ways, with undo entries, so
  a rollback puts each record back before its links.
- **The reads:** `Neighbours` and `Walk` on the store and through a
  transaction, which sees its own changes.
- **The snapshot's links,** so `TestSnapshotOfTheFixtures` compares the
  compacted part's second batch too and `withoutLinks` goes.
- **The tests:** the model test with links, 0.x's link and walk cases run
  against the store and 0.x side by side as S1 and S4 did, random graphs
  against a reference walk written plainly in the test, and a rough timing
  of walks at 100,000 records with 5 links each, written down for G2.
- **Planted bugs** for links and walks, each with a line in
  `beta/plants.txt`.
