# S5: Links and walks

Status: done, 8 October 2026.

## The contract

From BETA.md: links and walks: link lists, the reverse index, deletes and
drops removing links both ways, breadth-first walks by type and direction.
Done when the model test, 0.x's link and walk cases, and random graphs
against a reference walk pass.

## What was built

- **`beta/internal/store`**, in the new `halves.go`, `links.go` and
  `walk.go`, with changes to `store.go`, `write.go`, `tx.go` and
  `snapshot.go`:
  - `links`: one record's links one way, as halves, each the link's type
    and the record at the other end, in byte order of type and then of

## Decisions settled

**The structure: two lists a record, in blocks.**

- A link from a to b of type t is two halves: (t, b) in a's links out, and
  (t, a) in b's links in. A half is 16 bytes, the type's handle and a
  pointer to the record. So a walk follows pointers and reads no hash
  table, and a delete or a drop finds every link of a record in its two
  lists.
- Each list is in byte order of type and then of the key at the other end,
  0.x's order for Neighbours out and in. Neighbours reads a list as it is,
  and both ways merges the two, since the links out all come from the
  record and the links in all go to it, so each is in order of type, from
  and to already. A link from the record to itself is in both, and comes
  once.
- A list is a list of blocks of up to 256 halves, with the rules of S4's
  blocks for a table's keys: a search over the blocks' first halves, a
  split when a full block takes another, a join below a quarter, and a
  half after every half going on the end. A record that every other record
  links to takes a link in or out in about the time a record with a few
  does. A plain sorted list would move half of a hub's links on each insert
  into the middle, and a compacted file gives the links into a hub in order
  of the key they're from, which lands in the middle of its list when
  they're of several types.
- A block grows one half at a time up to 8 halves, then doubles. Go's
  allocator has a size for every 16 bytes up to 128, so a record with a few
  links keeps no spare room. That took the measured cost from 56 bytes a
  link to 43.
- The record's lists come straight after its key, so a walk that reads a
  record's key finds the lists' headers in the same 64 bytes. The record
  grows from 72 bytes to 120, in Go's 128-byte size.
- A list that isn't empty costs one more allocation, its list of blocks,
  and a walk one more read for it. A list kept flat until it outgrows a
  block would save that read and 24 bytes, at the cost of a second path
  through every operation. The walks met their targets without it.

**Link types.** A handle from `unique.Make`, which copies the text the
first time it sees it and lets it go once no handle is left, so a type is
kept once however many links have it, and a type nobody uses any more
takes no memory. The store remembers the last type it made a handle for,
so a run of links of one type makes one call. Reads compare types by their
text, and never make a handle. The store has a function called `unique`,
so `halves.go` imports the package as `intern` and calls the handle's type
`linkType`.

**The writes.**

- `Link(from, typ, to)` checks the type with `rules.LinkType`, then `from`
  as `Get` does, by `rules.TableOf` and then for a record, then `to` the
  same way, in 0.x's order and with 0.x's messages. A link that's there
  already changes nothing and gives no change, so the log writes it once.
- `Unlink(from, typ, to)` checks nothing, as 0.x's doesn't: anything wrong
  gives 0.x's "not found: no link from docs:1 to docs:2". With `typ` "", it
  takes every link from one record to the other, found in the shorter of
  the two lists, and gives an Unlink for each, in byte order of type.
- The store's own `Link` and `Unlink` take and return a change list, as
  `Put`, `Delete` and `Drop` do, and panic while a transaction is open. The
  transaction's return only an error.
- `Apply` takes a Link when its type keeps the rules, both records exist
  and the link isn't there: a writer never adds a link twice, so a Link of
  a link that's there is `ErrInvalid`, "the link from -type-> to is added
  when it's there already". It takes an Unlink whose type and keys keep the
  rules, as the codec requires, and whose link is there, or else
  `ErrNotFound`.

**Deletes and drops.**

- A delete calls `cut` before `unhash` and `unlist`. `cut` takes each half
  that points at the record out of the list at the other end, each with an
  undo entry, `undoHadOut` or `undoHadIn`. The record's own lists stay as
  they are: nothing can reach the record once it's out of the hash table,
  and a rollback, newest first, puts the record back and then the other
  ends of its links.
- A drop calls `cut` for each of its records before `unhash`, and leaves
  alone the halves in the lists of the table's own records, so a link
  between two records of the table takes no undo entry. Only the records
  that stay lose halves.
- The change is the Delete or the Drop alone, as FORMAT.md says, and every
  store that applies it works out the same links.

**The undo kinds,** made where the lists change, in `link`, `unlink` and
`cutHalf` in `links.go`:

| Kind | Made before | Holds | Put back by |
|---|---|---|---|
| `undoNoLink` | a link added | the record it's from, the type and the record it's to | taking both halves out |
| `undoHadLink` | a link taken out by an unlink | the same | putting both halves back |
| `undoHadOut` | a half taken out of a record's links out, for a delete or a drop at its other end | the record and the half | putting the half back |
| `undoHadIn` | the same in a record's links in | the record and the half | putting the half back |

Each is put back by type and key, so a block that split or joined since
needn't be put back as it was.

**The reads.**

- `Neighbours(key, dir, typ)` checks the key as `Get` does, then the
  direction, with 0.x's message "direction 3", and doesn't check the type,
  as 0.x doesn't: a type no link has gives none. It returns nil for none,
  as 0.x does, and a list of its own otherwise.
- `Walk(key, dir, typ, depth)` checks the depth, then the direction, then
  the key, in 0.x's order. It's a breadth-first search with a set of the
  records it has seen, the start among them: each round finds the records
  one link further on that it hasn't seen, which are the ones that many
  links away, and sorts them by key. So each record comes once, with the
  fewest links it takes, and the start never comes, as 0.x's recursive
  query gives it. A type filter starts each list at the first half of the
  type, by a search.
- A walk's set of seen records and its lists come from a `sync.Pool`, so a
  walk allocates only the steps it returns. The set is a table of record
  pointers open to probing, hashed with `maphash.Comparable`, with a list
  of the slots in use, so it empties in the time it took to fill. A fresh
  Go map for each walk took most of a walk's time: 56 µs three links out,
  against 30 with the pool. The pool isn't the store's, so a read still
  changes nothing in the store, and a walker that grew past 65,536 slots
  isn't put back.
- Through a transaction, both see its changes, since they're in the copy.

**The snapshot's links** come after the tables, in byte order of the key
they're from, then type, then the key they're to. Every key of a table
starts with its name and a colon, so the tables go in order of their names
with a colon after each, which `compareAsKeys` compares without building
the strings: users2 before users, since a digit sorts before a colon. Each
table's records come in key order and each record's links out are in order
already, so nothing else is sorted.

**The planted bugs:** `store/link-added-twice`, a Link of a link that's
there; `store/unlink-one-end`, an Unlink that leaves the half at the end
the link is to; `store/unlink-types-reversed`, an Unlink of every type with
its changes in reverse order; `store/links-in-kept`, a delete or a drop
that leaves the links into its records; `store/link-undone-at-one-end`, a
rollback of a link that leaves the half at the end it's to;
`store/both-not-merged`, Neighbours both ways unmerged;
`store/walk-unsorted`, a walk's rounds in the order found;
`store/walk-start-included`, a walk that gives its start when a path leads
back; and `store/snapshot-links-by-table`, the snapshot's links in order of
table names.
