# Q1: Values and functions

Status: done, 8 October 2026.

## The contract

From BETA.md: values and functions: SQLite's comparison rules for untyped
values, arithmetic, the listed text and number functions, `LIKE`,
`BETWEEN`, `IN`, `IS NULL`. Done when A4's expression answers match
exactly.

## What was built

The evaluator is in `beta/internal/query`, beside Q3's parser, which is as
it was apart from a sentence in `Error`'s comment. SQLite's routines for
numbers are in `beta/internal/value`.

- **`eval.go`,** the compiler. `Compile(e, scope)` turns an expression from
  Parse's tree into an `Eval`, a `func(*Frame) (value.Value, error)`, once
  for each statement, and `CompileCondition` turns a condition into a
  `Cond`, as WHERE takes it. It follows SQLite's code generator as well as
  its rules for values, since the parts SQLite skips show in which error a
  statement gives. A `Frame` holds the arguments and the planner's row, and
  a `Scope` gives what the evaluator can't work out itself.
- **`values.go`,** SQL.md's "Values": each kind read as another,
  `sqlite3MemCompare`, affinity, truth, arithmetic, `||` and CAST.
- **`funcs.go`,** the text and number functions, with `coalesce()` and
  `ifnull()`. **`like.go`,** LIKE, from `likeFunc` and `patternCompare`.
  **`vectors.go`,** `distance()` and `vector()`.
- **`args.go`,** `Arg`, which makes a Go value an argument as SQL.md's
  "Arguments" table has it.
- **`beta/internal/value/sqlnum.go`,** SQLite 3.53.4's own routines, ported
  step for step: `ParseReal` is `sqlite3AtoF`, `ParseInt` is
  `sqlite3Atoi64`, `RealText` is a real's text as `vdbeMemRenderNum` writes
  it, and `RealPlaces` is round()'s `"%!.*f"`. `AppendVector`'s comment no
  longer says V1 uses it, and nothing in the package was taken away.
- **Fifteen planted bugs,** in `plant_on.go` and `beta/plants.txt`:
  `query/real-text-shortest`, `query/text-reads-as-number`,
  `query/plus-keeps-affinity`, `query/in-takes-item-affinity`,
  `query/in-list-stops-early`, `query/in-record-is-a-list`,
  `query/and-or-sees-signs`, `query/minus-zero-lost`,
  `query/div-rounds-down`, `query/nan-kept`, `query/min-keeps-earliest`,
  `query/substr-zero-is-one`, `query/like-folds-unicode`,
  `query/where-or-works-out-both` and `query/time-in-utc`.
- **Tests:**
  - `eval_corpus_test.go`: `TestTheCorpusExpressionsGive0xsAnswers`, the
    closing test.
  - `eval_test.go`: a table of cases for each part of SQL.md's "Values" and
    one for the functions, from `TestKinds` to `TestFunctions`, 634 cases in
    all, and `TestEvalsRunOnSeveralGoroutines`.
  - `cond_test.go`: `TestWhereConditions`. `scope_test.go`: the evaluator
    with a fake Scope, for fields, the vector field, the one-record
    subquery, walks, and what a nil Scope refuses. `args_test.go`:
    `TestArgumentsConvert`.
  - `eval_sqlite_test.go`, built with cgo only: the evaluator against 0.x
    through `zerox`, on random expressions, random numbers and text, the
    rule tables, Go arguments, expressions over the corpus's fixture with a

  - In `value`: `sqlnum_test.go` on fixed cases, and `sqlnum_sqlite_test.go`,

## The result

- **Every expression in the corpus gives 0.x's answer exactly:** all 3,000,
  through `Parse` and `Compile` with no Scope, reals to the bit and errors
  by kind. A4.md's note asks for `sqlcorpus.Replay` on the engine, which
  needs SQL through the driver (G4), so the closing test runs each case
  through the parser and the evaluator directly.
- **The evaluator agrees with 0.x far beyond the corpus,** with answers
  compared exactly, apart from long distances (below):

  | What | Cases |
  |---|---|
  | Random expressions with the awkward values: the ends of 64 bits, -0, 1e999, subnormals, reals with more digits than SQLite keeps, text that reads as a number or partly, text with NUL bytes or that isn't UTF-8, bytes, Unicode, and arguments of every kind | 60,000: 54 refused by the parser, 7,818 errors, and the rest values of every kind |
  | Text that reads as a number, and random reals, as arguments in each place "Text as numbers" names | 40,000 |
  | The rule tables of `eval_test.go` | 634 |
  | Go values as arguments, through database/sql | 47 |
  | Expressions over the fixture's docs table, with fields, the one-record subquery and IN over a walk, through a fake Scope over the records 0.x holds | 92 fixed and 12,000 random |
  | Conditions, as `SELECT 1 AS v WHERE`, some joined by AND | 65 fixed and 30,000 random |
  | `distance()` and `vector()` on vectors of up to 300 values, as text and as bytes | 4,000 pairs |

  Against SQLite itself, `sqlnum.go` agrees on 40,000 random reals' text,
  40,000 random texts read as a real and as an integer, and 20,000 calls
  of `round()` with places. While the evaluator was being written, other
  seeds ran 400,000 random expressions, 120,000 over the fixture, 120,000
  conditions and 500,000 inputs to the number routines, and no difference
  was left.
- **Distances** add up their dot products in 8 running sums, as the store's
  `Nearest` does (A5.md), where 0.x adds them up in one. Up to 3 values the
  bits are the same. Beyond that, the test allows
  `conformance.DistanceBound`, though most still agree to the bit: 1,749 of
  the 1,768 random ones over 8 values, whose distances are near 1.
- **The planted bugs are caught,** all fifteen, one at a time with
  `-failfast` as `scripts/planted.sh` runs them, and Q3's eleven still are.
- **Bugs found on the way,** by the random tests, each now a case in a
  table:
  - `1.5 IS NULL` is the integer 0 to SQLite's parser, which then settles an
    AND, and the folding goes on through `(1.5 IS NULL) IS NOT NULL`.
  - `x IS (y IN ())` is SQLite's `x IS FALSE`, unless y calls a function.
  - A list of three constant items or more is worked out whole, before x,
    and a single constant item makes `x IN (y)` into `x = +y`.
  - `x IN ((SELECT ...))` is IN over the subquery's rows, so no record gives
    0, even for a NULL x.
  - `sqlcorpus.Same` with `close` set takes two equal infinities as
    different, since their difference is NaN, so the tests here compare
    exactly first.
- `sh scripts/check-beta.sh`, `go vet ./...`, `go test -short ./...`,
  `go test -race` on `query` and `value`, and `query`'s tests with
  `CGO_ENABLED=0`, which leave out the cgo files, pass. The package's cgo
  tests take about 7 seconds, and 2 with `-short`.

## Decisions settled

**The evaluator's shape** (`eval.go`):

- An expression compiles once for each statement, into closures, and an
  `Eval` may run on several goroutines at once, each with a `Frame` of its
  own. `Frame.Args` holds a value for each `?`, and `Frame.Row` the
  planner's row, which only the Scope's Evals read.
- An expression without fields, subqueries, walks, aggregates or dates
  compiles with a nil Scope. Otherwise the planner's Scope gives:
  - `Column`, a field of the current row. Every field compares with
    SQLite's BLOB affinity, and the vector field may give a `KindVector`,
    which reads as bytes everywhere.
  - `Record`, the one-record subquery, given its compiled key: the field's
    value, and whether the record is there, which only
    `x IN ((SELECT ...))` needs.
  - `Walk`, the keys a walk reaches, as text, given its compiled arguments.
  - `Call`, the calls the evaluator leaves to others: the aggregates,
    `walk()`, `date()` and `datetime()`, given their compiled arguments.
- What SQLite raises as a statement runs is an `*Error`, with SQLite's
  message: "integer overflow" from `abs()`, LIKE's two errors, and "string
  or blob too big". `distance()` and `vector()` refusing their arguments is
  a `*FuncError` with 0.x's message, so a write can make it "invalid" (Q6).
  Both are of kind "error" in a SELECT.
- `Arg` is database/sql's `driver.DefaultParameterConverter`, then what
  go-sqlite3 binds, so named types, pointers and Valuers go as database/sql
  sends them. A NaN in `Frame.Args` reads as NULL as well, for a caller that
  skips `Arg`.

**SQLite's hard parts,** from P5.md's note:

- **The text of reals.** `value.RealText` is SQLite's own:
  `sqlite3FpDecode`'s decimal arithmetic with its 64-bit mantissa, then
  `%!.17g`.
- **Reading numbers.** `value.ParseReal` keeps about 19 significant digits,
  as `sqlite3AtoF` does, so a literal or text with more can read
  differently from Go's `strconv.ParseFloat`.
- **CAST's affinity in comparisons** is `sqlite3CompareAffinity` and the
  conversions of OP_Eq, with a field's BLOB affinity, a plus sign taking
  affinity away, and IN taking x's affinity only.
- **`min()` and `max()` on ties:** `max()` keeps the earliest of the tied
  arguments and `min()` the latest, as `minmaxFunc` runs.
- **Signs in front of literals:** a minus sign negates a number literal as
  written, so `-9223372036854775808` is an integer and `-0.0` keeps its
  sign. Any other minus is `0 - x`.

**What SQLite's code generator decides,** where the order shows in errors,
each checked against 0.x:

- AND and OR settle on an integer literal of 32 bits only when no sign is in
  front of it, so `-0 AND x` works out x. An empty IN list and a literal's
  IS NULL settle them too, since SQLite's parser makes those constants.
- With the one-record subquery or IN over a walk on one side of an operator,
  the other side goes first, and the subquery isn't worked out when that
  side is NULL, or settles an AND or an OR.
- `x IN (...)` with one constant item is `x = +y`. A list of three constant
  items or more is worked out whole before x. Any other list works out x,
  then the items until one equals x. IN over a walk works out the walk
  first, and so does IN over the one-record subquery.
- LIKE is the function `like(p, x, e)`: the pattern first, then x, then the
  escape. BETWEEN works out x, then low, then high.
- As a condition, as `sqlite3ExprIfFalse` codes it, AND, OR, NOT and
  BETWEEN stop once the answer is known, so `WHERE (1=1) OR E` gives no
  error where `SELECT (1=1) OR E` does.

**Where SQL.md is silent,** settled as 0.x's SQLite behaves and checked
against 0.x. The wording for SQL.md:

- "Text as numbers", after the first paragraph: "Only about the first 19
  significant digits count, as SQLite reads a number, so
  `3500000000000000.2500001` is 3500000000000000.0, where Go's
  `strconv.ParseFloat` gives 3500000000000000.5."
- "What gets worked out", in place of the AND and OR bullet: "When one side
  of AND or OR settles the result, the other side isn't worked out: an
  integer literal that fits in 32 bits with no sign in front of it, so
  `0 AND x` and `x AND 0` give 0 and `1 OR x` gives 1, where `-0 AND x`
  works out x; an empty IN list; and a literal's IS NULL or IS NOT NULL,
  which SQLite's parser makes 0 or 1. SQLite's routine is
  `sqlite3ExprSimplifiedAndOr`."
- "What gets worked out", in place of the IN bullet: "`x IN (...)` works out
  x, then the items in turn, and stops at the first that equals x. A list
  of three items or more without fields or subqueries is worked out whole,
  then x. An empty list doesn't work out x. IN over a walk or over the
  one-record subquery works out the subquery first."
- "What gets worked out", a new bullet: "When one side of a comparison, an
  arithmetic operator, `||`, AND or OR holds the one-record subquery or IN
  over a walk and the other side doesn't, the other side goes first. The
  subquery isn't worked out when that side is NULL, or when it settles an
  AND or an OR."
- "What gets worked out", a new bullet: "LIKE works out the pattern, then x,
  then the escape, and its errors come before NULL: `NULL LIKE 'a' ESCAPE
  'ab'` is an error."
- "What gets worked out", after the WHERE bullet: "AND's terms at the top of
  a WHERE are worked out in turn as written, without the rule for literals
  above, so `WHERE E AND 0` raises E's error, where `SELECT E AND 0` gives
  0."
- "IN, BETWEEN and IS", a new bullet: "`x IN ((SELECT f FROM t WHERE key =
  e))`, with the one-record subquery as the only item, is IN over the
  subquery's rows, as SQLite's parser makes it. With no such record the set
  is empty, so it gives 0 even when x is NULL. The field's affinity counts
  beside x's, so a CAST to TEXT changes nothing there."
- "IN, BETWEEN and IS", a new bullet: "`x IS (y IN ())` and
  `x IS (y NOT IN ())` are SQLite's `x IS FALSE` and `x IS TRUE`, which
  take x's truth, unless y calls a function. So `0.5 IS (1 NOT IN ())` is
  1."
- "Text and number functions": `substr(x, y [, z])` could add "Empty bytes
  give NULL". `replace(x, y, z)` could say "x as text when y is empty or
  starts with a NUL byte". `trim(x [, y])` could add "y's characters are
  those before its first NUL byte, and each is matched byte for byte, so
  part of a character can be trimmed."
- "ORDER BY", rule 2, could add: "A literal's IS NULL or IS NOT NULL is an
  integer too, 0 or 1, as SQLite's parser makes it, so `ORDER BY 1 IS NOT
  NULL` sorts by the first column and `ORDER BY 'a' IS NULL` is out of
  range."
- "Arguments", after the table: "A `uint` beyond 2^63 - 1 wraps around to a
  negative integer, as database/sql converts it, where a `uint64` that big
  is an error."

## Notes for later tasks

- **Q2, dates:** `date()` and `datetime()` reach `Scope.Call` now, with
  their compiled arguments, which are text literals. Q2 can work them out
  in `funcs.go`'s `call` instead, with the statement's 'now' in a new field
  of `Frame`, and take them off the Scope's list there. They give text,
  which compares as any text does.
- **Q4, operators:** the aggregates reach `Scope.Call` with their compiled
  arguments, so the operator's Eval can read each aggregate's result from
  `Frame.Row`. `min()` and `max()` with one argument are aggregates
  (`Call.Aggregate()`), and with more they're the evaluator's. Q4 is in the
  same package, so it can sort with `compare`, which is
  `sqlite3MemCompare`'s order, and take truth with `truth`. For `sum()`,
  `total()` and `avg()`, `numericAffinity` is `sqlite3_value_numeric_type`,
  which `sumStep` uses to make text a number, and `realOf` reads the rest
  as a real.
- **Q5, the planner:**
  - It implements `Scope`. `Column` can hand out the store's values as they
    are, the vector as a `KindVector`. `Record` and `Walk` should work out
    their subquery once for each statement, as SQL.md says, and `Record`
    reports whether the record is there.
  - WHERE: split it at its top-level ANDs, as SQLite's `whereSplit` does,
    without simplifying, and compile each term with `CompileCondition`.
    Without a FROM, 0.x works out the terms in turn; `evalWhere` in
    `cond_test.go` does the same, and `TestWhereConditionsAs0xHasThem`
    holds it to 0.x. SQLite's parser makes `x AND y` the literal 0 when
    either side settles it false and neither calls a function, before the
    split, which shows only when the one-record subquery's key raises an
    error.
  - ORDER BY: `ORDER BY 1 IS NOT NULL` is a column number to SQLite, as the
    wording above says.
  - `TestFieldsAs0xHasThem` shows a way to test the planner's Scope: a fake
    over the fixture agrees with 0.x on 12,000 random expressions.
- **Q6, writes:** a `*FuncError` in an INSERT, UPDATE or DELETE is
  "invalid", and every other error from the evaluator is "error". The
  evaluator can give text that isn't valid UTF-8, infinite reals and
  `KindVector` values, which a write checks as `Put` does.
- **G3 and G4, the driver and slice 3:** `query.Arg` makes each of the
  driver's arguments a value as SQL.md's table has it, NaN and `time.Time`
  included, and `TestArgumentsAs0xBindsThem` holds it to 0.x on 47 Go
  values. G3 converts arguments on its own in the same round, so one of the
  two can go. A result can be a `KindVector`, to hand out as a `[]byte`,
  copied. Once SQL runs through the driver, the expression corpus can go
  through `sqlcorpus.Replay`, as A4.md's note asks.
