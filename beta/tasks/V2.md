# V2: Vector blocks

Status: done, 13 October 2026.

## The contract

From BETA.md: vector blocks, only if the open target is missed: compaction
writes each table's vectors as one block, read on opening without parsing.
Done when a compaction round trip keeps every vector's bits and the open
target is met.

On 13 October 2026 the owner settled V2's scope: vector blocks alone,
knowing that opening stays above its target of 250 ms. So the closing test
is the round trip keeping every vector's bits, and the open target stays
missed. The result gives the times.

## What was built

## Decisions settled

**Where a block sits.** In the compacted part alone, after its table's puts
and before the next table's create change, the table's vectors in byte
order of key, in as many blocks as they need. Compaction is the one writer:
a commit never holds a block, so the log's `Append` and a transaction's
`Apply` refuse one, and a reader takes a block in a batch past the
compacted part, or in generation 1, which has none, for damage. Every
record a block names exists by then, and nothing after it in the compacted
part touches the vectors.

**The layout.** `V`, the table's name, the vector size (u32), the number of
vectors (u32), each record's key in byte order, then the vectors back to
back, each value an f32, little-endian as everywhere in the format. The
keys come first so that the values are one run of bytes, which a reader
copies straight into its slots. The vector size and the count come before
anything that rests on them, so the codec knows the values' length, and
holds it to the batch's length before it looks at a value.

**Which records hold a vector.** A block names each record it gives one by
its key, and leaves the rest out. A bitmap over the table's records in key
order would be smaller, a bit a record where a key takes 2 bytes and its
own length, but one wrong bit would send every vector after it to the wrong
record without a sign. With keys, each vector says whose it is, and the
store holds each to the rules: a record of the table, with no vector yet,
in byte order. Keys like `docs:12345` cost under 1% of a 384-value
vector's 1,536 bytes.

**No norms in the file.** A reader works each norm out from the values,
with the 8 sums vecmath uses everywhere, which give the same bits on amd64
and arm64, so a store that opened a compacted file holds the norms a put
gives, bit for bit. The same sum checks the values: it's finite only when
every value is, and above zero once any value isn't zero. So a reader makes
the pass anyway, and a stored norm would add 8 bytes a vector and a field
that could disagree with the values. FORMAT.md's "What isn't in the file"
lists the norms already.

**Runs near a megabyte.** A table's vectors go in a run of blocks, each
alone in its batch and filled until the next vector would take the batch's
changes past a megabyte, as compaction fills its other batches. A vector
longer than a batch's size goes in a block of its own, which can't happen
at a megabyte, since 65,536 values take 256 KB. One change for a
table's whole array would be a batch as large as the table, 154 MB for
100,000 vectors of 384 values, which the writer would build whole and the
reader read whole, where batches of a megabyte keep both flat. FORMAT.md
leaves the split to the writer: a reader takes a block in a batch with
other changes too, and decodes that batch as a copy.

**A batch of the compacted part ends at 1,024 changes too.** Taking the
vectors out of the puts packs a megabyte of puts with about 40,000 changes,
where a put with a vector of 384 values left room for about 680. A reader
decodes each batch into a list of changes, which grows as it's read, and
lists that long made the records' decoding about 100 ms slower on a
compacted open here, which took most of what the blocks saved. Ending a
batch at 1,024 changes keeps the lists about as long as before V2, and took
the open from about 621 ms to about 555 by the middle runs. It costs 98 more
batches for 100,000 records, about 5 KB of heads and markers, and changes
nothing in the format: FORMAT.md leaves the split to the writer. A commit
can still hold a long batch of puts, an import's for one, and decoding it
costs what it did.

**How a damaged block is found.** By the batch's checksum, as for any
change; by the codec's rules for a block on its own, which take in a count
that disagrees with the keys and values given, since the change then runs
past the end of the batch or leaves bytes over; by the store's rules for
the state, the values' check among them, as it applies the block; and by
the log's rule that a block goes in the compacted part alone. Each is a
`*errs.Damage` naming the batch. The codec's and the log's give an offset
in the block, and the store's the batch's, as for any change the store
refuses.

**The format version stays 1.** A build from before V2 reads a block as a
change of a kind it doesn't know, 0x56, which is damage, so it refuses a
file that holds one, and never misreads it. Every other file is the same
bytes as before, a compacted one included when its database holds no
vectors, and both builds read it. Raising the version would make every
file unreadable across the two builds, for the sake of the one change an
older build can't misread anyway. The cost is that an older build calls a
newer compacted file damaged where it could have said the format is newer.
No Beta is out yet, so no one has an older build to meet one with.
FORMAT.md's sentence that every change raises the version needs new words,
under the coordinator's notes.

**Writing.** `Compacted` walks each table's keys, which are in byte order
(S4), and takes each record's slot, so the vectors come in key order
whatever order the slots are in after a delete freed one and a put took it.
Each vector's bits are its slot's memory, handed out as a string with
package unsafe, without the copy into a `value.Vector` that `Snapshot`
makes. Compaction reads the copy inside its `Read`, so nothing changes
them meanwhile. The codec's check of a block looks at its keys and lengths
and leaves the values alone, since the store holds only vectors that kept
the rules. So a vector's one copy is the one into its batch.

**Opening, and a reload.** A batch of vector blocks alone goes to the store
straight from the log's read buffer, without the copy into a string that
every other batch gets, when the Target allows it with
`Options.BlocksInPlace`. The public package sets it, since the store copies
a block's vectors into its arrays and keeps none of its strings; a Target
that keeps its changes leaves it unset, and gets copies as before. The
store checks the block against the state before it changes anything, then
takes a slot for each vector, copies the bits in and works out the dot
product, which checks the values and gives the norm, as a put does. A
vector that fails gives back every slot the block took: through the
transaction's undo list in `ApplyBatch`, and through `untake` outside one,
so the store is as it was either way. A reload goes the same way, after
`Reset`, and a store that took a compacted part holds each table's vectors
in slots in key order.

**`Check`** finds a damaged block wherever it reads the file: at Open, in
the read before it, which follows the file and reloads it when another file
has taken the path, and in its own read of the file, by the batch's
checksum. As with every batch, a block whose checksum fits but whose
changes break the rules shows where the file is read from its start, since
`Check`'s own read decodes no changes (G7).

**The APIs.** The internal packages gain, and lose nothing:
`format.Vectors`, `format.Vector`, `Change.Vecs`, `format.BlockHeadSize`,
`format.BlockVectorSize`, `format.DecodeBatchInPlace`,
`store.Store.Compacted` and `logfile.Options.BlocksInPlace`. What they do
differently: the store's `Apply`, `ApplyBatch` and `LoadBatch` take a
vector block, and a transaction's `Apply` and the log's `Append` refuse
one. `Change` is 24 bytes larger, for `Vecs`. The public package's API
doesn't change.

### FORMAT.md, word for word

For the coordinator to put in place. Each changed part is given whole.

The opening's third paragraph, in place of "The Beta hasn't been released,
... and never misreads it.":

````markdown
The Beta hasn't been released, and this format can still change before it
is. A change that a build without it could misread raises the format
version, even before the release, so a build of the Beta refuses a file from
another build whose format differs. A change that such a build reports as
damage keeps the version: the vector block is a change of a kind a build
from before it doesn't know, so that build refuses a file that holds one,
and reads every other file as before. Either way, no build misreads a file.
````

"Changes", whole:

````markdown
## Changes

Each change starts with a byte giving its kind, an ASCII letter, so a hex
dump shows which change is which.

| Kind | Byte | Change | Then |
|---|---|---|---|
| `T` | `54` | Create a table | the table's name (string), its vector size (u32), the number of fields (u16), then each field's name (string), in the table's order |
| `P` | `50` | Put fields | the key (string), the number of fields (u16), then each field's name (string) followed by its value |
| `D` | `44` | Delete a record | the key (string) |
| `L` | `4c` | Add a link | the key the link is from, its type and the key it's to (strings) |
| `U` | `55` | Remove a link | the same as for adding one |
| `X` | `58` | Drop a table | the table's name (string) |
| `V` | `56` | Vector block | the table's name (string), the vector size (u32), the number of vectors (u32), then each record's key (string), then each record's vector, as Vector blocks describes |

Changes apply in order, each to the state the ones before it left, and each
has to be valid there:

- **Create a table.** No table of that name exists. The new one starts
  with the vector size and fields given, and no records. The field names
  follow the rules for them, and no two match regardless of case. A vector
  size of 0 means none yet; any other is at most 65,536, and then one of the
  fields is the vector field. A put into a table that doesn't exist yet is
  written after a create change with size 0 and no fields. Compaction, and
  any writer that knows a table's whole shape from the start, such as an
  import, writes its whole field list and its vector size instead.
- **Put fields.** The table exists. The record is created if it doesn't
  exist, even when the put names no fields. Then each field given is set to
  its value, and fields the put doesn't name keep theirs. Null clears a
  field.
  - The fields come in byte order of their names as written, and no two of
    them match regardless of case.
  - A field the table has is written exactly as the table spells it. Any
    other name is a new field, which joins the end of the table's field
    list, in the order the put gives them, even when its value is null.
    Byte order is the order 0.x adds a put's new fields in.
  - The vector field is the one whose name matches `vec` regardless of
    case. It holds a vector or null, and no other field holds a vector. A
    table's first vector sets its vector size, if that's 0, and every vector
    after it must have that many values.
  - A table holds at most 65,535 fields, the most a create change can
    carry, so HyperCrux refuses a put that would add one more.
- **Delete a record.** The record exists. It goes, with every link to or
  from it. The change doesn't list the links: every reader works out the
  same ones from the same state.
- **Add a link.** Both records exist, and the link isn't there already.
- **Remove a link.** The link is there.
- **Drop a table.** The table exists. It goes with its records, every link
  to or from them, its field list and its vector size. A later put into a
  table of the same name needs a new create change first.
- **Vector block.** Only a compacted part holds one. It gives records of one
  table their vectors, by the rules in Vector blocks.

Puts are always written, even when they set the values a record already
has. Any other change that would do nothing isn't written: adding a link
twice writes one change, a delete of a record that isn't there fails before
anything reaches the file, and a transaction that changes nothing writes no
batch. Removing every link from one record to another, whatever their
types, writes one remove change for each, in byte order of type.
````

"Names and limits", whole:

````markdown
## Names and limits

Keys and names follow 0.x's rules, which the Beta keeps:

| | Rule | Length |
|---|---|---|
| Table name | lower-case letters, digits and underscores, starting with a letter, and not starting with `hc_` or `sqlite_` | 1 to 63 bytes |
| Key | a table name, a colon, and at least one more byte, in UTF-8 without zero bytes | 3 to 1,024 bytes |
| Field name | letters, digits and underscores, starting with a letter or an underscore, and not `key`, `rowid`, `oid` or `_rowid_` in any case | 1 to 64 bytes |
| Link type | UTF-8 that doesn't start with a zero byte | 1 to 200 code points |

The format's own widths set the other limits. A table has at most 65,535
fields, and a put sets at most 65,535. A text or bytes value holds at most
4,294,967,295 bytes, and a vector block at most 4,294,967,295 vectors.
HyperCrux's own limits can be lower: a put can't take a table past 1,999
fields, which is 0.x's limit.
````

"Compaction", whole:

````markdown
## Compaction

Compaction writes a new file holding only the live data, and then renames
it over the database. BETA.md describes the steps. The new file has a header
with the next generation and its last four fields set, then the compacted
part: ordinary batches, each with its marker, holding

- every table, in byte order of its name, as a create change with its vector
  size and its whole field list, then a put for each of its records, in byte
  order of their keys, carrying every field that holds a value apart from
  the vector, and no nulls, then the vectors of the records that hold one,
  in vector blocks, in byte order of their keys (see Vector blocks);
- then every link, as an add change, in byte order of the key it's from,
  then its type, then the key it's to. That's the order of whole keys,
  which can differ from the order of their tables: `users2:zed` comes
  before `users:ann`, since a digit sorts before a colon.

The writer splits the compacted part into batches as it likes, keeping each
change whole, so it can stream a large database out without building it all
in memory. HyperCrux gives each vector block a batch of its own, filled to
about a megabyte, so a table's vectors take a run of blocks. The batches are
numbered from 1, and the first commit after them takes the next number,
which a reader finds in the marker just before the end of the compacted
part, or is 1 when nothing was compacted. The header's last field points
just past the last compacted batch's marker; a database with no tables has
no compacted batches, and then it's 68. The writer only knows that offset at
the end, so it can write the header last.

Nobody can read the new file before the rename, and the file is synced
once before it, so the compacted part's markers need no sync of their own
either.

A reader applies the compacted part like any other batches. A put in it
can carry its record's vector in place of a vector block, and a reader
takes either. A compacted file is whole before anyone can see it, so a file
shorter than its compacted part, or a log that ends inside it, is damage,
and nothing before the end of the compacted part is ever cut. The
continues-from fields aren't needed to read the file. They're there for a
later version that has the old file open, so it can carry on after a
compaction without reading the new file from the start: the state at the end
of the compacted part is the state after the batch the header names.
````

"Vector blocks", new, after "Compaction":

````markdown
## Vector blocks

A vector block gives records of one table their vectors, back to back, as
the table's array in memory holds them, so a reader puts them straight into
its own array. Compaction writes them, after each table's puts, and nothing
else does.

| Size | Field |
|---|---|
| 1 | Kind: `V`, `56` |
| string | The table's name |
| 4 | The vector size, u32 |
| 4 | The number of vectors, u32 |
| a string each | Each record's key, in byte order |
| 4 times the vector size, each | Each record's vector, in the order of the keys, each value an f32 |

The keys come first and the vectors after them, so the values are one run of
bytes. A block names each record it gives a vector, and leaves out the
records without one, so every vector says whose it is. The norms aren't in
the block: a reader works each one out from the values, in the pass that
checks them.

A block applies to the state the changes before it left, as any change
does, and has to be valid there:

- The table exists, and its vector size is the block's, which is 1 to
  65,536.
- The block holds one vector at least. Each key belongs to the table, and
  the keys come in byte order, so none comes twice.
- Each key names a record of the table that holds no vector, and the vector
  becomes that record's. Its values follow the rules for a vector's values:
  none is NaN or infinite, and they aren't all zero.

A vector block anywhere but in a compacted part is damage: in a batch past
the compacted part, or in a file of generation 1, which has none. So is a
block that breaks the rules above. The batch's checksum covers a block as it
covers any change, and the syntax shows a count that disagrees with the keys
and the values given, since the change then runs past the end of its batch,
or leaves bytes over.

A build from before vector blocks reads one as a change of a kind it doesn't
know, which is damage, so it refuses a file that holds one, and never
misreads it.
````
