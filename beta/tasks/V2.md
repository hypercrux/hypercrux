## The contract

From BETA.md: vector blocks, only if the open target is missed: compaction
writes each table's vectors as one block, read on opening without parsing.
Done when a compaction round trip keeps every vector's bits and the open
target is met.

With the owner's scope, the closing test here is the round trip keeping
every vector's bits. The coordinator's recorded run after the merge times
the open, and the record and the board give it beside the target, which
stays missed.

## What's there already

- **The measure** (I1): `BenchmarkOpenFile_100k_384dims` in
  `beta/hypercrux/opening_test.go`, from the log of 20 commits and from that
  log compacted. On a quiet machine I1 timed 769 ms and 638 ms against the
  target of 250 ms. The coordinator's recorded run after G5, on a slower
  machine, gave 826 ms from the compacted file, which the benchmark now
  makes with `Compact`. I1.md's table says where a compacted file's time
  goes: about 390 ms of its 679 is the vectors, and about 250 ms the
  records, keys, fields and hash table, each through the general put path.
- **What vector blocks would save,** by I1's reckoning: about 240 ms, the
  batch copy of the vectors' bytes, the codec's check, the store's decode
  and copy, and most of the reads, so a compacted file would open in about
  440 ms on I1's machine. The load of a compacted part that appends keys
  in order, sizes the hash table once and leaves out checks the codec has
  made, and decoding from the read buffer without copying each batch into
  a string, are the rest (I1.md's note under V2). The owner left them out
  of V2.
- **The compacted part,** in `beta/FORMAT.md`'s "Compaction": ordinary
  batches of creates, puts and links in byte order, which a reader applies
  like any others. The format version is 1, and no byte of it has changed
  since P2. No Beta file is out yet: R4 makes the first release.
- **The writer and the reader:** `Compact` in the public package (G5),
  which runs the log's `Compact` on the store's `Snapshot`, and Open's read
  of the log into the store's `LoadBatch`. A reload after another process
  compacts reads the new file the same way, after `Reset` (F9). F8.md's
  note says where a compaction's own time goes: half in
  `format.AppendBatch`, most of it checking every vector value again, and a
  third in the snapshot copying each vector into a `value.Vector`.
- **The store's vector arrays** (V1): each table's vectors back to back in
  blocks of up to a megabyte that hold no pointers, their norms in float64
  in an array of their own, and an owner for each slot. A store that loads
  a compacted part gets arrays with no free slots, the slots in the order
  of the records' keys.

## To settle, and write down in this file

- **The block** in FORMAT.md: where it sits in the compacted part, its
  layout, how it says which records hold a vector, whether it keeps the
  norms, whether one table's vectors go in one change or in runs that keep
  batches near a megabyte, how a damaged block is found, and whether the
  format version stays 1.
- **Writing:** compaction writes each table's vectors from its array as
  they are, without the snapshot's copy into a `value.Vector` or the
  codec's check of each value again (F8.md's note).
- **Opening** reads each block straight into its table's array, checking
  each vector's values as `Put` would. The same goes for a reload, and for
  `Check` wherever it reads the file.
- **The tests:** a compaction round trip keeping every vector's bits, -0
  and subnormal values among them, the closing test; a block's damage
  found; the crash suites and the many-process harness through compaction
  with blocks; the format's fixtures and fuzz targets taking in the block;
  and the open timed with `BenchmarkOpenFile_100k_384dims`, which the
  coordinator's recorded run after the merge gives.
- **Planted bugs,** such as a block that drops its last vector, or a block
  read without its check, each with a line in `beta/plants.txt`.
