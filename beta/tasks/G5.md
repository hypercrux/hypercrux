# G5: The command and `Compact`

Status: done, 13 October 2026.

## The contract

From BETA.md: the command, with the same verbs apart from `adopt` plus
`import`, `export` and `compact`; `Compact()` in Go. Done when A1's command
suite passes against both binaries, apart from listed differences.

## Decisions settled

**The log's fix.** Before its first commit into a file, a Log syncs the
database's folder once, unless it made the file's name last itself: it
created the database, made a database of an empty file, or compacted into
the file, and its folder sync after that worked (`named`). I1's note
suggested files of generation 2 or more. That covers a compaction, but an
empty file made a database is generation 1 and has the same gap, after a
folder sync that fails or a process that dies between its rename and the
sync, and nothing in a file tells it apart from a database created whole.
So the rule goes by what the Log did, and it covers a backup moved into
place without a folder sync as well. The sync comes in `Append`, after the
batch is encoded and before anything is written, so a transaction that
changes nothing pays nothing, and a compaction, which syncs the folder
itself, needs none first. When it fails, the commit fails before anything
is written, the copy goes back, and the Log isn't stuck: the next `Append`
tries again. Each Log pays it once for each file it moves to: after Open of
a file another made, after a reload, and after another handle's compaction.
So each run of the command that writes into a database already there pays
one folder sync, about 87 µs here, beside its commit's own sync.

**`Compact()`** checks that it isn't inside an Update (`Outside`), takes
the log's write lock, which reads on to the end of the log and may move to
a file that has taken the path, compacts from a read of the copy, and lets
go of the lock. It returns the compaction's error. A failure to let go of
flock is dropped, as `Update` drops it: the compaction stands, and the lock
goes at this DB's next Update or Close. A panic while the snapshot is read
carries on to the caller, as the log's `Compact` lets it, once
`NAME.compact` has gone.

**The compaction after a commit** comes in `Update` once `Commit` has handed
a batch to `Append` and it worked, while the Update still holds the lock:
when `Due` says one is due, a read of the copy goes to the log's `Compact`.
An Update whose transaction changed nothing writes no batch and compacts
nothing, even when another process's commits have made one due. `Update`
returns nil once its commit has succeeded, whatever the compaction does,
and a panic in the compaction is recovered into its error, since the commit
is in the file and a caller that saw the panic would take it for a failed
one.

**Where a compaction's error goes.** Each DB keeps the error of the last
compaction it ran, by `Compact` or after a commit, and clears it when one
works. `Check` gives it in `Report.CompactionError`, a field of its own,
beside the sizes, and OK doesn't count it: a compaction that fails leaves
the database whole, in its old file or, when it stuck, in the new one, so
it isn't a problem in the database. A stuck DB says so itself too, since
every later write fails with `ErrStuck`. Another process never sees the
error, and nor does the command, which opens the database afresh each run.

**`Options.MinGrowth`** is the log's one addition to its API, for tests: the
crash workload whose commits compact by themselves sets 1,000 bytes, and
`opening_test.go` sets the largest value there is, so its log keeps its 20
commits. Every other DB uses a megabyte, as `Due` did.

**The command** is 0.x's code with the differences above. The SQL goes
through `Exec` when the statement's first word, after spaces and comments,
is INSERT, UPDATE or DELETE, for the count of changed rows, and through
`Query` otherwise. 0.x's own check for one statement stays, with exit code
2 (P5.md, Q3.md). `init` makes an Update that changes nothing, whose lock
makes a database of an empty file. `check` names damage that stops the
database opening with `Damage`'s own words, without the package's name and
the path, which are the words `Check` uses. Standard output is buffered and
flushed at the end, and a failed flush exits with 1.

**The suite on every `go test`.** cmdtest builds both commands when
`HYPERCRUX_BIN` is unset, so CI needs no change, and the Beta's skips come
from SQL.md's table, so the spec and the run can't drift apart.
`TestEveryNamedTestExists` and `TestCommands` read the table through one
function. `TestDrop` isn't a section, so the table needs no row for it.

## Notes for later tasks

- **R1, long runs:** `HYPERCRUX_CRASH_SEEDS` raises the seeds of the four
  crash workloads through the public package, the compactions after commits
  among them. In full, the kill test's file passes a megabyte once, so a
  commit is followed by a compaction once a run; `HYPERCRUX_PROCS_TIME`
  lengthens the many-process run, whose writers call `Compact`.
- **R2, the review:**
  - The compaction after a commit doubles the batched put's time on a
    database that only grows, 14 µs to about 26 here, since `Due` can't
    tell live data from dead without a pass over the copy (F8.md). Every
    process applies every batch since the last compaction, at Open or as it
    follows, so each could count the bytes a put overwrites, a delete
    removes and a drop takes, and all would agree. Compacting once those
    reach the live data would leave a database that only grows alone. It
    changes F8's `Due` and BETA.md's rule, so it's the owner's call.
  - Open's error for a file that isn't a database repeats the package's
    name: "hypercrux: PATH: hypercrux: not a HyperCrux database: ...". The
    log's `load` wraps the codec's error with the path, and the command
    prints it as it comes.
  - `go build ./...` fails on macOS and Windows at `beta/cmd/hypercrux`:
    every file but `doc.go` is Linux only, which leaves a main package with
    no `main`. `go vet` and `go test`, which CI runs there, pass.

    snapshot from the caller; `Check` shows it.
