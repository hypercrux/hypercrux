# P1: The beta/ folder, its build, CI and the task board

Status: done, 7 October 2026.

## The contract

From BETA.md: the `beta/` folder beside 0.x, its build, and CI on amd64 and
arm64 with the race detector, fuzzing and planted-bug jobs; the task board.
Done when a trivial test passes in every job, and 0.x's own tests and builds
pass unchanged.

## What was built

- **A workflow of its own, `beta`** (`.github/workflows/beta.yml`), on every
  push to main and every pull request. A newer push to the same branch
  cancels a run still going. Its jobs:
  - `rules`: `sh scripts/check-beta.sh`.
  - `arm64`, on `ubuntu-24.04-arm`: `go vet` and `go test` on all of
    `./beta/...`, then the race detector with `-short`. It takes the place of
    A5's job in the `test` workflow, which ran `vecmath` only. The
    conformance suite reaches 0.x through cgo, and the runner's own C
    compiler was enough.
  - `fuzz`: `sh scripts/fuzz.sh 30s`. A failing input is uploaded as the
    artifact `failing-fuzz-inputs`.
  - `planted`: `sh scripts/planted.sh`.
- **The `test` workflow** is back as it was before A5: `go vet ./...` and
  `go test ./...` on ubuntu and macOS, plus the race detector with `-short`
  on Linux. On Linux amd64 that already runs every test in `beta/`.
- **Planted bugs:**
  - A planted bug is built in only with the build tag `hypercrux_planted`,
    and `HYPERCRUX_PLANT` names the one to switch on.
  - A package with planted bugs has a pair of files. `plant_off.go` is for
    ordinary builds: there `const plant = ""`, so the compiler drops every
    branch that checks it. `plant_on.go`, built with the tag, reads the
    variable and holds the bugs.
  - `beta/plants.txt` lists each bug, with the packages whose tests must
    catch it.
  - The first two are in `vecmath`: `vecmath/four-sums`, 4 running sums
    instead of 8, and `vecmath/sums-in-a-row`, the 8 sums added left to
    right instead of in pairs.
- **Scripts:**
  - `scripts/check-beta.sh` checks the rules for `beta/`. Every Go file
    starts its build tag with `linux`, apart from one untagged `doc.go` in
    every package directory. The code is gofmt'd, and `go vet ./beta/...`
    passes with `GOOS=darwin` and with `GOOS=windows`. Then it runs the board
    check.
  - `scripts/check-board.py` checks that the board has BETA.md's tasks with
    their hours, in an order where each task comes after the tasks it needs.
  - `scripts/fuzz.sh [time]` runs every `Fuzz` function in the module, found
    by name, for 30 seconds each unless a time is given. It fails if it
    finds none.
  - `scripts/planted.sh` first runs the tests with the tag and no bug
    switched on, which have to pass, so a failure after that comes from the
    bug. Then it switches on each listed bug in turn and requires its tests
    to fail. It prints "caught" or "MISSED" for each and a count at the end,
    and a miss fails the job.

## Decisions settled

- **What gates a release.** Releases wait for the `test` workflow only. It
  runs every test in `beta/` on Linux amd64 with the race detector, so a
  broken Beta test still holds up a release of 0.x. The `beta` workflow
  doesn't, so a slow fuzz run or a flaky ARM runner can't keep a fix to 0.x
  from shipping. When the Beta itself is released, in R4, its release waits
  for the `beta` workflow too.
- **Job times.** Each job takes three minutes or less. Fuzzing costs 30
  seconds a target on every push, plus the build. Hours-long runs are R1's.
- **Planted bugs.** The tag keeps them out of every ordinary build, and the
  variable picks one at run time, so one test build serves every bug in a
  package. A name the package doesn't know switches nothing on, so a typo
  shows up as a missed bug instead of a false catch.
- **The plants format.** One line a bug: its name, then the packages whose
  tests must catch it. Names are `package/what-goes-wrong`.
- **Fuzz targets** are found by name, so a new one joins the job without an
  edit. A failing input from CI goes into the package's `testdata/fuzz`
  with the fix, where `go test` replays it from then on.
- **The board** says how the work is run, under "How to pick up the work",
  and `check-board.py` keeps its rows in line with BETA.md on every push.

## Notes for later tasks

- **A new package in `beta/`** needs a `doc.go` without a build tag, and
  every other file in it starts with `//go:build linux`. The `rules` job
  fails otherwise.
- **Tasks that plant bugs,** T3 and T4 first: add a `plant_off.go` and
  `plant_on.go` pair to the package if it hasn't one, put the bug's name in
  `plant_on.go`'s list, and add a line to `beta/plants.txt`. BETA.md wants
  planted bugs in commits, recovery, compaction, vectors and links.
- **F1 and Q3:** their fuzz targets join the `fuzz` job by themselves. For
  F1's 30-minute run, `go test -fuzz` can name the decoder's target alone;
  `sh scripts/fuzz.sh 30m` runs every target for that long.
- **The fuzz job's length:** each target adds 30 seconds. If the job runs
  past five minutes, split it into one runner per package.
- **R4:** the release workflow's trigger names the `test` workflow only.
  The Beta's release has to wait for `beta` as well.
