# P1: The beta/ folder, its build, CI and the task board

Status: next. Planned at 2 hours. It needs A3, which is done.

## The contract

From BETA.md: the `beta/` folder beside 0.x, its build, and CI on amd64 and
arm64 with the race detector, fuzzing and planted-bug jobs; the task board.
Done when a trivial test passes in every job, and 0.x's own tests and builds
pass unchanged.

## What's there already

- **The folder and the build rule:** `beta/`, with every file Linux only
  except one untagged `doc.go` per package (A1). On macOS and Windows the
  packages build empty, which is checked with `GOOS=darwin` and
  `GOOS=windows`.
- **The task board:** `beta/tasks/README.md`, with a file per task.
- **The `test` workflow:**
  - on ubuntu and macOS: `go vet`, `go test ./...`, and on Linux the race
    detector with `-short`;
  - `arm64`, on `ubuntu-24.04-arm`, for `beta/internal/vecmath` only (A5).
  - `go test ./...` already runs all of `beta/` on Linux amd64: about two
    and a half minutes, with A1's killed writers and A3's 2,000 sequences.
- **The `release` workflow** runs after `test` passes on main. Any job in
  `test` that fails, or flakes, holds up the next release.

## To settle, and write down in this file

- **The layout of the jobs.** A starting point:
  - amd64: as now.
  - arm64: widen to `go test ./beta/...` and the race detector with
    `-short`. The conformance suite reaches 0.x through cgo, which needs a
    C compiler there.
  - Fuzzing: each fuzz target for a short time on every push. Today that's
    `internal/export`'s two; F1's decoder and Q3's parser add theirs.
    Hours-long runs are R1's.
  - Planted bugs: a job that switches a planted bug on, with a build tag
    or an environment variable, and requires the tests to fail. The first
    one can go in `vecmath`, 4 sums instead of 8 or another combining
    order, so the job has something to catch before the engine exists.
    A3's broken engines already show the pattern for whole engines.
- **What gates a release.** A long or flaky job shouldn't hold one up.
  Fuzzing and planted bugs might go in a workflow of their own, which the
  release doesn't wait for. Weigh that against catching a bug before it
  ships.
- **The time each job takes.** Keep a push's jobs to a few minutes.
- **The board:** P1's part is to check it says how the work is run, and
  that every task's row matches BETA.md.
