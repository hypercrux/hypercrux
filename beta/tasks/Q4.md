# Q4: Operators

Status: done, 8 October 2026.

## The contract

From BETA.md: operators: scan, filter, project, sort, top k, limit and
offset, aggregates over the whole result. Done when each operator passes
against a fake store, and aggregates match A4's answers.

## What was built

All of it is in `beta/internal/query`, in files of its own. No file that
was there changed apart from this one and `beta/plants.txt`, which has
twelve new lines.

- **`ops.go`,** the operators, each a `Rows`, and what they share:
  - `Scan(r, src)`: a table's records in key order, through
    `store.Reader`'s `Scan(table+":", "")`, started at its first `Next`.
  - `Filter(in, conds, f)`: the rows for which each of a WHERE's terms is
    true, worked out in turn.
  - `Project(in, cols, f)`: the result columns over each row.
  - `Sort(in, cols, keys, f)` and `TopK(in, cols, keys, k, f)`: ORDER BY,
    stable, in SQL.md's order of values. TopK keeps the best k rows as it
    reads, for an ORDER BY with a LIMIT.
  - `Limit(in, n, skip)`: LIMIT and OFFSET, and `Bounds(limit, offset, s,
    f)`, which works them out first, as SQLite's `OP_MustBeInt` takes them.
  - `SortKey`: an ORDER BY term, as a result column or an expression of its
    own.
  - `RowSource` and `RowScope`: the Scope that hands a row's fields to
    compiled expressions. `TableSource` makes a table's source, and its
    `Fill` puts a record into a row.
- **`agg.go`,** the aggregates. `NewAggregates` finds every aggregate call
  a query names and compiles its arguments. `Aggregates` is the Scope the
  result columns compile with, and `Aggregate` is the operator that gives
  the one row. The accumulators are SQLite's `countStep`, `sumStep` with its
  Kahan-Babuska-Neumaier summation and its three finalizers, and
  `minmaxStep`.
- **Twelve planted bugs,** in `plant_ops_on.go`, whose `init` switches them
  on, so `plant_on.go` stays as it was: `query/sort-unstable`,
  `query/sort-nulls-last`, `query/top-k-later-tie-wins`,
  `query/top-k-works-out-every-row`, `query/limit-counts-offset`,
  `query/offset-after-zero-limit`, `query/sum-uncompensated`,
  `query/sum-in-reverse`, `query/sum-text-as-real`, `query/sum-wraps`,
  `query/max-later-tie-wins` and `query/aggregates-as-compiled`.
- **Tests:**
  - `ops_corpus_test.go`: `TestTheCorpusAggregatesGive0xsAnswers`, the
    closing test, and `TestTheCorpusQueriesOverOneTableGive0xsAnswers`.
    `TestQueriesOverTheFixture` holds 56 queries over the fixture, which
    show what SQLite works out and what it leaves. `storeDB` fills a real
    store through `sqlcorpus.Fixture`, and `runSelect` puts the operators
    together by hand for a SELECT over one table, as the planner will.
  - `ops_test.go`: each operator against `fakeReader`, a fake
    `store.Reader`: empty tables, one row, ties, NULLs, values of every
    kind, limits at the edges, what each reads and works out, and rows
    filled on several goroutines at once.
  - `agg_test.go`: `aggCases`, 32 columns of values with what each of the
    seven aggregates gives over them, and two tables of expressions over
    aggregates.
  - `ops_sqlite_test.go`, built with cgo only: those tables and the 56
    queries held to 0.x, and random sorts and aggregates on random rows
    against 0.x through `zerox`.

- **Found on the way,** each now a case in a table:
  - SQLite works out every aggregate a query names, the `sum()` in
    `0 AND sum(x)` included, where the evaluator skips that side. So

## Decisions settled

**Rows and the Scope** (`ops.go`):

- A row is a `[]value.Value`. `Frame.Row` holds a `*[]value.Value`, and
  each operator points it at the row it's working on, so handing a row to
  the Evals allocates nothing.
- Each operator that works out expressions takes the statement's `Frame`
  and copies it. So the arguments, and whatever else the statement keeps in
  its Frame, such as Q2's moment for 'now', reach every row.
- `RowSource` is one source's run of places in a row, from `Base`. A
  table's are its key and then its fields in order. `RowScope.Column` finds
  a name as SQL.md's "Sources, qualified names and clashes" has it, with
  SQLite's messages: "no such column: d.n", "ambiguous column name: key".
  The one-record subquery, walks and the calls the evaluator leaves to
  others go to `RowScope.Next`, the planner's Scope.
- `Fill` fills only the fields a statement reads, which the RowScope
  marked as it compiled, and the vector only when it's read, as a copy of
  kind `KindVector`. So a planner compiles every expression before it reads
  rows. Fill and the Evals only read what they share, so a nearest search's
  filter can fill rows of its own on several goroutines.

**The order of work,** which shows in which rows raise an error, as
SQLite's code generator orders it, each checked against 0.x:

- Without ORDER BY, a SELECT is Scan, Filter, Limit, then Project, so the
  rows OFFSET skips get as far as WHERE, and once LIMIT's rows are out
  nothing more is read.
- With ORDER BY and no LIMIT, it's Scan, Filter, Sort, then Limit, and
  every row's terms and result columns are worked out.
- With ORDER BY and a LIMIT, it's Scan, Filter, TopK with k of LIMIT plus
  OFFSET, then Limit. TopK works out every row's terms, and a row's result
  columns only when it keeps the row, as SQLite's sorter does under a LIMIT
  (`pushOntoSorter` with `pDeferredRowLoad`): when fewer than k have come,
  or when the row comes before the last of those kept. A row that ties the
  last comes after it, since it came later, and is left out. A term that's
  a result column, by its alias or its number, is worked out for every row,
  as a term. A negative LIMIT, or a LIMIT plus OFFSET past 64 bits, keeps
  every row, as `OP_OffsetLimit` has it, so the planner sorts.
- An aggregate query is Scan, Filter, Aggregate, Limit, then Project over
  the one row. The aggregates finish, sum()'s error included, before the
  OFFSET skips the row, and a skipped row's result columns aren't worked
  out.
- `Bounds` comes first: LIMIT, then OFFSET. A LIMIT of 0 runs nothing
  more, OFFSET included.

**Sorting:** in `compare`'s order, `sqlite3MemCompare`'s, with DESC
reversing it. Ties keep the order rows came in, by a sequence number each
kept row carries. Sort keeps every row, and TopK a heap of k rows with the
last on top.

**Aggregates** (`agg.go`):

- `NewAggregates` walks the result columns and then the ORDER BY terms
  that are expressions, as `sqlite3ExprAnalyzeAggList` does, and compiles
  each call's arguments with the rows' Scope. The result columns then
  compile with the Aggregates, whose `Call` reads each aggregate's result
  from the one row. An aggregate query's ORDER BY isn't worked out, apart
  from its aggregates, as SQLite drops it for one row.
- Each row works out each call's arguments in turn and steps the call. A
  field outside an aggregate's argument, which the parser and the planner
  refuse, gives an error if it's ever worked out.
- `sum()`, `total()` and `avg()` are SQLite's `SumCtx`: whole numbers
  exactly while they fit, then reals with Kahan-Babuska-Neumaier summation
  in the order of the rows, whole numbers past 2^52 added in two parts.
  Text that all reads as a number counts as that number, through
  `numericAffinity`, and other text and bytes count as `realOf` reads them.
  After the whole numbers overflow, a value that isn't one clears the
  error, as `sumStep` does. Go keeps float64 sums in float64 and doesn't
  reorder them, so they give SQLite's bits.
- `min()` and `max()` replace the value kept only when one comes strictly
  before it or after it, so a tie keeps the earliest row's value.

**LIMIT and OFFSET:** `OP_MustBeInt`'s rules. An integer, a real that
`sqlite3VdbeIntegerAffinity` makes a whole number strictly between the
smallest and the largest integers, or text that reads as one of those.
Anything else is "datatype mismatch", bytes and `-9223372036854775808.0`
included.

**The planted bugs** are in a file of their own, `plant_ops_on.go`, whose
`init` sets `plant` when `HYPERCRUX_PLANT` names one of them. So this task
leaves `plant_on.go`, which Q2 may change in the same round, as it was.

**Where SQL.md is silent,** settled as 0.x's SQLite behaves and checked
against 0.x. The wording for SQL.md:

- "LIMIT and OFFSET", in place of its paragraph: "`LIMIT n` keeps the first
  n rows, and `OFFSET m` skips m rows before them. Both are worked out
  once, LIMIT first, before anything else in the statement, and can't use
  fields or aggregates. Each must give a whole number: an integer, a real
  without a fraction strictly between the smallest and the largest
  integers, or text that reads as one of those, with spaces at either end.
  Anything else, NULL and bytes included, is an error, "datatype mismatch",
  and so is `LIMIT -9223372036854775808.0`. A negative LIMIT means no limit,
  and a negative OFFSET means 0. A LIMIT of 0 gives no rows, and nothing
  more of the statement is worked out, its OFFSET included, so
  `LIMIT 0 OFFSET NULL` is no error. OFFSET needs a LIMIT. SQLite's
  `LIMIT m, n` is outside the subset."
- "What gets worked out", in place of the bullet on ORDER BY terms:
  "Without ORDER BY, the rows OFFSET skips are worked out as far as WHERE,
  and their result columns aren't. Once LIMIT's rows are out, no more rows
  are read." And: "With ORDER BY, every row that passes WHERE has its terms
  worked out, before LIMIT. Without a LIMIT, its result columns are worked
  out too. With one, SQLite's sorter keeps the best LIMIT plus OFFSET rows
  so far, and a row's result columns are worked out only when the sorter
  keeps it as it comes: when fewer than that many have come, or when it
  comes before the last of them. A row that ties the last comes after it.
  A term that's a result column, by its alias or its number, is worked out
  for every row, as a term."
- "Aggregates", under "Queries", two new bullets: "Every aggregate the
  result columns and ORDER BY name is worked out over every row that
  passes WHERE, even where the expression around it doesn't need its
  value, so `0 AND sum(abs(x))` raises abs()'s error. An aggregate query's
  ORDER BY isn't worked out apart from its aggregates, since it sorts one
  row." And: "The aggregates finish before LIMIT and OFFSET apply to the
  one row, so sum()'s "integer overflow" shows under `LIMIT 1 OFFSET 1`
  too, and the result columns of the row OFFSET skips aren't worked out."
- "Aggregates", under "Functions", after the table: "Once the integers
  leave 64 bits, `sum()` goes on as a real, and a value that isn't an
  integer after that clears its error: the sum of 9223372036854775807, 1
  and 0.5 is 9223372036854775808.0, and that of 9223372036854775807, 1 and
  -1 is an error. A sum, total or average that would be NaN, from
  infinities of both signs such as '1e999' and '-1e999', is NULL, `total()`
  included. Reals add up from 0.0, so the sum of -0.0 alone is 0.0, where
  `min()` and `max()` give -0.0 back."
- "Text as numbers", the row for `sum()`, `total()` and `avg()`: "text that
  reads as a number, all of it, counts as that number. Other text counts as
  a real, read as for CAST to REAL, and so do bytes, so `sum(x'35')` is
  5.0."

## Notes for later tasks

- **Q5, the planner:**
  - `runSelect` in `ops_corpus_test.go` is a worked example for a SELECT
    over one table: compile everything first, then `Bounds`, then the
    operators in the order above. A LIMIT of 0 runs nothing, the scan
    included.
  - Give `RowScope` the statement's sources and `Next`, Q5's own Scope for
    the one-record subquery, walks, `walk()`, `date()` and `datetime()`. A
    walk as a table is a `RowSource` with the columns key and depth, and
    json_each's has SQLite's eight, of which only value may be used, so
    Q5 refuses the others before handing a name on. A join is one row
    holding both sources' runs, each at its `Base`, which the walk's
    operator fills, with `Fill` for the table's record.
  - WHERE: split at its top-level ANDs (`whereTerms` in `cond_test.go`),
    compile each with `CompileCondition`, and hand them to `Filter` in
    order.
  - ORDER BY: SQL.md's three rules. An alias or a column number is a
    `SortKey` with `Col`, and an expression a `SortKey` with `Eval`,
    compiled with the sources' fields first and then the result columns'
    aliases. An expression that's the same as a result column is that
    column to SQLite (`resolveOrderByTermToExprList`). Working it out as an
    expression gives the same answer and the same errors.
  - An ORDER BY whose first term is the key going up, by name, alias or
    number, is the scan's own order. 0.x reads its key index then and
    sorts nothing, so plan it as Scan, Filter, Limit and Project, which
    gives 0.x's answer and errors: `ORDER BY key LIMIT 1 OFFSET 3` leaves
    the result columns of the rows it skips unworked. Going down, 0.x reads
    the index backwards and stops after LIMIT plus OFFSET rows. TopK gives
    the same rows, but works out every row's result columns, since each
    comes before those kept, so an error can show that 0.x never meets.
  - An aggregate query: `NewAggregates` over the result columns and the
    ORDER BY terms that are expressions, the result columns compiled with
    the Aggregates, then Scan, Filter, Aggregate, Limit and Project. Refuse
    a field in its ORDER BY that's outside an aggregate, once aliases are
    found. Column numbers are still checked.
  - Without a FROM, the query has one row with no fields: a Rows of one
    empty row, under the same operators.
  - Nearest's filter: give each goroutine a row of its own and a copy of
    the Frame pointing at it, `Fill` the record into the row, and work out
    the Conds.
- **Q6, writes:** an UPDATE's or a DELETE's records come from Scan and
  Filter with a `RowScope` over the table, read whole before the first
  write, and copied, since a row is good only until the next `Next`. An
  UPDATE's values are a `Project` over the same rows. `Fill` leaves the
  fields a statement doesn't read NULL, so a write takes the rest from the
  store's record.
- **G4, slice 3:** the top Rows' row is used again at each `Next`, so the
  driver copies each, and a `KindVector` goes out as a copy of its bytes.
  Close the Rows once they're read.
