# A2: Export and import for 0.x

Status: done, 7 October 2026. Released as HyperCrux 0.2.0, the first release
the release workflow published on its own.

## The contract

From BETA.md: JSON lines with each table's vector size and field order,
links, and numbers that read back to the same bits. Done when random files
with awkward values (subnormals, -0, extremes, bytes, Unicode) go through
export, import and export byte for byte.

## What was built

- `internal/export`: the format's reader and writer, in plain Go with no
  cgo, so the Beta's G6 uses the same code and writes the same bytes. The
  writer checks the order it's given and writes each value one way only.
  The reader is strict, apart from the leniencies EXPORT.md lists.
- `export.go` in the root package: `DB.Export(w)` and `DB.Import(r)`.
  - Export reads one snapshot (`snapshot()`, split out of `Check`). It runs
    all of `Check`, SQLite's integrity check included, and refuses on any
    problem. It refuses UTF-16 files, and values `Put` wouldn't take.
  - It reads each field as `+field`, so go-sqlite3 doesn't turn a DATETIME
    or BOOLEAN column's values into Go times and booleans. It lists columns
    with `pragma_table_xinfo`, so generated columns come out as fields.
  - Import runs in one transaction, into a file without record tables, once
    `Check` passes on it. Tables are made by `ensure()` in field order, with
    `dims` set straight into `hc_tables`. Records go in by plain INSERT, so a
    repeated key fails, with values through `encodeField`. Links go in by
    plain INSERT through the triggers.
- The command: `hypercrux export FILE` writes to standard output.
  `hypercrux import FILE` reads standard input, creates the file if it's
  missing (and removes it again if the import fails), then prints Check's
  counts.
- [EXPORT.md](../../EXPORT.md): the format.
- Tests:
  - `internal/export`: number and string forms, 2,000 random round trips,
    refusals, and two fuzz targets.
  - Root package: 40 random files through export, import and export (8 with
    `-short`), compared byte for byte and value by value with SQLite types.
    Also typed, generated and sized tables; refusals on both sides; an
    export cut at every byte; an export during writes; UTF-16.
  - `cmd/hypercrux`: the exact export text, and import's refusals.
  - `beta/conformance/cmdtest`: a new section, ExportAndImport.
- The smoke tests for Linux, macOS on Apple silicon and Windows now send a
  file through export and import too.

## Decisions settled

- **API:** `db.Export(w io.Writer) error` and `db.Import(r io.Reader) error`,
  plus `hypercrux export FILE` and `hypercrux import FILE`.
- **Lines:**
  - The first line is `{"hypercrux":"export","version":1}`.
  - Each table is `{"table","dims","fields"}`, with `dims` null when the
    table has no vector size.
  - Each record is `{"key","fields"}`.
  - Each link is `{"from","type","to"}`.
  - The last line is `{"end":{"tables","records","links"}}`, with counts, so
    an export cut short is refused.
- **Values:**
  - Integers are int64.
  - Reals are the shortest float64 decimal, switching to an exponent below
    1e-6 and from 1e21 as JavaScript does. Whole numbers get `.0`, and -0.0
    keeps its sign.
  - Vector values are the shortest float32 decimal, without the `.0`.
  - Bytes are `{"base64":"..."}` in standard base64 with padding.
  - Text escapes only the quote, the backslash and characters below U+0020,
    in lower-case hex.
- **Values `Put` refuses**, which plain SQL can store, stop the export with
  an error naming the record. The format has no markers for them, so an
  export holds exactly what `Put` and `Link` take, and import goes through
  the same rules.
- **Importing into a file that has records:** refused. So is a table name
  already taken by any table, view or index in any mix of case, a file
  Check finds problems in, and a UTF-16 file.
- **What's carried:** only record tables and links. Declared types,
  constraints, indexes and a table's own triggers stay behind. Generated
  columns come back as plain columns, and the key comes first.

## Releases now publish themselves

The owner asked for this on 7 October: he publishes no releases, in this
project or any other.

- `.github/workflows/release.yml` runs after the test workflow finishes on
  main. Its plan job goes on only after a successful push to this
  repository, and only if that commit is still main's head. It reads
  `const Version` in `hypercrux.go`, and does nothing if the tag exists. It
  fails if the version isn't above the newest `v*` tag.
- The builds and checks are as before, from that commit. Then
  `gh release create` tags it and publishes "HyperCrux vX.Y.Z" with the
  binaries, SHA256SUMS and the notes. gh uploads to a draft first, so
  nothing is public until the files are there.
- A release published by hand still gets its binaries, and the workflow can
  still be run by hand for an existing tag.
- **To release:** raise `Version` in `hypercrux.go` and the version line at
  the top of the README, in one commit on main. A push that doesn't raise
  it releases nothing. A push made before a release run finishes moves the
  release to the newer commit.
- **Checked on 0.2.0:** run 37631020225 had every job green. Tag v0.2.0 is
  at 62d86ff, made by github-actions, and is the latest release. The Linux
  binary from the site's download link matched its checksum, reports 0.2.0
  and passed the smoke test. The other four links answer.

## The review

A review agent read the change and found no fault in the round trip itself.
These are fixed and tested:

- generated columns were left out;
- export skipped SQLite's integrity check;
- Check didn't look at the range of `dims`, so export could write one that
  import refuses;
- import trusted the target's triggers without checking them;
- UTF-16 files sort keys differently from UTF-8;
- in the workflow, one queue for all runs could drop a pending run, and an
  older version could go out from a stale commit.

The fuzzer also caught a flaw in a test, which handed encoding/json a number
too large for a float64. That input is now a seed in
`internal/export/testdata`.

## Notes for later tasks

- **G6:**
  - Use `internal/export`. Give the writer tables by name, records table by
    table and by key, and links by from, type and to, all in byte order.
  - Fields follow the table's column order, and the vec field holds a
    `[]float32`.
  - The reader returns `Table`, `Record` and `Link` values, with a record's
    fields in table order.
  - The command suite expects the texts "already holds record tables" and
    "not a valid HyperCrux export".
- **G6's closing test:** 0.x to the Beta and back, byte-identical. It can use
  `hypercrux.DB.Export` on the 0.x side.
- **The conformance suite:** its `DB` interface has no `Export` or `Import`
  yet. G6 adds them, and a round-trip test with them.
- **P5 and S1:**
  - A table's vector size outlives its vectors and comes through an import.
    The Beta keeps the same rule.
  - Imported values go through `Put`'s conversions.
- **R3:** the Beta's own format document mustn't take the names FORMAT.md
  or EXPORT.md, which are 0.x's.
- **R4:** the Beta's release is published by the same workflow when its
  version is raised. The R4 row in BETA.md says so now.
