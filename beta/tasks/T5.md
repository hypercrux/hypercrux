# T5: Benchmarks

Status: done, 8 October 2026.

## The contract

From BETA.md: benchmarks mirroring 0.1's, with 0.1 run alongside. Done when
one results file holds both.

## What was built

All of it is in `beta/bench`, a new package, and one new script. The
package's code uses only the standard library. Its tests import 0.x's
package and the Beta's, as `zerox` and `betax` do, and nothing in
`beta/hypercrux` or `beta/internal` imports it.

- **`doc.go`:** the package comment.
- **`results.go`:** `Parse`, which reads what `go test -bench` printed, with
  `-v` or without it, into a `Run`; `Run`'s `Times`, `Middle`, `Skipped`
  and `WriteTable`; and `Targets`, BETA.md's targets by benchmark.
- **`engines_test.go`:** the two engines, each through its public package,
  behind `engine`, `db` and `tx`.
- **`fixtures_test.go`:** the files the benchmarks share, built once per run
  on each engine as 0.1's are, and `TestMain`, which removes them.
- **`bench_test.go`:** the 14 benchmarks, `both`, which runs each on both
  engines, and `later`, which names what the Beta can't run yet.
- **`mirror_test.go`:** `TestEveryBenchmarkRunsOnBoth`,
  `TestTheSkipsStillWait` and `TestTheTargetsAreBETAs`.
- **`results_test.go`:** `TestParse`, `TestParseWithoutV`,
  `TestParseRefusesABadTime`, `TestTheMiddleRun` and `TestDurations`, and
  `TestRecord`, which writes the results file's table when the script asks.
- **`scripts/record-beta-bench.sh`:** runs the benchmarks and writes
  `test/results/beta-bench.txt`.

## The result

- **One results file holds both.** `sh scripts/record-beta-bench.sh` writes
  `test/results/beta-bench.txt`: a header like `record-tests.sh`'s, a table
  with the middle of three runs of each benchmark on 0.x and on the Beta
  beside the Beta's target, and then the runs, three for each benchmark on
  each engine, all from one run of one test binary. Checked end to end with
  `-short -benchtime 1x -count 1` into a file elsewhere, in 1.9 seconds.
  The recorded run is the coordinator's, below.
- **What the Beta runs now:** Put, Put_384dims, PutBatch_384dims, Get and
  Open_100k_384dims. Eight more wait for G2 (the four Nearest searches
  without a filter, the three walks and Link), and
  Nearest_100k_384dims_tenthFiltered waits for G4. Their rows read "waits
  for G2" or "waits for G4", and the runs show each skip with its reason.
- **Every benchmark ran,** once each on small data with `-short`, in about
  a second for the lot. At full size, once each: opening on both engines,
  Walk_100k_depth1, Nearest_10k_1536dims and Get on 0.x, which between them
  build every big file on 0.x and the Beta's 100,000-record table. Put,
  Put_384dims, PutBatch_384dims and Get on the Beta ran 20,000 iterations
  each.
- **The same work as 0.1's.** A short run of Get on 0.x through the package,
  beside 0.1's own `BenchmarkGet` at the root, gave 15 to 24 µs against 23
  to 30 µs, three runs each on the shared machine. The adapter adds one
  interface call to each operation.
- **The tests catch a broken mirror.** Of 11 breakages made by hand, one at
  a time, the tests caught all 11: one of 0.1's benchmarks missing, one
  added, one run on 0.x alone; an entry in `later` with the wrong task,
  naming a call that works, naming a benchmark that isn't there, or giving
  the filtered search G2; and a target changed, dropped, added, or given to
  Put as a time. Of 14 bugs put into `results.go` by hand, the tests caught
  all 14, among them the upper middle for an even count, GOMAXPROCS left on
  the name, notes unmarked, trailing spaces kept and the run's time unread.
  A review found one more, a message's second line read as a run when it
  starts with Benchmark, which `TestParseWithoutV` now covers.
- **How long the recorded run takes:** about 5 minutes as things stand, and
  about 8 once G2 and G4 let the Beta run all 14. Building the files takes
  about 26 seconds on 0.x (19 of them the graph, 5 the 100,000 vectors) and
  2 on the Beta. Each benchmark then takes about 4.5 seconds a run on each
  engine, as 0.1's recorded run did (189 seconds for 13 benchmarks of three
  runs), and 19 run now, 14 on 0.x and 5 on the Beta. After G2 the Beta
  opens its 100,000-record files once per round, as 0.1's benchmarks open
  theirs, which adds about a minute.
- **Times:** the package's tests take 0.01 seconds, and 1 second under
  `-race`.
- `go vet ./...`, `go test -short ./...`, `go test -race` on `beta/bench`
  with and without `-short`, and `sh scripts/check-beta.sh` pass.

## Decisions settled

**Where they live.** `beta/bench`, with the benchmarks and the engines in
its tests. The code that reads the runs and writes the table is the
package's own, so G2, F7 and I1 can use `Parse`, `Middle` and `Targets` for
their checks.

**The names.** 0.1's, each with the engine after it as a sub-benchmark:
`BenchmarkGet/0.x` and `BenchmarkGet/Beta`. `-bench /Beta` picks one engine.
go test runs a sub-benchmark's `-count` runs in a row, so each benchmark's
three runs come together, 0.x's first.

**The same data and the same work.** Each benchmark is written once, against
`db` and `tx`, and each engine's adapter hands every call straight to its
package. A `map[string]any` is each package's `Fields` underneath and a
`[]float32` its `Vector`, so nothing is copied, and `engine.vector` boxes a
vector as the package's own `Vector`, as 0.1's benchmarks put a `Vector` in
`Fields`. The files are 0.1's, built from the same seeds in the same order,
one per engine. One difference: 0.1's graph adds its links with an INSERT
into `hc_links` through the transaction's own SQL handle, which only 0.x's
package can reach. Here both engines add them with `Tx.Link`, which gives
the same links, since 0.x's `Link` is that INSERT OR IGNORE after two
checks. It takes 0.x about 19 seconds once per run.

**Skips.** `later` in `bench_test.go` names each benchmark the Beta can't
run yet, by 0.1's name, with its task and the Beta's calls that wait for it,
as `betax`'s `later` names tests. The benchmark is skipped on the Beta
before its file is built, with "waits for task G2, which brings Nearest".
`TestTheSkipsStillWait` makes each of those calls on a small database, and
needs at least one of each entry's calls to fail as a stub does, naming the
entry's task, and none naming another. So once G2 makes Link, Walk and
Nearest work, the test fails until G2 takes its eight lines out, and the
benchmarks run. A benchmark that meets a stub without an entry fails with
the stub's message, which names its task.

**Opening.** `BenchmarkOpen_100k_384dims` times `Open` and one `Get` on the
100,000-record table that Nearest_100k_384dims searches. The `Get` makes
each engine answer from the records: 0.x reads the SQLite file as it goes,
so its `Open` reads little more than the schema. `Close` comes after the
timer stops, and on the Beta so does `debug.FreeOSMemory`, so each open
builds its copy in fresh memory from the system, as a new process does.
Without it, every open after the first would reuse the heap the last copy
left. Once `Compact` works, the Beta's file is compacted after it's built.
Until then, `Compact` is G5's stub, the file is a log of the 20 commits that
built it, and the benchmark logs a line saying so, which the table gives as
a note beside the Beta's time. Once `Compact` works the note goes, with
nothing changed here.

**The results file:** `test/results/beta-bench.txt`, beside 0.1's
`bench.txt`.

- The header gives what ran; the date, Go's and SQLite's versions and the
  commit; the kernel, the processor, the number of CPUs and the load average
  at the start; and the command.
- The table has a row for each benchmark, in the order they ran, with the
  middle of its runs on each engine, sorted by time (the faster of the two
  middle ones for an even count), and the Beta's target from BETA.md, "no
  slower than 0.x" for Put. Times have three significant figures in the
  largest unit that keeps them at least 1, such as 4.25 ms or 42.5 µs. A
  skipped benchmark's cell says what it waits for, and what a benchmark
  logged goes in a note under the table, marked beside its time. The line
  above the table says how long the run took.
- Then go test's output, as it printed it.

**How the table is written.** `Parse` and `WriteTable`, through `TestRecord`
with `HYPERCRUX_BENCH_OUTPUT` and `HYPERCRUX_BENCH_TABLE` set, as
`TestRecord` in `beta/sqlcorpus` records the corpus. A main package would
need a `main` on macOS and Windows too, where only its `doc.go` builds.
The script puts the header, the table and the output together.

**The script.** `scripts/record-beta-bench.sh`. With no arguments it runs
`go test -run ^$ -bench . -benchtime 3s -count 3 -timeout 60m -v
./beta/bench`, as `record-tests.sh` runs 0.1's, and writes the results
file. `-v` because go test shows a skipped benchmark only with it, and
`-timeout 60m` because the run will pass go test's 10 minutes as the Beta
runs more. The output shows as it comes. Given a file and flags, it writes
that file with those flags in place of `-benchtime 3s -count 3`, and the
header calls it a check. If the benchmarks fail, it writes nothing.

**Small data.** With `-short`, every file is a hundredth of its size, and
at least 10 records. The names keep 0.1's sizes, so the script's header
marks such a run as a check.

**CI, and the quick test.** The benchmarks run only with `-bench`. The tests
read source files and BETA.md, open one small Beta database and read sample
output. `TestEveryBenchmarkRunsOnBoth` reads this package's test files and
0.1's `bench_test.go` with go/parser: each of 0.1's 13 benchmarks has one
here of the same name, the only other is the opening one, and each is the
single statement `both(b, ...)`, so it runs on both engines, or is skipped
on the Beta by `later`. Every name in `later` and in `Targets` is a
benchmark here. `TestTheTargetsAreBETAs` reads BETA.md's Targets table and
holds `Targets` to it row by row, through `targetRows`.
